# Claude Code への指示テンプレート

> このフォルダをリポジトリ直下（例: `design_handoff_spaceai_ui/`）に置き、Claude Code には次の1行だけ貼ればOKです。書き換えは不要（環境依存の情報はフェーズ1で Claude Code 自身が調査・提案します）。
>
> ```
> design_handoff_spaceai_ui/CLAUDE_CODE_PROMPT.md を読んで、その「指示本文」に従って作業を開始して。
> ```

## 指示本文（Claude Code はここから読むこと）

```
design_handoff_spaceai_ui/ に Space AI の新UIデザイン一式がある。
まず README.md を読み、Space AI App.dc.html（本体8画面）と Space AI States.dc.html
（認証・モーダル・トースト・空状態・投稿履歴・通知のカタログ）をブラウザで開いて確認してから作業して。

目的: 既存アプリの「見た目だけ」をこのデザインに置き換える。
機能・API・データ取得・ビジネスロジック・ルーティング構造・状態管理は一切変更しないこと。

前提:
- HTMLファイルはデザインリファレンス。コードをコピーせず、このリポジトリの既存スタックの流儀で再現する。
  使用フレームワーク・スタイリング手法は指定しないので、フェーズ1で自分で調査して特定すること。
- 文言・数値はダミーなので、既存の実データ・実文言をそのまま使う。
- 【対象範囲】このパッケージに含まれる画面・状態だけを置き換える。パッケージに無い画面・状態
  （管理画面、独自ページ、カバーされていないモーダルや遷移など）は**既存デザインのまま一切触らない**。
  新旧デザインが一時的に混在してよい。判断がつかない画面は変更せず、対象外リストとして報告する。

進め方（必ずこの順で、フェーズごとにコミットを分ける）:
1. 現状把握（自動調査）: 以下を調べて報告し、私の承認を得てから着手する。
   - 使用フレームワーク・スタイリング手法（package.json・設定ファイルから特定）
   - ビルド・リント・テストの実行コマンド（scripts・CI設定から特定。以降のフェーズで使う）
   - 既存のUIコンポーネント・テーマ/トークン定義・共通レイアウト・ルーティング一覧
   - 「既存画面/コンポーネント → 新デザインの対応表」と実装計画、作業ブランチ名の提案
     （既存の命名規約に合わせる。例: feature/ui-redesign）
2. トークン導入: README のデザイントークン（色・フォント・角丸・影）を、フェーズ1で特定した
   既存のテーマ機構（tailwind.config / CSS変数等）に追加。既存の値は消さず追加し、この時点では見た目を変えない。
   フォント（Noto Sans JP / Inter / Material Symbols Outlined）のロードもここで。
3. 共通シェル: サイドバー(234px)・トップバー(54px)・ページコンテナ(max-width:1180px, bg #f6f6f7)を
   新デザインに置換。既存のルーティングとナビ項目の対応を維持。
4. 画面ごとに1画面ずつ置換（ホーム → ニュース → 投稿作成 → 下書き・スケジュール → 分析 → 設定 →
   ベースmd → 料金）。各画面ごとに: 実装 → ビルド/リント/既存テスト通過を確認 → 参照HTMLの同一画面と
   見比べたスクリーンショットを提示 → 私のOK後に次へ。
5. 補助UI: 認証画面（A-1〜A-4）・モーダル（M-1〜M-3）・通知ドロップダウン（N-1）・
   トースト/エラー/上限バナー（T-1〜T-4）・空状態（E-1〜E-3）・投稿履歴（H-1）を
   States カタログの ID を参照して既存の該当箇所に適用。既存システムに対応する画面・状態が
   無いものはスキップし、スキップした一覧を報告する。
6. プラン分岐（normal/md/premium）・トライアル表示・投稿作成の3状態（入力/生成中/編集）は、
   既存の状態・データソースに接続する。分岐条件のロジック自体は既存実装を正とする。

守ること:
- 作業はフェーズ1で承認された新規ブランチで。main へ直接コミットしない。マージは必ずPR経由で、
  私がレビュー・承認してから行う。
- コンポーネントの public な props / API・関数シグネチャ・DOMのdata属性やテストIDを壊さない。
  変更が必要なら先に相談。
- 既存コンポーネントで再現できるものは再利用し、無い場合のみ新規作成（命名は既存規約に従う）。
- 旧スタイル・旧コンポーネントは削除せず残す（未対象画面が参照しているため）。掃除は全画面完了後、
  参照が無いことを確認してから別コミットで。
- 各フェーズの後にフェーズ1で特定したビルド・テストコマンドを実行し、失敗したら先に直す。
- 判断に迷う点（既存UIとデザインの矛盾、足りない状態やAPI）は勝手に決めず、選択肢を挙げて質問する。

マージ前の最終確認（PR作成の条件）:
- 全画面（未対象の既存画面も含む）を巡回し、表示崩れ・consoleエラーが無いこと。
- ビルド・リント・既存の単体/E2Eテストがすべて通ること。
- 「新デザイン適用済み画面」「既存のまま残した画面」「スキップした補助UI」の3つの一覧を
  PR説明に記載すること。
```

## 使い方のコツ

- 貼るのは冒頭の1行だけ。環境情報（スタック・コマンド・ブランチ名）はフェーズ1で Claude Code が調査・提案するので、その報告を確認・訂正してから承認する。
- **一括で「全部反映して」と頼まない**こと。フェーズ分け＋各フェーズで確認を挟むのが、不具合を出さずマージする最短ルートです。
- Claude Code がスクリーンショットを撮れる環境（Playwright等）があるなら「各画面の before/after スクショを撮って比較して」と足すと精度が上がります。
- マージは PR レビュー後に自分で行うのが安全です。上の「マージ前の最終確認」を満たした PR だけをマージしてください。
- このフォルダ自体はリポジトリにコミットしなくても良い（.gitignore に `design_handoff_spaceai_ui/` を追加）。コミットする場合もデザイン資料として置いておけば実害はありません。不要になったら全画面完了後の掃除コミットで削除。
