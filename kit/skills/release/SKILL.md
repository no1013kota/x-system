# release：staging と本番へ反映する

運営者から受けた依頼を**全部終えてから**1回だけ実行する。途中のタスクはローカルにコミットを積み、ここでまとめて push する（CI は push ごとに走り、時間がかかるため）。

反映に使うコマンドと URL は `CLAUDE.md`「反映コマンド」表（「staging へ反映」「本番へ反映」「公開先 URL」）で指す。**「無い」と書かれた行の手順は飛ばし、報告に理由を書く**（黙って省略しない・手で代わりの操作をしない）。

## 0. 前提を確かめる（1つでも欠けたら止まる）

- `git status --porcelain` が空。ブランチは作業ブランチ。
- 作業ブランチと本番ブランチの名前が分かっている（例: `stg` → `main`）。`CLAUDE.md` にも運営者の指示にも無ければ、推測せず運営者に確認して止まる。
- 各タスクで `CLAUDE.md`「変更影響 → 必須の検証」の該当行を実行済み（未実行の行は報告に書く）。
- `CLAUDE.md`「検証コマンド」表の型検査・lint・単体・DBテストが緑（直近の変更後に1回。「無い」行は飛ばして理由を報告する）。
- 「反映コマンド」表のコマンドは **sandbox 外**で実行する（公開先へ接続するため。sandbox 内では名前解決に失敗することがある）。
- 引数 `staging` なら手順4で終える。

## 1. CI の要否を決める（判断ではなく対応表で）

`git diff --name-only origin/<本番ブランチ>...HEAD`（例: `origin/main...HEAD`）の全ファイルを次の表に当てる。**1つでも「必要」に当たれば CI を回す。表のどちらにも当たらないファイルがあれば「必要」**。運営者が「CI なしで」と言っていても、「必要」に当たる変更なら理由を添えて CI を回す（逆に運営者が「CI ありで」と言えば従う）。

| 変更したファイル | CI |
|---|---|
| `src/**`・DB の migration・E2E テスト・依存（`package.json`・lock ファイル）・設定ファイル（フレームワーク・型検査・テストランナー・E2E・ホスティングのもの）・CI の定義（GitHub Actions なら `.github/workflows/**`）・`scripts/**`・公開する静的ファイル（ブログの画像を除く）・`.env.example` | **必要** |
| `docs/**`・`tasks/**`・ブログ記事とその画像・`.claude/**`・ルートの `*.md`（`CLAUDE.md`・`README.md` 等）・`.gitignore`・`.mcp.json` | 不要（「検証コマンド」表の docs の検査と単体・DBテストが緑であること） |

「不要」で、GitHub と GitHub Actions を使っていれば、印を HEAD に付ける（コミットを書き換えない）:

```bash
git commit --allow-empty -m "chore(release): CI 軽量化（<理由: docs のみ 等>） [light ci]"
```

他の CI なら、CI の省略の仕組みがあればそれに従い、無ければ CI を回す。

## 2. push（1回だけ）

```bash
git push origin <作業ブランチ>     # 例: git push origin stg
```

## 3. CI を待つ（「必要」のときだけ）

GitHub Actions なら、Monitor で `gh run list --branch <作業ブランチ> --json headSha,status,conclusion` を HEAD の SHA で突き合わせ、`completed success` まで待つ。他の CI なら、その CI の画面かコマンドで HEAD の SHA の結果を確かめる。赤なら **ここで止めて原因を直す**（GitHub Actions なら `gh run view <id> --log-failed`）。直したら手順0からやり直す。

## 4. staging

「反映コマンド」表の「staging へ反映」を実行する。migration があり、コマンドが「適用したのでもう1回実行する」よう求める作りなら、その指示どおりもう1回実行する（求めなければ1回で終える）。

出力を読む。コマンドが結果の項目や「デプロイ後の検証」（人間確認・実物で1周 など）を出す作りなら、その各項目まで読む。そうでなければ終了コード（0 以外なら失敗）とエラー出力で判定する。❌ や失敗があれば止まる。軽量化した場合も CI は完了して緑になる（本体を飛ばすだけ）。
コマンドがホスティング側の build の完了を待たずに「build 中」で止まる作りなら、少し（例: 1〜2分）待って再実行する。

## 5. PR → 本番ブランチ

GitHub なら:

```bash
gh pr create --base <本番ブランチ> --head <作業ブランチ> --title "release: <内容>（<タスクID>）" --body "<内容・検証・migration の有無>"
gh pr merge <URL> --merge --delete-branch=false
git checkout <本番ブランチ> && git pull -q origin <本番ブランチ>
```

GitHub でなければ、使っているサービスの PR（マージリクエスト）で同じ順に行う。

本番ブランチのデプロイ（ホスティング側の build）が成功になるまで待つ。

- ホスティングが GitHub のコミットへ status を返すなら、`gh api repos/<owner>/<repo>/commits/<sha>/status` を一定間隔で見る（例: 15秒間隔・最大8分）。
- status が返らない（空のまま）なら、「本番へ反映」のコマンドが build の完了待ちを兼ねる作りならそれに任せる。そうでなければ、ホスティングの画面で本番ブランチの最新デプロイが成功したことを確かめてから進む（自分で確かめられなければ運営者に確認して止まる）。
- 失敗なら止めてホスティング側のログを見る。

## 6. 本番

「反映コマンド」表の「本番へ反映」を実行する（migration の再実行は手順4と同じ: コマンドが求めるときだけもう1回）。

- DB の接続先を切り替えてから反映する方式なら、切り替えと戻しの手順は「反映コマンド」表の「本番へ反映」の行に書かれているものだけを使う（書かれていなければ切り替えず、止めて運営者に確認する）。切り替えたら、**終わったら必ず staging へ戻す**（戻し忘れると次の staging 反映が本番 DB を見る）。
- 終わったら `git checkout <作業ブランチ>` で作業ブランチへ戻る。

## 7. 実ブラウザで確認する

変更した画面を「反映コマンド」表の「公開先 URL」で開く。Playwright の一時スクリプトはリポジトリ直下に置き、**終わったら消す**（残ると次の release の前提確認が「未コミットの変更」で止まる）。見るもの: HTTP 200・コンソールエラー 0・失敗リクエスト無し・画像やグラフが描画されている（遅延読み込みはスクロールしてから判定）。

## 8. 報告

PR（番号か URL）・本番 URL・確認した画面・**CI の要否とその理由**・migration の有無・実物で1周した検査の費用・所要時間・省略したものと理由。

## ルール

- 本番 DB へは「本番へ反映」以外で書かない（読むのは可）。
- force push・`git add -A`・コミットの書き換え（amend/rebase）をしない。軽量化の印は空コミットで足す。
- 途中で ❌ が出たら次の手順へ進まない。原因を直してから手順0へ戻る。
- **GitHub 公式の省略の印（角括弧付きの skip ci など）はコミットメッセージに書かない**（本文で言及するときも角括弧を外す）。GitHub Actions はメッセージ全体を見て workflow ごと止め、必須チェックが報告されず PR がマージできない。軽量化は CI の側で「印があれば本体を飛ばす」形にし、その印（例: light ci）も空コミットの件名にだけ付ける。
- 所要の目安は CI の時間で決まる（例: CI あり 約30分、CI なし 約15分）。
