# verify-integration：統合テスト

変更に関係する境界だけを選んで検証する。**単体テスト・E2E・外部liveの代わりにはしない。**

## 手順

1. **守る契約を先に列挙する** — DB制約／DBの権限（RLSなど）／API契約／状態遷移／冪等性／同時実行。無関係な変更はしない。
2. **接続先の安全を確認する** — ローカル（`127.0.0.1`）のテスト用DBであること。**ローカル以外（検証用の共有環境・本番）のDBで reset・drop・truncate・破壊的migrationをしない。** DBの初期化（migrationを全件クリーン適用し直す操作）は破棄可能なローカルでクリーン適用確認が要るときだけ（未明示なら承認を得る）。
3. **前提を整える** — ローカルDBが起動していることを確認する（DB未接続のとき実DBを使うテストをskipする仕組みなら、未起動でも緑に見える）。テストデータは一意ID。
4. **対象テストを選ぶ** — 下表。`rg` で対応する「実DBを使うテスト」を探し、無ければ追加する。
5. **実行する** — CLAUDE.md「検証コマンド」表の単体・DBテストを、変更に近いテストファイル1件から → 関連する境界群 → 共通基盤・schema・認証・DBの権限を変えたら全件回して退行確認（実DBを使うテストは、DB未接続のときskipではなくfailする形で回す）。
6. **完全性を見る** — pass数だけでなく fail／skip／todo。**必須の「実DBを使うテスト」が1件でもskipなら合格としない。**
7. **報告** — 環境／検証した契約／結果／skip／未検証事項。

## 変更種別 → 見る契約

| 変更 | 契約 |
|---|---|
| migration / DBの権限（RLSなど） | schema・seed・行レベルの権限・別ユーザー拒否・制約・**ロール権限（GRANT）** |
| サーバー側の処理（API・Server Action） | 認証・入力検証・所有権・Origin・署名・DB反映 |
| 定時処理 / job | 状態遷移・冪等・再試行・同時実行。DBキューなら lease・stale回収・deadline も（該当するものだけ） |
| 課金・利用量 | Webhook重複・イベント順序・契約状態・利用上限（残量）の原子的更新 |
| 外部API・AI | モックで契約と記帳（liveはしない。ただし下の「実物」は別途必須） |

## 見落としやすい3点

- **ロール権限（GRANT）を明示的に検査する。** RLSのような行レベルの権限は、テーブルレベルの権限があって初めて評価される。一般利用者ロールの可否だけでなく **サーバー側が使う特権ロール自身の権限**も見る。管理者権限でDBへ直結する経路と、DB側のロール権限が効く経路（DBクライアントライブラリ・API経由）の両方があるプロジェクトでは、前者は権限を回避してしまい、**後者だけが `permission denied` で落ちる**。テーブル追加時は既定権限（新しく作ったテーブルに自動で付く権限）まで確認する。過去に、特権ロールのGRANT漏れで外部連携が内部エラーになった事故があった（モックしたテストでは見えず、実DBを使うテストでしか再現しない種類）。
- **注入した本番実装は無検証になりやすい。** 依存注入で純粋化した中核は単体で覆えるが、**route/actionが渡す実DBクエリ・外部呼び出し**は覆えない。純粋関数のテストが充実しているほど「テスト済み」に見える。route/action自体を実DBで叩くテストの有無を確認する（例: 外部サービス連携を開始するAPIがあるなら、そのテストはセッションだけモックし、DBクエリは実際に走らせる）。
- **外部APIとの噛み合いは実物でしか分からない。** モックしたテストは「送ったリクエストが受理されるか」「返ってきたものを扱えるか」を一切検証しない。外部AI／外部APIの呼び出し・プロンプト・出力の形・tool定義に触れたら **CLAUDE.md「変更影響 → 必須の検証」表の「受理されるかの検査」＋「実物で1周」の両方**。

  受理されるだけでは足りない実例（すべて同じ日に見つかったもの。手動操作で初めて発覚した）:

  | 症状 | 検出できた層 |
  |---|---|
  | 必須パラメータの欠落で400 | 受理されるかの検査 |
  | 出力schemaが相手の要件を満たさず400 | 受理されるかの検査 |
  | 200だが応答の前置き文でJSON検証が落ちる | **実物で1周だけ** |
  | 200だが字数上限で全件破棄され結果が常に0件 | **実物で1周だけ** |

  費用が出るため、どの変更で自動実行するか（対象となるファイルの場所）と1周あたりの上限（例: $0.50）を「要決定」で決めておき、それに従う。上限を超えたら止めて報告する。**実費を必ず報告する。**

## ルール

- テストを通す目的で RLS・認可・署名検証・冪等guard を弱めない。
- ローカル以外（検証用の共有環境・本番）へ書き込まない。実課金・外部サービスへの実送信（投稿・通知）・実メールをしない。
- 「合格」は必要な統合テストが全実行され、failと必須skipが0のときだけ。環境不足なら**単体成功と統合未実施を分けて**報告する。
