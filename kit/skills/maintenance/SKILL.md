# maintenance：定期点検

**変更していないのに壊れる部分**を点検する。CIとテストは「変更したときに」壊れたことを教えるが、外部APIの仕様変更・新しい脆弱性・データの滞留・費用の増加は**時間の経過だけで**起こる。過去に、AI provider のAPIが新しい必須パラメータを要求するようになり、コード変更なしで生成が全滅したことがある。

運営者は1人なので、**判断はまとめて求め、実行できることは実行してから報告する**。

## 週次（引数なし・数分で終わる＋実費が少額出る）

上から順に実行し、**途中で失敗しても止めずに最後まで進める**（結果をまとめて報告するため）。

1. **状態確認**: 運営者向けの状態確認コマンド（または画面）があればそれを実行し、警告・異常の表示があれば原因を調べる。無ければ、公開先の主要画面と直近の定時処理の結果を開いて異常が無いか見る。
   （本番の異常を運営者へ通知する仕組み〔メール等〕があれば、その通知も確認する。）
2. **外部APIの受理確認**: CLAUDE.md「変更影響 → 必須の検証」表の「外部 AI／外部 API の呼び出し・プロンプト・出力の形」行にある**受理されるかの検査**を回す（実費ほぼ0円）。落ちたら**その日の変更ではなく provider 側の仕様変更**を疑い、公式ドキュメントで該当箇所を確認する。
3. **実物1周**: 同じ行の**実物で1周**（実APIで成果物まで見る検査）を回す（実費が出る。必要ならローカルでアプリを起動する）。AI・外部APIの成果物と、報告に出る成果物の形（例: 文字数・書式・リンクの有無など、そのアプリで決めている成果物の形）を目で見る。
4. **依存の脆弱性**: `npm run audit:check`。新しい high/critical が出ていたら、`scripts/audit-allowlist.json` に足す前に**上げられるか**を試す（`overrides` でnested版も寄せられることがある）。
5. **溜まったデータ**: テストで作ったユーザー・送信待ちのまま残った通知など、溜まりやすいデータの件数を見る。掃除するコマンドがあれば、まず dry-run で件数を見てから適用する。掃除の仕組みが無く溜まっているなら、件数を報告し `/add-task` で起票する。
6. **未pushの確認**: `git branch -vv` で未pushコミット数を見る。溜めすぎない。

**報告に含める**: 状態確認で出た警告・異常、受理確認と実物1周の結果と実費、audit の増減、掃除した件数、未pushコミット数、**運営者に決めてほしいこと**。

## 月次（`/maintenance monthly`・週次に追加して実行）

7. **費用の実績**: 当月と前月の外部APIの利用記録（従量課金の実績を記録しているテーブル・画面）を provider 別に集計し、想定と比べる。増えていれば原因（呼び出し回数の内訳。用途別・provider 別など）を分解して示す。
8. **バックアップの復元テスト**: `docs/` にあるDBバックアップの復元手順で**復元まで**試す。取れているだけでは復元できるとは言えない（手順が無ければ、それ自体を `/add-task` で起票する）。
9. **外部APIの変更確認**: 使っている外部API（AI provider・連携先サービス・決済サービスなど）の変更履歴を確認し、`docs/` で外部APIの仕様に依存すると記した箇所（「実装時に要確認」などの注記）と突き合わせる。破壊的変更があれば `/add-task` で起票する。
10. **古いデータの確認**: 定時処理の実行記録・外部取得の結果・通知など、保持期限を決めているデータの保持が効いているかを件数で見る。増え続けていたら cleanup が動いていない。

## ルール

- **実費が出る手順（3）は、実行前に金額の見込みを伝えてから実行する。**（7 は記録の集計なので実費は出ない）
- 外部へ副作用を出す操作（外部サービスへの実投稿・実課金・第三者へのメール）はしない。点検は読み取りと非productionに限る。
- 直せるものはその場で直す。仕様判断が要るものは `tasks/BACKLOG.md` の「要決定」へ追記して先へ進む。
- 見つけた不具合は `/add-task` で起票する（この場で実装しない。点検と修理を混ぜると、点検が終わらない）。
- 定期実行するなら `/loop /maintenance`（セッション中）またはクラウドスケジュール（`/schedule`）で週1回にする。

## なぜこれが必要か

`docs/operations/development-and-testing.md` §1 のテストの層はすべて**変更起点**で走る。変更していないのに壊れる次の4つは、どの層も捕まえない。

| 時間経過で壊れるもの | 週次で見る手順 |
|---|---|
| 外部APIの仕様変更（必須パラメータの追加など） | 2・3 |
| 新しい脆弱性の公表 | 4 |
| データの滞留（送信待ちの通知・テストユーザー） | 5 |
| 費用の増加 | 1（状態確認に当月費用が出るならそれ）・7 |
