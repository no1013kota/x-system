# security-audit：穴を探して、確かめて、直すか判断を仰ぐ

**推測を報告しない。** セキュリティの指摘は「ありそう」で書くと嘘が混ざり、本物の指摘まで信用されなくなる。**攻撃者の手順を1本書き、コードで到達を確かめてから**報告する。

**勝手に方針を変えない。** 穴の埋め方には「実装で閉じる」ものと「運営者が決める」ものがある。§4の表で機械的に振り分ける。

**分母を先に出す。** 何を見なかったかを言えない監査は、緑に見えても意味がない（過去の初回実行で、公開入口・依存・ファイル保存・CSPを丸ごと見落とした）。§1で入口を機械的に数え上げ、§5で1つずつ消し込む。

## 1. 攻撃面の棚卸し（最初にやる・省略しない）

**コマンドで数え上げる。** 手で列挙すると漏れる（過去に、CSP適用先の数え上げ漏れで認証画面が壊れたまま長期間気付かなかった）。

フレームワークによってファイルの置き場と目印は違う。`< >` はこのプロジェクトのものへ読み替えて実行する。

```bash
find <アプリのディレクトリ> -name '<APIハンドラのファイル名>'                 # API・公開ハンドラ（メール確認・webhook のような未認証の入口を含む）
grep -rln '<サーバー側処理の目印>' <サーバー側処理のディレクトリ>              # サーバー側の処理（Server Action など、ブラウザから直接呼べるもの）
find <アプリのディレクトリ> -name '<ページのファイル名>' -not -path '<認証必須の領域>'  # 未認証で開けるページ
ls <migration のディレクトリ> | tail -5                                      # 直近のスキーマ変更
git log --oneline -20 --name-only | grep -E '<API・サーバー側処理のパス>'      # 直近で増えた入口
```

出た一覧を**そのまま報告の骨子にする**。各項目は最後に「見た（根拠）」「穴あり」「範囲外（理由）」のどれかで埋まっていること。

## 2. 前提（このプロジェクトの守り方）

既に**検査で守っている**ものは「無い」ではなく「**検出器が生きているか**」を見る。

下の表の検出器はこのプロジェクトのものへ読み替える。対応する検出器が無い行は、無いことを理由つきで報告する（黙って省略しない）。

| 守り | 検出器（例。このプロジェクトのものへ読み替える） | 破れたときの症状 |
|---|---|---|
| 行の越境（RLS・GRANT など、使っている DB の仕組みの権限） | 実 DB で行の権限と役割の権限を検査するテスト | 他人のデータが見える／ログイン利用者の役割が直接書ける |
| 利用者どうしの干渉 | 利用者の分離を検査する実 DB テスト | 1人の大量投入で他人が止まる |
| 外向き副作用 | 外向きチャネル（外部サービスへの送信・メール・課金）の環境ガード ＋ そのテスト | 非本番から本物の送信・メール・課金が出る |
| 定時処理の認可 | 定時処理の入口の認可テスト | 秘密無しで定時処理が叩ける |
| サーバー側処理の到達性 | 呼ばれないサーバー側処理を検出するテスト | 呼ばれない処理が残り攻撃面になる |
| 環境ごとの鍵 | 環境と鍵の対応を検査するテスト | ローカルの鍵で本番を叩く |
| CSP（nonce） | 「検証コマンド」表のビルド ＋ 実ブラウザで公開ページのコンソールエラーまで見る | 事前描画で script が動かず**200のまま画面だけ壊れる** |
| 依存の脆弱性 | `npm run audit:check`（allowlist付き） | 既知CVEが本番依存に入る |
| 秘密値の露出 | 外部サービスの生エラーを保存する列があれば利用者向けの読み取りから除外する・利用者向けエラーへの変換・ログ送信前の秘匿処理 | 外部サービスの生文言・鍵がブラウザやログへ出る |

> **検出器がスタブで死んでいることがある。** 過去に、実 DB を使う API 入口のテストが決済 webhook の署名検証を
> **素の `Error`** でスタブしていたため、本文を public プロパティに持つ実クラスが一度も通らず、
> 本文がログへ漏れる穴を1件も検出できなかった。
> **「テストがある」で安心しない**——そのテストが**実物を通しているか**を確かめる。

## 3. 見る場所（全部見る。畳まない）

過去の初回実行で 4 に畳んだ結果、**公開入口・依存・ファイル保存・CSPが丸ごと落ちた**。分割して回すなら、
下の見出しをそのまま単位にする。

1. **認可（誰のデータか）** — 入口で本人か。所有権は**DB 問い合わせの条件（SQL なら where）**にあるか
   （アプリ側の突き合わせだけだと競合で抜ける）。ID を受け取る経路は毎回本人のものか確かめているか。
2. **未認証で叩ける入口** — API・メール確認・パスワード再設定・webhook のような認証前の入口・公開ページ。
   認証が無いのは仕様として正しいか。**そこで何が書き換わるか**（Cookie・DB・課金・メール送信）。
3. **費用の出る経路** — AI・外部API・メール送信・決済。契約（プラン・上限）のガードを通るか（正本は `docs/requirements/`）。
   **入口だけでなく実行時（ジョブを取り出す時点）でも見ているか**。上限・冪等キーを回避できないか。
4. **秘密値** — トークン・APIキー・定時処理の秘密・暗号鍵。
   ログ・**例外オブジェクトのプロパティ**・エラー本文・DB・応答・エラー監視サービスのcontextへ出ていないか。
5. **入口の検査** — Origin（CSRF）・署名（決済 webhook）・state/PKCE（OAuth）・人間確認・
   スキーマ検証の未知フィールド・**本文サイズの上限**。
6. **境界の値** — 利用者が渡す ID・URL・`next`・コード。オープンリダイレクト、SSRF、
   パストラバーサル、Cookie注入。
7. **保存物へのアクセス** — ファイル保存先（バケット等）が非公開か、ポリシーはあるか、
   **署名URLを誰の path に発行しているか**（クライアントから path を受け取っていないか）。
8. **AIへの入力と出力** — 利用者の文字列がプロンプトへ入る経路。**出力を信用してDB・外部APIへ
   流していないか**。合成後の**総量**に上限があるか（個々のフィールドに上限があっても合計は別）。
9. **時間差（TOCTOU）** — 確認から実行までに変わる状態（契約・上限・所有権）。
10. **依存とビルド** — `npm run audit:check` を実際に走らせ、**allowlistの理由が今も成り立つか**
    （到達経路が本番に無いと言えるか）を確かめる。
11. **応答ヘッダ・CSP** — 「検証コマンド」表のビルドを回し、実ブラウザで公開ページのコンソールエラーまで
    見る（`CLAUDE.md`「変更影響 → 必須の検証」の本番ビルド行）。CSPの許可先が増えていないか。
12. **可用性** — 未認証で無制限に回せる処理（ログ肥大・DB書き込み・外部API）。

## 4. 直すか、判断を仰ぐか

| 条件 | どうする |
|---|---|
| **明確な穴**で、直しても利用者から見た正常系の挙動が変わらない（検査の追加・条件の追加・値の秘匿） | **直す**。回帰テストを同じコミットで |
| 直すと**利用者に見える挙動が変わる**（できていたことができなくなる・文言が変わる） | **要決定へ**（暫定案つき） |
| **外部サービスの設定**が要る（決済・DB・人間確認・連携先 API の管理画面） | **要決定へ**。手順を書いて依頼する |
| 方針そのものの変更（列挙対策の可否・保持期間・公開範囲） | **要決定へ**。判断の材料を3点以上並べる |
| **本番データの露出が疑われる**（既に漏れた可能性） | **止めて報告**。調査手順を示し、勝手に消さない・勝手に通知しない |
| 反証できた（到達不能・既に守られている） | **報告に「棄却」として残す**。理由も書く |

## 5. 手順

0. **緑を確認**: `CLAUDE.md`「検証コマンド」表の型検査・lint・単体・DBテストを回す（表に無い行は飛ばし、理由を報告する）。
1. **棚卸し**（§1）。**分母の一覧を作る。**
2. **探索**（§3の1〜12）。各候補に *攻撃者の手順 / file:line / 到達の根拠 / 影響 / 深刻度*。
3. **反証（必須）**: 候補ごとに「どこかの層で止まらないか」をコードで確かめる。**止まるなら棄却**。
   ここを飛ばした報告は出さない（過去の初回実行でも候補の一部が反証で棄却になった）。
   **可能なら実際に動かして確かめる**（過去の初回実行では、ログ出力を実際に走らせて再現した）。
4. **振り分け**（§4）。
5. **直す**: 1件ずつ。**穴を再現する回帰テストを先に書き、修正を戻すと赤くなることを確認する**。
   検証は `CLAUDE.md`「変更影響 → 必須の検証」の該当行。
6. **要決定を書く**: `tasks/BACKLOG.md` の「要決定」へ `**D-<番号>: <論点>**` と案A/案B＋推奨。
7. **漏れの点検（省略しない）**: §1の一覧を1行ずつ消し込み、**「見なかったもの」を名指しで報告する**。
   「全部見た」と書かない——書けるのは消し込みが終わったときだけ。
8. **報告**: 直した穴／要決定／**棄却した候補と理由**／**見なかった範囲**。

## やってはいけないこと

- **検査を消して「直した」ことにする**（落ちるテストを消す・条件を緩める）。
- **秘密値を報告・コミット・テストへ書く**。再現手順は値を伏せる。
- 本番・検証環境（staging）のデータで試す。再現は**ローカルのテストデータ**で行う。
- 反証していない指摘を報告に混ぜる。
- 「多層防御」を理由に利用者の利便性を落とす変更を勝手に入れる（要決定へ）。
- **観点を畳んで回す**（§3を4つ以下にまとめない。過去の初回実行ではそれで4カテゴリを落とした）。

## Definition of Done

- [ ] §1の棚卸しを**コマンドで**行い、一覧を報告の骨子にした
- [ ] §3の1〜12をすべて回した（回せなかったものは理由つきで報告した）
- [ ] 候補すべてに**反証**を通した（棄却は理由つきで残した）
- [ ] 直した穴には**穴を再現する回帰テスト**があり、修正を戻すと赤くなることを確認した
- [ ] 判断が要るものは「要決定」へ案つきで起票した（実装していない）
- [ ] §1の一覧を消し込み、**見なかった範囲を名指しで**報告した
- [ ] 秘密値を報告・コード・テストへ書いていない
- [ ] `/doc-sync` 実行済み（方針に触れたら正本へ書き戻した）
