# speed-up：密結合をほどいて速くする

**遅さの正体はたいてい密結合。** 「画面がDBの都合を知っている」「判定が複数の層に散っている」「前の結果が要らないのに直列で待っている」——これらは同じ原因の別の症状で、ほどくと構造も速度も同時に良くなる。このスキルはその1本の作業に絞る。

`/refactor` との違い: あちらは内部品質全般（重複・命名・型・デッドコード）。**ここは「結合」と「待ち時間」だけ**を見て、必ず**数字**（往復回数・段数・実測ms）で前後を示す。

## 大原則（必ず守る）

1. **利用者に害があるならやらない。** 速さのために正しさ・分かりやすさを削らない。判定は下の「§ やる前の関門」で機械的に行う。**迷ったら実装せず、`tasks/BACKLOG.md` の「要決定」へ暫定案つきで起票して先へ進む**（CLAUDE.md 原則5）。
2. **推測で直さない。** 着手前に数字を取る。取れないものは「効きそう」でも触らない（効果が確認できない変更は、リスクだけが残る）。
3. **振る舞い保存。** 外部挙動・DB/API契約・画面仕様・エラー契約を変えない。変わるならこのスキルの対象外（`/dev-loop` へ）。
4. **1単位＝1コミット（WIP=1）。** 速度改善は「まとめて入れて、どれが効いたか分からない」が最悪。1つ入れて測る、を繰り返す。
5. **判定を消して速くしない。** 認可・契約・前提の検査は、**別の層へ移すのは可・消すのは不可**。移したときは移した先のテストを先に用意する。

## やる前の関門（利用者への影響判定）

候補ごとに次の表を上から当てる。**1つでも「やらない」に当たったら実装しない**（報告に理由を残す）。

| 変更 | 判定 | 理由 |
|---|---|---|
| **契約状態・利用上限・残量・課金情報をリクエストを跨いでキャッシュする** | **やらない** | 解約したのに使える／契約したのに使えない、が起きる。金銭と権利に関わる値は毎回読む |
| **認可・契約・前提の検査を削る**（「往復が減るから」） | **やらない** | 費用の出る操作が開く。移設は可（§大原則5） |
| **並列化・遅延化で失敗が握り潰される**（片方failで黙って空） | **やらない** | 「正常な空」と「失敗による空」が同じ見え方になる（原則1）。失敗の理由が残る形（例: `Promise.allSettled`）にしてから並列化する |
| **費用の出る経路（AI・従量課金の外部API）をprefetch／先読みする** | **やらない** | 押していないのに課金される |
| **エラー・失敗の記録（エラー監視サービス・台帳）を削る** | **やらない** | 原因が辿れなくなる（原則2） |
| 表示件数を絞る・一部を後から読む | **画面に明示できるならやる**。できないなら**要決定へ** | 「全部見えている」と誤解させない（例: 「ほかN件は『すべて見る』から」） |
| 情報の出る順・位置・タイミングが変わる | **要決定へ**（暫定案つき） | 速さと引き換えに運営者の見え方が変わる。決めるのは運営者 |
| 内部だけの変更（直列→並列・重複往復の削除・純粋関数の抽出・境界の整理） | **やる** | 利用者から見た結果が同じ |

## 手順

1. **緑を確認**: CLAUDE.md「検証コマンド」表の型検査・lint・単体・DBテストを回す。緑でなければ報告して着手しない。
2. **計測（飛ばさない）**: 「§ 何をどう測るか」で**現在値**を取る。数字が取れない候補は捨てる。
3. **候補出しと関門通し**: 「§ 見るべき結合」で洗い、*file:line / 症状 / 現在値 / 期待効果 / 関門* を付ける。`--audit` はここで止めて報告。
4. **1単位を実行**: 関門を通ったうち**効果が大きく影響範囲が狭いもの**を1件。テストが薄ければ先に特性テストを別コミットで足す。
5. **再計測**: 改善していなければ**戻す**（速くならなかった変更は複雑さだけを足す）。
6. **検証**: `CLAUDE.md`「変更影響 → 必須の検証」に従う。特に CSP・キャッシュ・事前描画など**本番ビルドでしか出ない設定**は「検証コマンド」表のビルド ＋ 実ブラウザ。全リクエストを通る層（middleware など。フレームワークによっては proxy と呼ぶ）は CSP ヘッダの生成やセッション更新を担っていることがあるため、触れたら同じ検証を回す。サーバー／クライアント境界は**実ブラウザ**（型検査で出ない失敗がある・§落とし穴）。
7. **docs同期＋コミット**: `/doc-sync`（往復・段数は `docs/requirements/` の処理の流れを書いている箇所へ）。**数字を本文へ残す**（「4段→2段」）。`perf(...)` / `refactor(...)` で1単位＝1コミット。報告に**前後の数字**・落とした候補と理由・要決定へ回した項目を書く。

## 何をどう測るか

| 対象 | 測り方 | 目安 |
|---|---|---|
| **サーバー側の直列往復（waterfall）** | 対象ページの `await` を上から読み、**前の結果を使っていない `await` が連続していないか**数える。「N段」と記録する | 依存が無いのに2段以上あれば候補 |
| **全リクエストに乗る処理** | 全リクエストを通る層（middleware など・セッション更新）を読む。ここは**全遷移**を通るので、1本の往復が全画面に効く | DB・外部HTTPが1つでもあれば最優先候補 |
| **同一リクエスト内の重複読み取り** | 同じ関数が複数のサーバー側描画部品（React なら Server Component）から呼ばれていないか。リクエスト内メモ化（React なら `cache()`）でラップ済みかを確認 | 未ラップの共通読み取りは候補 |
| **実測の遷移時間** | **本番ビルドで測る**（「検証コマンド」表のビルドで作った成果物を別ポートで起動し、E2E の接続先をそこへ向ける）。一時的なE2Eテストで `page.goto` → 主要要素が見えるまでを3回測って中央値。計測用のテストはコミットしない | 前後比較にだけ使う。**開発サーバーの数字は大きくぶれる**ので、往復1本ぶんの改善は埋もれて見えない（過去に実際に埋もれた） |
| **HTTP経由のDB読み取り**（DBをREST API越しに叩くクライアント） | 直接接続（コネクションプール）と違いHTTPを1往復する。**同じ行を2か所から読んでいないか**を先に見る | 同じ利用者プロフィール行を画面と共通レイアウトで別々に読む形は候補（過去に2画面ぶん削除した） |
| **取得件数** | 一覧・履歴の `limit` の有無。無ければデータが増えるほど遅くなる | limit 無しは候補（ただし件数の明示とセット） |
| **クライアントへ送る量** | 「検証コマンド」表のビルドの出力が画面／経路ごとのサイズを出すなら、それを見る。クライアント側で動く部品の指定（React なら `"use client"`）が必要以上に上位に付いていないか | 目に見えて大きい画面／経路だけ扱う |

計測用の一時テスト（E2E のテストディレクトリに `tmp-*` の名前で置き、**必ず消す**。Playwright を使っていれば次の形）:

```ts
const t0 = Date.now();
await page.goto("/<対象の画面>");
await expect(page.getByRole("heading", { name: "<画面の見出し>" })).toBeVisible();
console.log("elapsed", Date.now() - t0);
```

## 見るべき結合（候補チェックリスト）

- **判定が散っている**: 同じ条件（契約・権限・上限）が複数の層に書かれている。→ **1か所を正本にして他は導出**。派生が消えると往復も消えることが多い（例: 画面の可否判定を1か所へ寄せた結果、全リクエストを通る層のDB読み取りが不要になった）
- **直列 await**: 依存の無い取得が縦に並んでいる。→ 並列で1波に（例: `Promise.all`。過去に共通レイアウトとホーム画面の直列 await を、例: 5段→2段 のように減らした）
- **重複読み取り**: 同じ利用者プロフィール／アカウントを画面内で何度も読む。→ リクエスト内メモ化（React なら `cache()`）
- **書き込みが読み取り経路に混ざっている**: 表示のたびに upsert する等。→ read-first にして、欠損時だけ修復
- **UIがDBの都合を知っている**: 画面が生SQL相当の形を受け取る。→ 表示に必要な形へ変換する層を挟む
- **副作用が中核に埋まっている**: DB・外部API・時刻が関数内で直接呼ばれ、テストで差し替えられない。→ 注入（外から差し替えられる形にする）
- **境界の乱れ**: サーバー専用のものがクライアント側から辿れる／クライアント側で動く部品が不必要に上位にある
- **上限が無い取得**: 件数が増えるほど遅くなる経路

## 落とし穴（実際に踏んだもの）

- **共通ナビゲーション部品を丸ごとクライアント化してはいけない。** 関数を props で渡している部品はサーバー／クライアント境界を越えられず、**その部品を使う全画面が実行時エラー**になる。**型検査では検出できない**（過去に実際に踏み、E2Eが全滅して切り戻した）。境界を動かす変更は必ず実ブラウザで確認する。
- **静的化・事前描画（prerender・ISR）で速くする前に、CSPとの両立を確かめる。** nonceベースのCSPを使っていれば静的な事前描画と両立せず、全ルートを動的描画にしている場合がある（`docs/decisions/` のADRと `docs/requirements/` を確認）。その場合は prerender へ寄せる提案をしない。**事前描画されたページはscriptが1本も実行されず、HTTPは200のまま画面だけ壊れる**（過去に長期間気付けなかった）。触れたら「変更影響 → 必須の検証」の本番ビルドでしか出ない設定の行（ビルド ＋ 実ブラウザ）を回す。
- **リクエスト内メモ化はリクエスト内だけ。** リクエストを跨ぐキャッシュ（フレームワークのデータキャッシュ・再検証つきキャッシュ）を契約・利用上限（残量）・利用者が編集中のデータに使わない（§関門）。
- **middleware など全リクエストを通る層に処理を足さない。** ここの1往復は全画面の遅延になる。逆に削ると効果が最も大きい。
- **「速くなった気がする」で終わらせない。** 前後の数字が無い変更はコミットしない。

## Definition of Done

- [ ] 前後の**数字**がある（往復回数・段数・実測ms のいずれか）
- [ ] 関門を全候補に当てた（落とした候補と理由を報告に書いた／判断が要るものは「要決定」へ起票した）
- [ ] 外部挙動を変えていない（テスト緑・契約不変）。境界を動かしたら実ブラウザで確認した
- [ ] `CLAUDE.md`「変更影響 → 必須の検証」の該当行を実行した
- [ ] `/doc-sync` 実行済み（数字を正本へ残した、または影響なしを理由付きで確認）
- [ ] 1単位でコミットした（`perf(...)` / `refactor(...)`・Co-Authored-By 付き）
