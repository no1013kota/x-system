# verify-e2e：E2Eテスト

ユーザー操作から画面・サーバー・DBの結果までを検証する。**確認範囲を超えた合格を報告しない。**

## 手順

1. **シナリオを決める** — タスク・docs・`git diff` から「開始状態 → 操作 → 期待する画面／DB・ジョブの最終状態」を書く。変更に直結する最小シナリオ＋壊れやすい主要経路。
2. **基盤を選ぶ** — リポジトリで管理しているE2Eテスト（Playwrightを使っていればそれ。CLAUDE.md「検証コマンド」表の E2E）を優先。無ければ探索的確認でよいが「自動E2E合格」とは呼ばない。
3. **安全を確認する** — 下表。1つでも外れたら止める。
4. **データを用意する** — 専用テストユーザー＋実行ごとの一意ID。作成IDを記録。DB全体をresetせず他者データに触らない。
5. **実行する** — 表示だけでなくURL・入力・二重送信防止・エラー表示・最終状態。console error・失敗request・予期しないredirectも見る。
6. **後片付け** — 今回作成分だけ削除。失敗時も試み、残ったらID付きで報告。
7. **報告** — 自動か探索的か／環境／シナリオ／結果／証拠／未検証事項。

## 安全な既定（E2Eの起動前に検査する。自動で検査する仕組み〔fixtureのguard等〕が無ければ実行前に手で確かめる）

| 項目 | 値 |
|---|---|
| 実行環境を示す環境変数 | 開発／テスト用の値（本番を指さない） |
| 外部サービスへの送信（投稿・通知など）のモード | dry-run（実際には送らない） |
| DB / baseURL | ローカル（`127.0.0.1`） |
| AI | モックまたはテストキー |
| 決済サービス | test / sandbox |
| メール | ローカルで捕捉する受信箱（外へ送らないテスト用のメールサーバー） |

**やらない**: 本番接続、外部サービスへの実投稿・実送信、実課金、第三者への実メール。秘密値をスクショ・trace・ログ・報告に残さない。

## 落とし穴（実際に踏んだもの）

- **fixtureで「済んだ状態」を作ると、その状態にする行為自体が未検証で残る。** 例: 外部アカウント連携の行を直接insertすると、連携の入口を一度も通らない。連携・登録・課金など入口がある機能は、飛ばした経路を別ケースで1回通す。外部サービスへは行かず、リダイレクト先（Location）や発行cookieの検証で止めてよい。
- **生成物は実データで描画するところまで見る。** 画像・グラフ・外部から取得した内容のカード・集計表。要素の存在では足りず、**実際に読み込めたこと**（画像なら `naturalWidth>0`）を確認する。CSP違反・署名URLの失効・レイアウト崩れ・デコード失敗はブラウザで実物を描画したときにしか出ない。過去の実例: 生成画像のプレビューがCSPの `img-src` に弾かれローカルでは**必ず**非表示だったのに、E2Eが画像を持つデータを一度も描画しておらず気付けなかった。
- **ジョブはローカルで自動進行しない。** ジョブの実行口（workerのエンドポイントか該当の定時処理）を明示的に叩き、完了は**期限付きで**pollする（無制限に待たない）。
- **1件目のtimeoutを「flaky」と即断しない。** アプリのコードを編集した直後は初回コンパイルで時間切れになりうる。編集を挟まず再実行して緑かを見る（起動前に主要な画面を温める仕組みがあっても、動的な画面は残る）。
- **flakyを無条件retryで隠さない。** 原因と再現条件を先に探す（`CLAUDE.md`「変更影響 → 必須の検証」の「落とし穴」）。
- **外部サービスに毎回依存すると、通しでだけ落ちる。** 過去の実例: 全件がログインで人間確認（bot対策のウィジェット）を通していたため、通し1回で相手のサービスへテスト件数分の要求を投げ、**繰り返すほど失敗が増えた**（単独実行は必ず緑）。待ち時間を伸ばす対処では、失敗が「トークンが来ない」から「ログインだけで時間を使い切る」へずれるだけ。**依存そのものを断つ**——ウィジェットのスクリプトの配信だけをスタブへ差し替え（Playwrightなら `page.route`）、**サーバー側の検証は本物のまま通す**（bot対策サービスが用意する「常に成功するテスト用のsecret」をローカルのサーバー側に設定しておけば、検証コードを変えずに通る）。本物のウィジェットは1件だけ残し、許可ドメイン等の相手側の設定は `CLAUDE.md`「変更影響 → 必須の検証」の「外部サービス側の設定に依存する画面」の行（実ブラウザ）で見る。
- **通り過ぎる途中の状態を掴まない。** 「登録直後は `pending`」のような検査は、外部API（AIなど）のキーがテスト用のダミーで、登録直後に走る後続のジョブが即失敗すると、`pending` を通り越して落ちる。**速さで結果が変わる検査**になっていないか見る（見たいのが「登録された」なら、行の存在で見る）。
- **前提を作る順番が結果を決める。** 画面が「終わるのを待って次を起票する」ループを持つとき、先にジョブを畳むと**その瞬間に新しいジョブが生える**。**画面を作り直して（reload）ループを捨ててから**状態を作る。

## 変更別に見る経路（該当のみ）

| 変更 | 通す経路 |
|---|---|
| 認証 | signup → 確認メール → login → logout → recovery → 保護route |
| フォーム | 正常／validation／二重送信／loading／再試行 |
| 外向きの送信（外部サービスへの投稿・通知など） | 作成（AI生成があればそれも）→ ジョブ完了 → 送る内容の編集 → dry-run送信 → 送信結果の記録 |
| 予約実行・定時処理 | 予約の登録 → 予定時刻の到来処理（dry-run）→ 同じ回の再実行で重複しないこと |
| 課金 | test環境で契約状態と画面権限 |
| UI | 狭い幅／キーボード／label／focus |

## ルール

- live外部サービスが必要になったら停止し、`tasks/BACKLOG.md` の「要決定」へ書いて運営者の判断を仰ぐ（勝手に本物へ接続しない）。
- 認証・課金・同意・外向き送信の安全策（dry-run等）を迂回しない。
- 「E2E合格」は自動シナリオが全assertion通過したときだけ。探索的確認は「確認済み（自動回帰は保証しない）」と書く。
