# refactor：システム全体の安全なリファクタリング

外部から見た振る舞い・仕様・公開API/契約を変えずに、内部品質（重複・複雑度・境界・型・命名・デッドコード・テスト容易性）を上げる。**全体を一度に書き換えない。** dev-loop と同様バックログ駆動で、1回の実行で扱うのは1単位のみ（WIP=1）。仕様変更を伴うものはリファクタではないので dev-loop 側で扱う。

## 大原則（必ず守る）

1. **振る舞い保存**: 外部挙動・DB/APIの契約・画面仕様・プロンプト出力・エラー契約を変えない。変わるならリファクタではない＝中止してユーザーに報告する。
2. **テストが安全網**: 着手前に全テストが緑であることを確認する。緑でない状態からは始めない。対象の挙動を守るテストが薄い箇所は、**先に特性テスト（characterization test）を別コミットで追加**してからリファクタする。
3. **小さく・可逆に**: 1単位＝1つの一貫した変更。無関係な変更を混ぜない。単位ごとに検証し、緑にできなければ直すか revert する。
4. **仕様の正本を守る**: docs/ が参照する構造（ファイル名・公開関数・型名・DBテーブル等）を変えたら /doc-sync で追随する。表現しきれない横断的判断は docs/decisions/ に ADR を残す。
5. **規約・秘密情報**: 実キーを混入しない。応答・コミット・ドキュメントは日本語、コード識別子・コメントは英語。`git add -A` を使わず、`git status` で無関係な変更の巻き込みを防ぐ。

## 手順

1. **緑を確認**: `git log --oneline -15` と `tasks/BACKLOG.md`・`tasks/REFACTOR_PLAN.md`（あれば）を読み、`CLAUDE.md`「検証コマンド」表の型検査・lint・単体・DBテストが緑であることを確かめる（表に無い行は飛ばし、理由を報告する）。緑でなければ報告し、着手しない。
2. **監査**: 計画に未着手候補があれば飛ばす。無ければ対象範囲を「## リファクタの観点」で洗い、各候補に *file:line / 種類 / 期待効果 / リスク / 規模 / 影響するテスト* を付ける。
3. **計画（要承認）**: 価値が高く低リスクな順に `tasks/REFACTOR_PLAN.md` へ並べる。**全体リファクタは着手前に計画を提示して承認を得る。** 判断が要るものは暫定案つきで「要決定」へ。`--audit` はここで停止。
4. **1単位を実行（WIP=1）**: 最上位の未着手を1件。テストが薄ければ特性テストを別コミットで先に足す。項目外へ広げない。
5. **検証**: `CLAUDE.md`「変更影響 → 必須の検証」に従う。加えて**差分が外部挙動・契約・スナップショットを変えていないこと**。動く経路があれば実際に動かす。
6. **docs同期＋完了**: `/doc-sync`（影響なしなら理由付きで記録）。計画のステータスを更新し、`refactor(<scope>): 概要` でコミット（関連ファイルのみ `git add`・Co-Authored-By 付き）。報告に実施内容・判断・検証結果・次候補・新たな要決定を書く。

## リファクタの観点（監査チェックリスト）

- **重複**: コピペされたロジック・定数・型の共通化（Single Source of Truth 化）。
- **複雑度**: 長大な関数・深い分岐の分割、早期return、責務分離。
- **境界・依存**: レイヤ違反（UIからDB直結等）、循環依存、サーバー／クライアント境界の乱れ（フレームワークにその区別があれば。例: サーバー専用のモジュールがクライアント側から import されている）。
- **型**（静的型のある言語なら）: `any` 相当の緩い型・不要なキャスト・非null断定の削減、判別可能ユニオン化、DB の列挙値とコード側の型のドリフト解消。
- **命名・一貫性**: 命名規約・ファイル配置・エラーハンドリング様式・レスポンス形の統一。
- **デッドコード**: 未使用の export・依存・フラグ・分岐の削除。**参照0件は機械的に洗える**——リポジトリ全体で識別子の出現が定義行だけの export を数える。消すときは次の2つに注意する。
  - **型だけ使われていることがある。** コンポーネントが未使用でも、同じファイルの型を誰かが import している。**型は置き場（型だけを集めたファイル）へ移す**——中身が消えた後もファイルが残る原因はこれ。
  - **検出器が消えたファイルを見張っていると、検査自体が落ちて何も守らなくなる。** 削除したら検出器の相手を実在するファイルへ寄せる。
- **テスト容易性**: 副作用の注入化（純粋関数への抽出）、薄い箇所への特性テスト追加。
- **パフォーマンス**（挙動を変えない範囲）: 明白なN+1・不要な再計算・重い同期処理の是正。

## やってはいけないこと

- 全体の一括書き換え・大規模な同時変更（必ず小単位へ分割する）。
- 外部挙動・DB/API契約・画面仕様・プロンプト出力の変更（それは機能変更＝ dev-loop で扱う）。
- テストを緑にしないままのコミット、スナップショット・契約テストの安易な書き換え。
- 承認前の全体リファクタ着手、無関係な変更の混在、`git add -A`。
- PRD の「やらないこと」（スコープ外の宣言）に反する方向への「改善」。検出したら実装せずユーザーへ警告する。

## Workflow の活用（任意）

監査（手順1）や広域の機械的置換は、ユーザーが多エージェント実行（ultracode／workflow）に opt-in している場合に限り Workflow で並列化してよい。「領域 × 観点」でfan-outして候補を集約→重複排除→リスク検証、という流れにする。実行フェーズ（手順3〜6）は必ず1単位ずつ検証ゲートを通し、複数単位を無検証で並行適用しない。

## Definition of Done

- [ ] 外部挙動を変えていない（テスト緑・契約/スナップショット不変を確認）
- [ ] `/doc-sync` 実行済み（更新した、または影響なしを理由付きで確認）
- [ ] `tasks/REFACTOR_PLAN.md` のステータスと実装メモを更新した
- [ ] `refactor(<scope>): …` かつ Co-Authored-By 付きでコミットした
