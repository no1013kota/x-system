## 1. テストは何層もあり、それぞれ見えないものがある

**どの層も単独では不十分**で、層ごとに「原理的に見えないもの」がある。だから `CLAUDE.md` の「変更影響 → 必須の検証」で、層を人が選ばず**対応表で決める**。

| # | 層 | 守るもの | **見えないもの** |
|---|---|---|---|
| 1 | 型・lint | 型の整合 | 実行時の振る舞い |
| 2 | 単体テスト | 純粋関数・モック注入での分岐と境界値 | **モックした境界の向こう側すべて** |
| 3 | DB 統合テスト | 実 DB での制約・権限・サーバー処理の本番実装 | 外部 API・ブラウザ描画 |
| 4 | E2E（実ブラウザ） | 操作・遷移・実データの描画 | 外部 AI の中身、本番ビルドでしか出ない設定 |
| 5 | 外部 API の受理確認 | 送っているリクエストが実 API に受理されるか | 応答をアプリが扱えるか |
| 6 | 実物スモーク | 応答をアプリが扱えて成果物が正しいか | 本番固有の環境差 |
| 7 | CI | 1〜4 の実行そのものを強制 | 5・6（実キーが必要） |
| 8 | 外部サービス側の設定 | 相手側の設定（許可ドメイン・メール送信元）がその環境で通るか | — |

層5と層6は別物: **受理される**（5）だけでは足りず、**扱える**（6）まで見る。

## 2. 検証をいつ回すか

遅いのはビルドと E2E だけなので、その2つだけ push 前へまとめる。変更ごと＝型・lint・単体（DB込み）。コミット前＝＋docs 検査。push 前＝＋ビルド・E2E。ただし「その変更に固有の検証」（外部 API の実物1周、本番ビルド設定、定時処理の実叩き）は段を待たずにその場で回す。

## 3. テストを書くときの決まり

- 実装詳細ではなく**公開される入出力・状態遷移・エラー**を検証する。
- 不具合修正は**修正前に失敗する再現テストを先に**書く。
- 「正常な空」と「失敗による空」を別の値で表し、テストでも区別する。
- flaky に見えたら回数ではなく**落ちる条件**を探す。
