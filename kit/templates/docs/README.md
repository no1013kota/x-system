# ドキュメントマップ

`docs/` は仕様の正本（Single Source of Truth）。**実装と食い違った状態を放置しない。**

## 1. どこに何があるか

| 文書 | 何が書いてあるか | 更新するとき |
|---|---|---|
| [PRD](./PRD.md) | 何を作るか・なぜ。機能一覧、スコープ、料金、上限 | 要件・料金・スコープ・上限が変わる |
| [要件詳細](./requirements/README.md) | どう作るか（画面・データ・処理・API） | 実装の構造が変わる |
| [開発とテストの進め方](./operations/development-and-testing.md) | テストの層と盲点、いつ回すか | 検証手段が変わる |
| [ADR](./decisions/README.md) | 上記で表現しきれない技術判断 | 不可逆な選択をしたとき |

## 2. 仕様の所有ルール（どこに書くか）

| 種類 | 正本 | 他の文書には |
|---|---|---|
| 機能の有無、プラン差、料金、上限 | PRD | 参照だけ |
| DB・API・画面・処理の数値と構造 | `requirements/` の担当文書 | 要約だけ |
| 未決の事業判断 | `tasks/BACKLOG.md`「要決定」 | 重複記載しない |

**同じ数字を2か所に置かない。** 片方だけ古くなる。1つの変更が複数文書へ影響するなら同じ作業単位で更新する。

## 3. コードとのズレを止める仕組み

**手で数え上げた一覧は必ず古くなる。** だから**機械が突き合わせる**検査を作る（例: docs 内のファイルパスが実在するか、docs の更新日がその文書を最後に変えたコミットの日付と合っているか、docs の表と DB の列が一致するか）。**新しく一覧や数値を docs へ書くときは、突き合わせる検査も同時に作る。** 作れないなら「実測が正」と明記して日付を添える。

このキットに最初から入っている docs の検査は2つ: `scripts/check-doc-refs.mjs`（docs と CLAUDE.md がバッククォートで指すファイルの実在）と `scripts/check-doc-dates.mjs`（更新日とコミット日付・version と変更履歴の一致）。どちらも git が追跡しているファイルだけを見る。依存ライブラリの脆弱性検査 `scripts/audit-check.mjs` は docs の検査ではなく、別に1本ある。

## 4. 更新ルール

- **version は文書内ヘッダを正とする。** ファイル名に version を含めない。
- 仕様変更時は冒頭の**更新日**と末尾の**変更履歴**を更新する。表記修正だけなら version は上げない。
- コードがまだない領域は「未実装」であることを明記する。
- コミット前に `/doc-sync` を実行する。
