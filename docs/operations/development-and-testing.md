# 第1部　やること

## 1. アプリを立ち上げる

毎回やることです。ターミナルで2つ実行します。

```bash
supabase start    # データを保存する場所を起動する
npm run dev       # アプリを起動する
```

- ブラウザで **http://127.0.0.1:3000** を開きます。
- **`localhost` ではなく `127.0.0.1`** と入れてください。`localhost` だと X（Twitter）との連携が動きません。
- 初めて使うパソコンでは準備が必要です。手順は [ローカル開発](./local-development.md) にあります。

**Claude に頼むなら**

```
アプリを起動して、開ける状態か確認してください。
```

---

## 2. 作りたいものを伝える

思いついたこと・直したいことを、**そのまま言葉で伝えれば作業リストに入ります。** 書き方を覚える必要はありません。

```
/add-task ニュースの通知をメール以外でも受け取れるようにしたい
```

```
/add-task 投稿履歴から同じ内容をもう一度投稿できるようにしたい
```

- Claude が「それは今回の開発範囲か」「既にできることではないか」を確認してから、作業リスト（`tasks/BACKLOG.md`）に追加します。
- 決めてほしいことがあれば聞いてきます（例: 費用が増える／画面の見せ方が複数考えられる）。
- **範囲外の要望は追加せず、その理由を教えてくれます。** 勝手に作り始めることはありません。

> 作業リストに1件もないと §3 の `/dev-loop` は動きません。まずここで登録します。

---

## 3. 作ってもらう

```
/dev-loop
```

これで **1件分の開発が最後まで終わります**（作るものを選ぶ → 実装 → テスト → 説明書の更新 → 保存）。

- 特定のものを先に作ってほしいときは `/dev-loop T-M7-28` のように番号を付けます。番号は作業リストに書いてあります。
- 続けて何件も進めたいときは `/loop /dev-loop`。止めたいときは止めるまで続きます。
- 判断が必要な場面では止まって聞いてきます。**勝手に決めて進むことはありません。**

**終わったら確認すること**

```
今回何を変えて、何をテストして、何がまだ確認できていないか教えてください。
```

**覚える言葉はこれだけ**

| 言いたいこと | 打つもの |
|---|---|
| こうしたい／これが困る（登録だけ） | `/add-task 〜したい` |
| 1件作ってほしい | `/dev-loop` |
| 続けて何件も作ってほしい | `/loop /dev-loop` |
| 画面の見た目を整えてほしい | `/ui-polish <画面の名前>` |
| 動きを変えずに中身を整理してほしい | `/refactor` |
| 説明書とコードのずれを直してほしい | `/doc-sync` |

- 下の3つは **`/dev-loop` が必要に応じて自分で使います。** 単独で頼みたいときだけ打ってください。
- テストは打ちません。§4のように**言葉で聞く**だけです。

---

## 4. テストしてもらう

**何をテストすべきかは、自分で判断しなくてよいです。** 次の文をそのまま貼ってください。

```
未コミットの変更と直近のコミットの両方を見て、変更した箇所を特定してください。
そのうえで CLAUDE.md の「変更影響 → 必須の検証」表の該当行を、すべて実行してください。
お金がかかる確認が含まれるなら、実行する前に金額を教えてください。
終わったら、確認できたこと・確認できていないこと・実行しなかった行とその理由を
分けて報告してください。
```

なぜこの言い方なのか（3つとも、抜けると実際に機能しません）。

- **「未コミットの変更と直近のコミットの両方」** — 別の日や別の会話で頼むと、Claude は何を変えたか知りません。しかも保存（コミット）済みだと差分は空に見えます。
- **「表の該当行をすべて」** — その場の判断で選ぶと漏れます。2026-07-28 に4系統が同時に壊れた原因がこれです（§10）。
- **「金額を教えて」** — 「全部」と頼むと、AIを実際に呼ぶ確認（約45円）まで黙って実行され得ます。

**先に §1（`supabase start`）を済ませてください。** データの保存先が止まっていると、データベース関連のテスト58本は**実行されないまま「成功」と数えられます**（`npm test` は緑に見えます）。公開前の確認（`npm run release:check`）だけは、この場合ちゃんと止まります。

> **`/dev-loop` で作った場合は、ここまで自動で終わっています。** この節は、自分で直接お願いしたときや、念のため確認したいときに使います。

**裏で使われるもの（覚えなくてよい）**

貼った文に応じて Claude が選びます。名前を指定する必要はありません。

| Claude が使うもの | 何をするか | お金 |
|---|---|---|
| `/verify-integration` | データベース・API・予約処理を本物のDBで検証する | なし |
| `/verify-e2e` | 実際のブラウザで画面を操作して確かめる | なし |
| `/ui-polish` | 画面の見た目・スマホ幅・キーボード操作を確かめる | なし |
| `npm run check:providers` | AIへ送る形が正しいかをAI側に確認させる | ほぼ0円 |
| `npm run check:turnstile` | 人間確認がその環境で実際に動くか確かめる | なし |
| `npm run smoke:live` | AIを実際に1周させ、出来上がりまで確かめる | **約45円** |

**AI を実際に呼ぶ確認について**

AI の書き方や出し方をいじったときだけ必要です。上の文で「金額を教えて」と書いてあるので、勝手には実行されません。実行してよいと決めたら、こう伝えます。

```
AIを実際に呼ぶ確認も実行して、結果とかかった費用を教えてください。
```

- リクエストの形の間違いは AI 側がすぐ断るので、**その種類はほぼ無料で見つかります**。
- 自動で実行される条件と上限は決まっています（§14）。
- 「なぜ2種類あるのか」は §9 にあります。

## 5. 自分の目で確かめる

テストが全部通っても、**実際に触ってみないと分からないこと**があります。特に見た目・画像・グラフです。

**まず確認用アカウントを用意します**（1コマンド。何度実行しても同じ状態に戻ります）。

```bash
npm run seed:review
```

`review@example.com` / `Review-Local-Pw1` でログインできます。中身が入った状態
（下書き・スケジュール・投稿履歴と実績・フォロワー数の推移・通知）で作られるので、**空の画面ばかりを
見て「壊れている」と誤解せずに済みます**。ローカル以外には作りません（接続先が `127.0.0.1` でなければ止まります）。

- ブラウザで http://127.0.0.1:3000 を開き、変えた画面を実際に操作します。
- スマホ幅でも見てください（ブラウザの幅を狭める）。
- 画像やグラフが**ちゃんと表示されているか**を見ます。枠だけ出ていて中身が空、というのが起きます。

**Claude に頼むなら**

```
変えた画面をブラウザで開いて、パソコン幅とスマホ幅の両方で
表示を確認して、スクリーンショットを見せてください。
```

## 6. 不具合を見つけたとき

- **画面に出た文章をそのままコピーして貼ってください。** 要約しないでください。
- 何をしたら起きたかを書きます（どの画面で、何を押したか）。
- 原因の推測は要りません。原因が残る仕組みになっています（§13）。

```
週次まとめのパターンで下書きを作ったら
「生成結果を検証できませんでした。もう一度お試しください。」と出ました。
原因を特定して直してください。
```

直った後、こう聞いておくと同じことが起きにくくなります。

```
この不具合が、次からは私が手で試さなくても見つかる形にしてください。
```

## 7. インターネットに公開する

**順番が大事です。** 飛ばすと動かない状態で公開されます。

1. テスト用の環境（staging）に反映する。
2. 自動テストが全部通ったのを確認する。
3. **テスト用環境のデータベースを更新する。** これを忘れると X との連携が失敗します。
4. テスト用環境を実際に開いて動作を確認する。
5. 問題なければ本番へ出す申請（プルリクエスト）を作る。
6. 自動テストが緑になったら承認して反映する。

**1コマンドで足ります**（環境を作り終えたあと）。

```bash
npm run release:staging      # テスト用環境へ
npm run release:production   # 本番へ
```

上の1〜6を順に確認し、**どれか欠けていればそこで止まって理由と次の一手を出します**。データベースの更新が必要なときは `-- --apply` を付けて実行すると、更新まで行います。

すべて通ったあと、**公開先で実際に動くか**も続けて確認します。①人間であることの確認（費用なし）②AIで生成・画像・ニュースを1周（約45円）の2つです。**片方が失敗しても両方の結果を出してから終わります**（直すべきことをまとめて把握できるように）。

> ①が失敗すると**利用者はログインも新規登録もできません**。2026-08-01、テスト用環境で実際にこの状態でした（Cloudflare側でドメインを登録していなかった）。相手のサービス側の設定はコードに現れないため、テストが全部緑でも起こります。

**Claude に頼むなら**

```
npm run release:staging を実行して、止まったら理由と次にやることを教えてください。
```

- **自動テストが赤いときは、このコマンドが止めます。** ただしGitHub側の保護は現在のプランで使えないため、コマンドを使わず直接pushすれば通せてしまいます（作業リストのD-14で対応方法を決めます）。
- 公開の操作（push・プルリクエスト作成）は Claude が勝手にやりません。頼むか、自分で操作してください。
- 詳しい手順は [デプロイ手順](./deployment.md) にあります。

> **本番公開の前に決めることがあります。** 「自動テストが赤いときは本番に反映できない」ようにする方法（作業リストの D-14）。いまは人が確認する運用なので、**赤いまま反映してしまうことが技術的には可能**です。公開までに決めてください。

## 7.5 週に1回の点検

**変更していないのに壊れる部分**があります。外部のAIサービスやXの仕様は予告なく変わり、依存関係には新しい脆弱性が見つかり、データは溜まります。テストは「変更したとき」しか教えてくれません。

```
/maintenance
```

これで状態確認・外部APIの受理確認・実物1周・脆弱性・溜まったデータ・未pushを順に点検し、結果をまとめて報告します。**実費は約50円**（実物1周の分）。

月に1回はこちら。費用の実績・バックアップの復元テスト・外部APIの変更確認まで含みます。

```
/maintenance monthly
```

- 見つかった不具合はその場で直さず作業リストへ起票されます（点検と修理を混ぜると点検が終わらないため）。
- 週1回の自動実行にしたいときは `/loop /maintenance`（このセッション中）か `/schedule`（セッションを閉じても続く）。

## 8. うまくいかないとき

| 症状 | やること |
|---|---|
| ブラウザで開かない | `npm run dev` が動いているか確認する |
| ログインできない・データが出ない | `supabase start` を実行する（データの保存先が止まっている） |
| X との連携が失敗する | `localhost` ではなく `127.0.0.1` で開いているか確認する |
| テストが「skip」と出る | `supabase start` を実行してから `npm run test:db` を使う |
| 画像が表示されない | Claude に「ブラウザのコンソールにエラーが出ていないか見て」と頼む |
| 何が起きているか分からない | **`npm run doctor` を実行する**（下記） |

### まず `npm run doctor`

```bash
npm run doctor
```

いまの状態が日本語で一覧になり、**問題があれば「次にやること」が1行で出ます。** ログを読む必要はありません。

```
■ Space AI の状態（ローカル）

✅ データの保存先
    起動しています
✅ データ構造の更新
    すべて適用済みです
✅ アプリ
    応答しています（http://127.0.0.1:3000）
⚠️  お知らせメール
    送信待ちが 53 件（最も古いものは 129 時間前）
    → 本番で初めて動いたときに一斉送信されます。Claudeに「古いお知らせメールを掃除して」と伝えてください
✅ 今月かかった費用
    $14.41（約2162円） — anthropic $13.22 / x $1.19

すぐ困る問題はありませんが、注意が 2 件あります
```

（実際の出力を貼ったものです。最後の1行が全体のまとめで、`⚠️` は「いま困らないが放置しない方がよい」、`❌` は「対応が必要」を意味します）

- 見るもの: データの保存先・データ構造の更新・アプリ・**定時実行の生存**（5分間隔なので15分以上音沙汰が無ければ異常。止まると予約投稿・通知メール・日次サマリが静かに全部止まる・T-M8-51）・生成と投稿の成否・ニュース取得・**お知らせメールの滞留と送信失敗**（`failed`は❌。SMTP設定が誤っていて全滅している状態は「送信待ち0件」になるため、滞留だけを見ていると ✅ に見える・T-M8-40）・Xアカウントの期限・止まっている処理・**今月の費用**・**データベースの使用量**（無料枠の上限に近づくと警告。超えると同じ組織のプロジェクトが全部止まるため）
- デプロイ先も見られます: `npm run doctor -- --base https://<URL>`
- 読み取りだけなので**費用はかかりません**

それでも分からないときは、下の文をそのまま貼ってください。

```
npm run doctor の結果を見て、直せるものは直してください。
```

**自分でコマンドを打ちたいとき**

| やりたいこと | コマンド |
|---|---|
| テストする | `npm test` |
| 中身が入った確認用アカウントを作る | `npm run seed:review` |
| データベースのテストも確実に動かす | `npm run test:db` |
| 保存前にまとめて確認する | `npm run release:check` |
| いまの状態を確認する | `npm run doctor` |
| 人間確認が動くか確かめる | `npm run check:turnstile` |

全コマンドは [ローカル開発](./local-development.md) §4 にあります。

# 第2部　中身の説明

ここから先は、第1部の手順がなぜそうなっているかの説明です。開発を進めるだけなら読まなくて構いません。

## 9. テストは8層あり、それぞれ見えないものがある

要点は、**どの層も単独では不十分**で、層ごとに「原理的に見えないもの」があることです。だから第1部§4では、層を自分で選ばずClaudeに判断させる形にしています。

層8は 2026-08-01 に追加しました。staging で Turnstile の許可ドメインを登録しておらず**ログインも新規登録もできない**状態だったのに、層1〜7 のすべてが緑でした。**相手のサービス側の設定はコードに現れない**ため、どの層も原理的に見えません（T-M7-48）。

| # | 層 | コマンド | 守るもの | **見えないもの** |
|---|---|---|---|---|
| 1 | 型・lint | `npm run typecheck` / `npm run lint` | 型の整合、例外の握りつぶし禁止 | 実行時の振る舞い |
| 2 | 単体（125ファイル） | `npm test` | 純粋関数・モック注入での分岐と境界値 | **モックした境界の向こう側すべて** |
| 3 | DB統合（58ファイル `*.db.test.ts`） | `npm run test:db` | 実DBでの制約・RLS・**ロール権限**・route/actionの本番実装 | 外部API・ブラウザ描画 |
| 4 | E2E（13ファイル27件） | `npm run test:e2e` | 実ブラウザでの操作・遷移・CSP・署名URL・**実データの画像描画**（`naturalWidth > 0`）・**スマホ幅でページが横に伸びないこと** | AI生成の中身（費用と不確定性のため実行しない）。**外部サービスへの実セッション**（Stripeの決済ボタンは押さない） |
| 5 | provider契約 | `npm run check:providers` | **送っているリクエストが実APIに受理されるか** | 応答をアプリが扱えるか。**Googleは既定でskip**（`PROVIDER_CHECK_GOOGLE=1` で有効化・T-M7-17） |
| 6 | 実物スモーク | `npm run smoke:live -- --account <id>` | **応答をアプリが扱えて成果物が正しいか**（下書き・画像・news item） | 本番固有の環境差・**ブラウザ描画**（ブラウザを起動しない） |
| 7 | CI | push / PR で自動 | 1〜4 の実行そのものを強制 | 5・6（実キーが必要でCIへ置かない） |
| 8 | 外部サービス側の設定 | `npm run check:turnstile -- --base <URL>` | **相手側の設定（許可ドメイン等）がその環境で実際に通るか** | Turnstile以外（OAuth・SMTP・Stripeの設定は手動確認） |

内訳: `src` 配下のテストファイル184本 = 単体125 ＋ `*.db.test.ts` 58 ＋ provider契約 `*.live.test.ts` 1。`npm test` の結果は 1,298 passed / 6 skipped（skipは既定で無効な実APIテスト）。

### 層5と層6は別物（第1部§4で2種類あると書いた理由）

- 層5 = **受理されるか**。リクエストの形が正しいかだけを見る。
- 層6 = **扱えるか**。返ってきたものでアプリが正しい成果物を作れるかを見る。

受理されても後段で落ちる不具合があるので、片方では足りません。

## 10. 2026-07-28 に何が起きたか（この手順の理由）

**Web検索付きの投稿生成・画像生成・ニュース取得・画像プレビューの4系統が同時に壊れているのを、利用者が手で操作して初めて発見しました。** そのとき単体1,261件・E2E13件・CI はすべて緑でした。

原因の型が層ごとに違っていました。

| 不具合 | 実際の症状 | 検出できる層 |
|---|---|---|
| Web Search tool の `allowed_callers` 欠落 | API が 400 | 5（受理されない） |
| PT-IMG schema の `additionalProperties` 欠落 | API が 400 | 5（受理されない） |
| 検索の前置き文でJSON検証が落ちる／`<cite>`が本文へ混入 | API は 200。**アプリ側で落ちる** | **6のみ** |
| 応答が字数上限に触れて全件破棄され分野が常に0件 | API は 200。**黙って0件になる** | **6のみ** |
| 生成画像プレビューがCSPで表示されない | 画面が壊れるだけ。エラーなし | **4のみ**（実データを描画したとき）。2026-07-31に `e2e/draft-image.spec.ts` を追加して解消（CSPから許可originを外すと `naturalWidth=0` で落ちることを実測） |

見落とした理由は「テストが足りなかった」ことではなく、**検証手段をその場の判断で選んでいた**ことでした。だから触った層と必須検証の対応を `CLAUDE.md` の表に固定し、第1部§4ではそれをClaudeに引かせています。

第1部§5（自分の目で確かめる）を独立した手順にしているのは、この表の最後の行が理由です。画像が表示されない不具合は、テストが全部緑でも起き、**人が画面を見るまで誰も気付きませんでした**。

### 2026-07-31：層を足したら、その層でしか見えない不具合が実際に出てきた

不足していた層（層4の実データ描画・画面幅、層6の実物1周）を埋める作業そのものが、**未報告の不具合を2件見つけました**。どちらも利用者が踏む経路で、単体テストでは原理的に検出できません。

| 見つかったもの | 症状 | なぜ他の層では見えないか |
|---|---|---|
| パスワード再設定の人間確認が出ない（T-M7-33） | ログイン画面から**すぐに**リンクを押すと、確認ウィジェットが永久に描画されず申請できない。エラー表示も無い | `next/script` が同じidのスクリプトを読み込み中にunmountされると次のマウントで準備完了が通知されない。実ブラウザ以外では再現しない |
| プラン選択がスマホ幅で横スクロールする（T-M7-36） | 契約前に**最初に見る画面**が、390px幅でページごと183px横へ動く | レイアウトはブラウザでしか計算されない。しかも要素を1つずつ見ると全て画面内に収まっており、**ページ全体のはみ出し量**で測らないと分からない |

教訓は「テストを増やす」ではなく、**見えていない層を特定して埋めると、その層に溜まっていた不具合がまとめて出てくる**ことです。層を足したときは、実際に不具合が出るかどうかを検出力の確認（わざと壊して落ちるか見る）とセットで確かめてください。

## 11. テストを書くときの決まり

### 単体テスト（層2）

- 実装の詳細ではなく、公開される入出力・状態遷移・エラーを検証する。カバレッジ率をテスト品質の代わりにしない。
- 不具合修正では、**修正前に失敗する再現テストを先に**書く。
- **実際に観測した応答・エラー文字列をそのまま回帰テストにする。** 2026-07-28 の修正はいずれも実測値をテストへ固定した（`parse.test.ts` の前置き文2形、`gen-output.test.ts` の `<cite>` 実例、`news-research.test.ts` の字数と `published_at` 形式）。想像で書いたケースは同じ穴を防げない。

### DB統合テスト（層3・`*.db.test.ts`）

- **データベースと Supabase クライアントをモックしない。** モックすると層2と同じものを二重に検証するだけになる。
- **route / action の本番実装を通す。** 依存注入で純粋化した中核は層2で覆えるが、`route` が渡す本番実装（DBクエリ・外部呼び出しの配線）は無検証になりやすい。参考: `src/app/api/x/oauth/start/route.db.test.ts`（セッションだけをモックし、Supabaseクエリは実際に走らせる）。
- **静的 import のhoistingに注意。** `@/lib/env` は import 時に検証するため、`.env.local` を流し込む前に読まれると落ちる。route は `beforeAll` 内で `await import()` する。
- 作成データは一意IDで作り、**自分が作った分だけ**をFK順に削除する。他者データを上書きしない。**テストごとに作った利用者はそのテストの終わりで消す**（残すと `follower_snapshot` のように全アカウントを対象にする処理の件数・上限を食い、無関係なテストが落ちる）。
- **fan-out（全利用者へ配る処理）のテストは、後片付けを「行の所有者」ではなく「イベントのキー」で消す。** `fanOutNewsDigest` は条件が合う**全利用者**へ通知を作るため、テスト用ユーザーの分だけ消すと、共有ローカルDBの**開発者の実アカウントに未来窓の偽ダイジェストが残り続けた**（3,436件。通知を押すと常に0件のニュース画面になり、利用者が実際に踏んだ・T-M8-64）。`dedupe_key`（窓のキー）で消せば、誰に配られたかを知らなくても全部消せる。
- **skipを成功と数えない。** `npm run test:db`（`REQUIRE_DB=1`）はSupabase未起動ならテスト前に落ちる。
- **利用者に紐づかない共有テーブル**（`news_items` など）は利用者IDで隔離できない。時間窓で隔離し、窓は `src/lib/db/test-window.ts` の `uniqueTestHourWindow()` を使う。**過去の窓はどこを選んでも壊れる**（現在に近いと実データと混ざり、40日より古いと並列実行中の `schedule-cleanup` に消される）。未来の窓なら自分の行しか存在しない。
- **本文中の `await import()` は、そのモジュールのコンパイル時間がテストの制限時間に加算される。** env を後から流し込む都合で動的importを使う `*.db.test.ts` では、並列実行の負荷で既定の5秒を超えて「Test timed out」になる（2026-08-02、4〜5回に1回・実測）。**`beforeAll` で先に読み込む**（以降はキャッシュに当たる）。制限時間は「止まっている」ことの検出用で、「遅い」ことの検出用ではないため、20秒へ引き上げてある。
- **並列実行で落ちるテストは、テストの都合ではなく実装の欠陥のことがある。** 2026-08-02、`news-digest.db.test.ts` が4回に1回落ちたのを追ったところ、真因は「配信対象を選んでから通知を挿入するまでの間に利用者が退会すると外部キー違反で処理全体が止まる」という**本番の不具合**だった（T-M7-54）。「並列だから仕方ない」で緩めず、まず実装を疑う。
- **`insert ... select` で親行の存在を確かめても、外部キー違反は防げない。** SELECT が見る行と外部キー検査が見る行は**同じ文の中でも別のスナップショット**で決まるため、SELECT の直後に親行の削除がコミットされると違反になる。上のT-M7-54を直した後も3回に1回落ち続け、2026-08-03に `for key share of <親テーブル>` を足して止まった（T-M8-19）。親行を先にロックすると、削除はこの文の完了まで待たされ、先に消えていれば0行になる。
- **競合の再現は並列実行の運任せにしない。** 別接続でトランザクションを開いたまま削除し、`pg_stat_activity` の `wait_event_type = 'Lock'` で**相手がロック待ちに入ったこと**を確認してから commit すると、順序が固定できて毎回再現する。ロック待ちを確認せずに commit すると競合が起きず、修正前のコードでも通る「再現しないテスト」になる。参考: `src/lib/jobs/news-digest.db.test.ts` の T-M8-19。

### E2E（層4）

- **生成物は実データで描画する。** 画像・グラフ・ニュースカード・分析表を表示する画面は、本物のデータを載せて実際に描画するところまで見る。要素の存在ではなく**読み込めたこと**（画像なら `naturalWidth > 0`）を確認する。
- **スマホ幅（390px）で横に伸びないことを見る。** 要素を1つずつ見ても気づけないので、`horizontalOverflow(page)`（ページ全体のはみ出しpx）で判定する。主要画面は `e2e/mobile-layout.spec.ts` がまとめて見張る。
- **外部サービスへ実際のセッションを作るボタンは押さない。** Stripeの決済・管理ボタンは遷移先と表示だけを見る（CIはダミーキーなので必ず失敗する）。ボタンの先の配線は層3が担当する。
- **「生成する」を押すE2Eは書かない（＝毎回課金される）。** Server Action が job を作ると `after()` が worker へ渡して**本物のAIを呼ぶ**（1回約$0.13）。`release:check` はE2Eを含むので、保存前チェックのたびに課金される。2026-08-03、テーマの配線を確かめるために押すテストを書いてしまい、**全体実行を10回ほど回した分（約$0.7）が課金されていた**（`external_api_usage_events` の時間別集計で気付いた）。押す必要があるものは `E2E_LIVE_AI=1` で明示的に有効化したときだけ走らせる（`check:providers` と同じ形）。jobの状態を見たいだけなら `seedRunningJob` のように**DBへ直接置く**。
- **E2E全体が課金しないことを数字で確かめられる**: 実行の前後で `select sum(estimated_cost_usd) from external_api_usage_events` を比べ、差が0であること。
- **「生成する」ボタンは押さない。** 実AI呼び出しは費用・不確定性・1分待ちをE2Eへ持ち込む。job の状態は `generation_jobs` を直接seedして表示だけを検証し、生成そのものは層6に任せる。
- `getByRole("alert")` は使わない。Next.js の route announcer も `role="alert"` を持つため必ず2要素に当たる。`alertIn(page)`（`e2e/fixtures/test.ts`）を使う。
- job はローカルで自動進行しない。worker（`/api/jobs/run`）や該当cron routeを明示的に叩き、完了は**期限付きで**pollする。
- 安全ゲート `e2e/fixtures/guard.ts` が `APP_ENV=development`・`X_POSTING_MODE=dry_run`・ローカルSupabase・ローカルbaseURLを起動前に検査する。外れたら1件も実行しない。
- retry は 0。flakyを無条件retryで隠すと「動いているつもり」になる。
- **サンドボックス内では1件も動かない。** ブラウザが起動できず、全件が `bootstrap_check_in ... Permission denied (1100)` で落ちる（Chromiumのフラグが数十行出るのでアプリが壊れたように見えるが、**ブラウザが立ち上がっていないだけ**）。エージェントから実行するときはサンドボックスを外す。
- **ネイティブモジュール（`sharp` 等）を入れ替えたら dev サーバーを再起動する。** 動いたままだと古いバイナリを掴み続け、画像生成が `job_failed`（理由なし）で落ちる。2026-08-01、sharpを0.35へ上げた直後にこれで15分溶かした。
- **`npm run ... | tail` で結果を判断しない。** 終了コードが `tail` のものになり、**全件失敗でも成功に見える**（2026-07-31 に実際に誤読した）。件数の行（`27 passed` / `27 failed`）を必ず確認する。

### provider契約テスト（層5）

- **本番のファクトリとschemaをそのまま使う。** テスト側で「正しいペイロード」を書くと、検証しているのが本番の形でなくなる。2026-07-27、テスト側の最小schemaがたまたま正しかったためにPT-IMGのschema不備を見逃した。

## 12. このリポジトリ固有の落とし穴

### データベースへの2経路が非対称

アプリは2つの経路でデータベースへ触ります。

| 経路 | 接続ロール | 権限（GRANT）の影響 |
|---|---|---|
| 直結pg（`DATABASE_URL`） | `postgres`（superuser） | **回避してしまう** |
| Supabaseクライアント（PostgREST） | `service_role` | **受ける** |

そのため**直結pgのテストだけが緑で、PostgREST経由の経路だけが `42501 permission denied` で落ちます**。2026-07-26、`service_role` に18テーブル中17テーブルの権限が無く、X連携が `internal_error` になりました。テーブルを追加したら `service-role-grants.db.test.ts` が既定権限（`alter default privileges`）まで見ます。

### 例外を握りつぶすと原因が消える

`catch {}` は eslint で禁止しています（`src/app/actions/**`・`src/app/api/**`・`src/lib/**`）。未知の失敗は共通の出口で `recordUnexpectedError` が記録します。

`onRequestError`（`src/instrumentation.ts`）は **throw された**例外しか Sentry へ送りません。共通の出口は catch して値を返すので、そこは自分で記録しないと何も残りません。

### 「正常な空」と「失敗による空」を必ず別の値で表す

2026-07-28 の不具合の多くは**成功として記録される失敗**でした。

- 修復callが `{"items":[]}` を返す → 「該当ニュースなし」と区別できない
- 除外4件を `console.warn` にだけ出す → 記録に残らない
- CSPブロック → 画像が出ないだけでエラーなし

`researchNews` は `dropped` と `dropReasons` を返し、スモークは「0件かつ除外あり＝全滅」を失敗、「0件で除外も0＝該当なし」を成功として区別します。分野ごとの結果は `news_fetch_outcomes` へ残し、cronの応答と `npm run doctor` の両方で運営者が区別できます（T-M7-40）。さらに**1日1通のまとめ**（画面通知＋メール）が「分野が3日連続で0件」のような**日をまたぐ劣化**を届けます（T-M7-29）。**新しい処理を書くときも、空になった理由を呼び出し側が説明できる形にしてください。**

### 任意項目のために本体を捨てない

`published_at` は任意項目なのに厳密なISO 8601を要求していたため、**日付だけ（`2026-07-28`）で書かれた記事5件すべてを失っていました**。任意のメタデータは正規化して、駄目ならそのフィールドだけ落とします。

### プロンプトで頼んだことは守られない前提で組む

「JSONのみ」と指示してもWeb検索併用時は前置き文が付きます。「120字以内」と書いても超えます。**出力形式は指示ではなく仕組みで保証する**（プロンプト設計書 §2 原則5）。抽出を寛容にする・正規化する・item単位で選別する、のいずれかで吸収します。

### 利用者どうしの分離は2つに分けて考える

| 分離したいもの | どこで守るか | どこで検証するか |
|---|---|---|
| **他人のデータを読み書きできない** | RLS（全public表で有効）＋`authenticated`に書き込みGRANTを与えない＋所有権チェック | `src/lib/db/rls.db.test.ts`（8件。**全テーブルにRLSがあるかを構造的に検査**するので、表を足したら落ちる） |
| **片方の挙動がもう片方を止めない** | 上限を利用者ごとに持つ（生成枠・同時実行5件・X日次上限）／失敗を分野・利用者単位で閉じる／選択順序を時刻順にする | `src/lib/ops/tenant-isolation.db.test.ts`（7件）＋`e2e/tenant-isolation.spec.ts`（画面に他人のものが出ないこと） |

**共有している上限には注意**が必要。`scheduler_tick`のdispatchは1起動50件、`follower_snapshot`は100アカウント、`metrics_collector`は50アカウント/500件で、これらは**全利用者で共有**する。順序が時刻順なので永久に後回しにはならないが、片方が大量投入すると**もう片方は次の起動まで遅れる**（tickは5分間隔）。この「遅れるが飢餓しない」ことをテストで固定している。

### 横スクロールする表の外側には `relative` を付ける

`overflow-x-auto` の中に `sr-only`（`position: absolute`）があると、**位置指定された先祖が無い限りクリップされずページ自体を横に伸ばします**（包含ブロックが初期包含ブロックになるため）。2026-07-31、`/plans` の比較表がこれでスマホ幅のページを183px横スクロールさせていました。要素を1つずつ見ると全て画面内に収まって見えるため、**ページ全体のはみ出し量**で判定します。

### production 以外から外向きの副作用を出さない

X投稿は `X_POSTING_MODE`、通知メールは `canSendViaSmtp`（production以外はループバック宛のみ）で止めています。2026-07-27、SMTPにガードが無く、動作確認で実際に98通送信しました。

**新しい外向きチャネルは「気付く仕組み」で守ります。** `src/lib/ops/outbound-channels.ts` が外へ出るファイルの一覧で、`outbound-channels.test.ts` が**一覧に無いファイルが外向き呼び出し（`fetch`・nodemailer・AI SDK・Stripe SDK・Storage削除）を持ったら落ちます**。外部へ出る処理を足したら一覧へ追記してガードを書いてください（T-M7-28）。

## 13. 落ちたときに原因はどこに残るか

第1部§6で「原因の推測は要らない」と書いた根拠です。

| 探す場所 | 何が分かるか |
|---|---|
| `generation_jobs.error` | 利用者向けメッセージ＋`provider_raw_error`（**providerの生の応答**）。画像schemaの400はここだけで特定できた |
| dev サーバーの標準エラー出力 `[unexpected] <at>` | 共通の出口で丸められた未知の例外の生スタック。Web検索の400はここで判明した |
| Sentry | production/preview の未知例外（DSN設定時）。`beforeSend` で秘密値と prompt 内容を除去する |
| `test-results/` | E2E失敗時の trace・screenshot（`retain-on-failure`／`only-on-failure`。CIでは失敗時のみ7日保存。html reporterは未設定なので `playwright-report/` は生成されない） |
| `cron_runs` | cron の受付履歴（時間窓claim。二重起動の抑止） |

**ログには秘密値を出さない。** `console.error` は redact を通らないため、生のエラーを出す箇所では何が含まれ得るかを意識してください。
