# 第1部　やること

## 1. 開発を始める

- ターミナルで2つ起動する。

  ```bash
  supabase start    # ローカルのデータベース
  npm run dev       # アプリ（http://127.0.0.1:3000 で開く）
  ```

- ブラウザは必ず `127.0.0.1` で開く。`localhost` では X 連携が動かない。
- 初回だけ環境構築が必要。手順は [ローカル開発](./local-development.md) を見る。
- 何を作るかは自分で決めず、`tasks/BACKLOG.md` の順番に従う。

**Claude への頼み方**

```
/dev-loop
```

これだけで「次のタスクを選ぶ → 実装 → テスト → ドキュメント更新 → コミット」まで1周します。タスクを指定したいときは `/dev-loop T-M7-28` のようにIDを付けます。

```
/loop /dev-loop
```

止めるまで連続で開発を回します。

---

## 2. 変更したら何をテストするか

**ここが一番大事です。** 変更した場所によって、やるべき検証が決まっています。自分で選ばず、下の表から引いてください。

| 変更したもの | Claude への頼み方 |
|---|---|
| 画面・見た目・コンポーネント | `/ui-polish 投稿画面に画像プレビューを追加した` |
| データベース・migration・権限 | `/verify-integration 下書きテーブルに列を追加した` |
| Server Action・API route | `/verify-integration ` ＋ **「本番の実装を通すテストも書いて」** |
| AI のプロンプト・出力の形・provider の設定 | **「実APIでの検証（check:providers と smoke:live）も実行して。かかった費用も教えて」** |
| ログイン・投稿・予約など利用者の主要な操作 | `/verify-e2e 下書きから投稿までの流れ` |
| 上記以外 | `npm run release:check` を実行してもらう |

- **複数に当てはまるときは全部やる。** 1つ選んで済ませない。
- Claude が検証を省いたときは、省いた理由を必ず聞く。

**そのまま使える頼み方**

```
CLAUDE.md の「変更影響 → 必須の検証」の表に従って、
該当する検証を全部実行してください。
実行しなかった行があれば、その理由も教えてください。
```

```
テストが緑でも、外部APIやブラウザはモックされていて未検証です。
その前提で、何が確認できていて何が確認できていないかを分けて報告してください。
```

## 3. 不具合を見つけたとき

- 画面に出たメッセージを**そのまま**伝える。要約しない。
- 何をしたら起きたかを書く（どの画面で・どのボタンを押したか）。
- 「たぶん〇〇が原因」と推測を添えなくてよい。原因の記録は残る仕組みになっている（§11）。

**Claude への頼み方**

```
週次まとめのパターンで下書きを作ったら
「生成結果を検証できませんでした。もう一度お試しください。」と出ました。
原因を特定して直してください。
```

```
この不具合が、次からは私が手で試さなくても見つかる形にしてください。
```

## 4. 自分でコマンドを打つとき

| やりたいこと | コマンド |
|---|---|
| ふつうにテストする | `npm test` |
| データベースのテストも確実に動かす | `npm run test:db` |
| ブラウザで通しで動かす | `npm run test:e2e` |
| コミット前に一式チェックする | `npm run release:check` |
| ローカルのテストデータを掃除する | `npm run db:clean-test-data`（消す前に内容が出る。実行は `-- --apply`） |

- テストの数だけでなく、**skip（実行されなかった件数）も見る。** `npm test` はデータベースが起動していないと58ファイル分を黙って飛ばします。`npm run test:db` なら飛ばさずに落ちます。
- 全コマンドの一覧は [ローカル開発](./local-development.md) §4 にあります。

## 5. お金がかかる検証

AI に実際にリクエストを送る検証が2つあります。**実行するとお金がかかります。**

| コマンド | 何を確かめるか | 費用の目安 |
|---|---|---|
| `npm run check:providers` | 送っているリクエストが AI 側に受け付けられるか | 数円 |
| `npm run smoke:live -- --account <XアカウントのUUID>` | 返ってきた結果でアプリがちゃんと下書き・画像・ニュースを作れるか | **1回 約45円**（$0.30）・40〜90秒 |

- **AI のプロンプトや出力の形をいじったら、必ず両方やる。** どちらか片方では足りません（理由は §7）。
- `npm run smoke:live` を引数なしで実行するとニュースだけを確認します。生成と画像も見たいときは `--account` を付けてください。
- アプリ（`npm run dev`）が起動している必要があります。
- リクエストの形が間違っている場合は AI 側が即座に拒否するため、**その種類の不具合はほぼ無料で見つかります**（実測: 3件の失敗を10秒・$0.011で検出）。

**Claude への頼み方**

```
npm run smoke:live -- --account <UUID> を実行して、
失敗したシナリオがあれば原因を特定して直してください。
かかった費用も報告してください。
```

## 6. デプロイするとき

1. `stg` ブランチに push する。CI（GitHub Actions）が自動で全部テストする。
2. CI が緑になったのを確認する。
3. **staging のデータベースに migration を適用する**（`supabase db push`）。これを忘れると X 連携が失敗します。
4. staging を実際に開いて動作を確認する（手順は [デプロイ手順](./deployment.md) §5）。
5. 問題なければ `main` を `stg` に合わせて push する。本番が更新されます。

- **CI が赤でも本番デプロイは止まりません。** `main` に push した瞬間に本番のビルドが始まります。順番を守ってください。
- staging でしか分からない問題があります（環境変数の抜け、migration 未適用）。`npm run smoke:live -- --base <stagingのURL> --account <UUID>` で確認できます。
- ただし**見た目の崩れは実際にブラウザで開かないと分かりません。** スモークはブラウザを使いません。

**Claude への頼み方**

```
stg へ push して、CI の結果を確認してください。
```

```
staging へデプロイしたので、デプロイ手順 §5 の検証を実行して結果を教えてください。
```

> push は外向きの操作なので、Claude は勝手に実行しません。自分で `! git push` を打つか、明示的に依頼してください。

# 第2部　なぜそうするのか

ここから先は、第1部の手順の理由です。

## 7. テストは7層あり、それぞれ見えないものがある

この構成の要点は、**どの層も単独では不十分**で、層ごとに「原理的に見えないもの」があることです。だから第1部のように「変更した場所から層を引く」形にしています。

| # | 層 | コマンド | 守るもの | **見えないもの** |
|---|---|---|---|---|
| 1 | 型・lint | `npm run typecheck` / `npm run lint` | 型の整合、例外の握りつぶし禁止 | 実行時の振る舞い |
| 2 | 単体（124ファイル） | `npm test` | 純粋関数・モック注入での分岐と境界値 | **モックした境界の向こう側すべて** |
| 3 | DB統合（58ファイル `*.db.test.ts`） | `npm run test:db` | 実DBでの制約・RLS・**ロール権限**・route/actionの本番実装 | 外部API・ブラウザ描画 |
| 4 | E2E（8ファイル14件） | `npm run test:e2e` | 実ブラウザでの操作・遷移・CSP・署名URL・描画（**画像とグラフの描画は現状のspecでは未カバー** → T-M7-26） | AI生成の中身（費用と不確定性のため実行しない） |
| 5 | provider契約 | `npm run check:providers` | **送っているリクエストが実APIに受理されるか** | 応答をアプリが扱えるか。**Googleは既定でskip**（`PROVIDER_CHECK_GOOGLE=1` で有効化・T-M7-17） |
| 6 | 実物スモーク | `npm run smoke:live -- --account <id>` | **応答をアプリが扱えて成果物が正しいか**（下書き・画像・news item） | 本番固有の環境差・**ブラウザ描画**（ブラウザを起動しない） |
| 7 | CI | push / PR で自動 | 1〜4 の実行そのものを強制 | 5・6（実キーが必要でCIへ置かない） |

内訳: `src` 配下のテストファイル183本 = 単体124 ＋ `*.db.test.ts` 58 ＋ provider契約 `*.live.test.ts` 1。`npm test` の結果は 1,277 passed / 6 skipped（skipは既定で無効な実APIテスト）。

### 層5と層6は別物

- 層5 = **受理されるか**。リクエストの形が正しいかだけを見る。
- 層6 = **扱えるか**。返ってきたものでアプリが正しい成果物を作れるかを見る。

受理されても後段で落ちる不具合があるので、片方では足りません。

## 8. 2026-07-28 に何が起きたか（この手順の理由）

**Web検索付きの投稿生成・画像生成・ニュース取得・画像プレビューの4系統が同時に壊れているのを、利用者が手で操作して初めて発見しました。** そのとき単体1,261件・E2E13件・CI はすべて緑でした。

原因の型が層ごとに違っていました。

| 不具合 | 実際の症状 | 検出できる層 |
|---|---|---|
| Web Search tool の `allowed_callers` 欠落 | API が 400 | 5（受理されない） |
| PT-IMG schema の `additionalProperties` 欠落 | API が 400 | 5（受理されない） |
| 検索の前置き文でJSON検証が落ちる／`<cite>`が本文へ混入 | API は 200。**アプリ側で落ちる** | **6のみ** |
| 応答が字数上限に触れて全件破棄され分野が常に0件 | API は 200。**黙って0件になる** | **6のみ** |
| 生成画像プレビューがCSPで表示されない | 画面が壊れるだけ。エラーなし | **4のみ**（実データを描画したとき）。ただし**現状のspecは画像を描画しておらず、この回帰は層2の `security-headers.test.ts` でしか押さえていない**（T-M7-26で解消する） |

見落とした理由は「テストが足りなかった」ことではなく、**検証手段をその場の判断で選んでいた**ことでした。だから第1部§2を対応表にしてあります。

## 9. テストを書くときの決まり

### 単体テスト（層2）

- 実装の詳細ではなく、公開される入出力・状態遷移・エラーを検証する。カバレッジ率をテスト品質の代わりにしない。
- 不具合修正では、**修正前に失敗する再現テストを先に**書く。
- **実際に観測した応答・エラー文字列をそのまま回帰テストにする。** 2026-07-28 の修正はいずれも実測値をテストへ固定した（`parse.test.ts` の前置き文2形、`gen-output.test.ts` の `<cite>` 実例、`news-research.test.ts` の字数と `published_at` 形式）。想像で書いたケースは同じ穴を防げない。

### DB統合テスト（層3・`*.db.test.ts`）

- **データベースと Supabase クライアントをモックしない。** モックすると層2と同じものを二重に検証するだけになる。
- **route / action の本番実装を通す。** 依存注入で純粋化した中核は層2で覆えるが、`route` が渡す本番実装（DBクエリ・外部呼び出しの配線）は無検証になりやすい。参考: `src/app/api/x/oauth/start/route.db.test.ts`（セッションだけをモックし、Supabaseクエリは実際に走らせる）。
- **静的 import のhoistingに注意。** `@/lib/env` は import 時に検証するため、`.env.local` を流し込む前に読まれると落ちる。route は `beforeAll` 内で `await import()` する。
- 作成データは一意IDで作り、**自分が作った分だけ**をFK順に削除する。他者データを上書きしない。
- **skipを成功と数えない。** `npm run test:db`（`REQUIRE_DB=1`）はSupabase未起動ならテスト前に落ちる。

### E2E（層4）

- **生成物は実データで描画する。** 画像・グラフ・ニュースカード・分析表を表示する画面は、本物のデータを載せて実際に描画するところまで見る。要素の存在ではなく**読み込めたこと**（画像なら `naturalWidth > 0`）を確認する。
- **「生成する」ボタンは押さない。** 実AI呼び出しは費用・不確定性・1分待ちをE2Eへ持ち込む。job の状態は `generation_jobs` を直接seedして表示だけを検証し、生成そのものは層6に任せる。
- `getByRole("alert")` は使わない。Next.js の route announcer も `role="alert"` を持つため必ず2要素に当たる。`alertIn(page)`（`e2e/fixtures/test.ts`）を使う。
- job はローカルで自動進行しない。worker（`/api/jobs/run`）や該当cron routeを明示的に叩き、完了は**期限付きで**pollする。
- 安全ゲート `e2e/fixtures/guard.ts` が `APP_ENV=development`・`X_POSTING_MODE=dry_run`・ローカルSupabase・ローカルbaseURLを起動前に検査する。外れたら1件も実行しない。
- retry は 0。flakyを無条件retryで隠すと「動いているつもり」になる。

### provider契約テスト（層5）

- **本番のファクトリとschemaをそのまま使う。** テスト側で「正しいペイロード」を書くと、検証しているのが本番の形でなくなる。2026-07-27、テスト側の最小schemaがたまたま正しかったためにPT-IMGのschema不備を見逃した。
- 構造化出力を使う実行を追加したら `PRODUCTION_SCHEMAS`（`provider-contract.live.test.ts`）へ登録する。
- **Googleは既定で検査しない**（運営キーのquota枯渇と画像404のため。T-M7-17）。Geminiアダプタを触ったら `PROVIDER_CHECK_GOOGLE=1 npm run check:providers` で有効化する。忘れると何も検査されないまま緑になる。

### 実物スモーク（層6）

- 判定は `src/lib/smoke/scenarios.ts` の1か所に集約する。ローカル（`npm run smoke:live`）とデプロイ先（`GET /api/cron/canary`）が**同じ判定**を使うため。
- 作成した job・draft はシナリオ側で必ず削除する。
- `/api/cron/canary` は **cron へ登録していない**（手動起動のみ。D-11で2026-07-28に決定）。定期実行へ切り替えるなら `vercel.json` に `crons` を追加する。

### スナップショット

`gen-prompts.test.ts` のスナップショットは**プロンプト設計書とのドリフト検知**。落ちたら「更新して通す」のではなく、正本（`docs/プロンプト設計書.md`）とコードの両方を更新したかを先に確認する。

## 10. このリポジトリ固有の落とし穴

### データベースへの2経路が非対称

アプリは2つの経路でデータベースへ触ります。

| 経路 | 接続ロール | 権限（GRANT）の影響 |
|---|---|---|
| 直結pg（`DATABASE_URL`） | `postgres`（superuser） | **回避してしまう** |
| Supabaseクライアント（PostgREST） | `service_role` | **受ける** |

そのため**直結pgのテストだけが緑で、PostgREST経由の経路だけが `42501 permission denied` で落ちます**。2026-07-26、`service_role` に18テーブル中17テーブルの権限が無く、X連携が `internal_error` になりました。テーブルを追加したら `service-role-grants.db.test.ts` が既定権限（`alter default privileges`）まで見ます。

### 例外を握りつぶすと原因が消える

`catch {}` は eslint で禁止しています（`src/app/actions/**`・`src/app/api/**`・`src/lib/**`）。未知の失敗は共通の出口で `recordUnexpectedError` が記録します。

`onRequestError`（`src/instrumentation.ts`）は **throw された**例外しか Sentry へ送りません。共通の出口は catch して値を返すので、そこは自分で記録しないと何も残りません。

### 「正常な空」と「失敗による空」を必ず別の値で表す

2026-07-28 の不具合の多くは**成功として記録される失敗**でした。

- 修復callが `{"items":[]}` を返す → 「該当ニュースなし」と区別できない
- 除外4件を `console.warn` にだけ出す → 記録に残らない
- CSPブロック → 画像が出ないだけでエラーなし

`researchNews` は `dropped` と `dropReasons` を返し、スモークは「0件かつ除外あり＝全滅」を失敗、「0件で除外も0＝該当なし」を成功として区別します。**新しい処理を書くときも、空になった理由を呼び出し側が説明できる形にしてください。**

### 任意項目のために本体を捨てない

`published_at` は任意項目なのに厳密なISO 8601を要求していたため、**日付だけ（`2026-07-28`）で書かれた記事5件すべてを失っていました**。任意のメタデータは正規化して、駄目ならそのフィールドだけ落とします。

### プロンプトで頼んだことは守られない前提で組む

「JSONのみ」と指示してもWeb検索併用時は前置き文が付きます。「120字以内」と書いても超えます。**出力形式は指示ではなく仕組みで保証する**（プロンプト設計書 §2 原則5）。抽出を寛容にする・正規化する・item単位で選別する、のいずれかで吸収します。

### production 以外から外向きの副作用を出さない

X投稿は `X_POSTING_MODE`、通知メールは `canSendViaSmtp`（production以外はループバック宛のみ）で止めています。**新しい外向きチャネルを足したら同じガードを付けてください。** 2026-07-27、SMTPにガードが無く、動作確認で実際に98通送信しました。

## 11. 落ちたときに原因はどこに残るか

| 探す場所 | 何が分かるか |
|---|---|
| `generation_jobs.error` | 利用者向けメッセージ＋`provider_raw_error`（**providerの生の応答**）。画像schemaの400はここだけで特定できた |
| dev サーバーの標準エラー出力 `[unexpected] <at>` | 共通の出口で丸められた未知の例外の生スタック。Web検索の400はここで判明した |
| Sentry | production/preview の未知例外（DSN設定時）。`beforeSend` で秘密値と prompt 内容を除去する |
| `test-results/` | E2E失敗時の trace・screenshot（`retain-on-failure`／`only-on-failure`。CIでは失敗時のみ7日保存。html reporterは未設定なので `playwright-report/` は生成されない） |
| `cron_runs` | cron の受付履歴（時間窓claim。二重起動の抑止） |

**ログには秘密値を出さない。** `console.error` は redact を通らないため、生のエラーを出す箇所では何が含まれ得るかを意識してください。

## 12. 費用と決まっていること

実APIを叩く層の実測値（2026-07-28）:

| 対象 | 実測 |
|---|---|
| 生成 P-6（Web検索あり） | $0.09〜0.16 |
| 生成 P-2（検索なし） | $0.011〜0.015 |
| 画像1枚（`gpt-image-1-mini`） | $0.003〜0.008 |
