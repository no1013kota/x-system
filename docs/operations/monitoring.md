# 運用メモ: 動いているかの見張り方

| 項目 | 内容 |
|---|---|
| バージョン | v1.0 |
| 更新日 | 2026-08-22 |
| 関連 | [開発とテストの進め方](./development-and-testing.md)／[デプロイ手順](./deployment.md)／要件01 §2・§8／要件04 §14 |

運営者が「いま何が壊れているか」を知る経路と、それぞれが**何を見て何を見ないか**をまとめる。

## 1. 経路は3つ。役割が違う

| 経路 | いつ | 何が分かるか | 運営者の操作 |
|---|---|---|---|
| **毎朝の運営者メール**（T-M8-164） | 毎日8:00 JST以降の最初の `scheduler_tick`。**異常があった日だけ**届く | 下の §2 の全項目のうち `error`／`warn` のもの＋直し方 | **不要**（届くのを待つ） |
| **`npm run doctor`** | 打ったときだけ。**定期実行されない** | §2 の全項目を、正常も含めて一覧 | コマンドを打つ |
| **Sentry** | 例外が起きた瞬間に自動送信 | §3 の「過去に起きた例外」とスタックトレース | アラートメールを設定しておく |

**doctorとSentryは重ならない。** doctorは「**いまの状態**」（設定が正しいか・止まっていないか）、
Sentryは「**過去に起きた例外**」。2026-08-19のAIクレジット切れは前者、
「特定の利用者の操作だけ落ちる」は後者でしか見つからない。

**`doctor` はVercelの定時実行には入っていない**（`vercel.json` の cron は
`news-fetch`／`scheduler_tick`／`metrics-collector`／`follower-snapshot` の4本）。
毎朝のメールは `scheduler_tick` に相乗りしており、**doctor用の定時実行は増やしていない**（原則3）。

**環境ごとの届き方**: 毎朝のメールが届くのは**Vercel Cronが動く環境（本番）だけ**。
stagingは別プロジェクトとして本番デプロイになっていれば届く。ローカルは定時実行が無く、
非productionから外部SMTPへ送らないガードもあるため届かない（要決定D-29＝手動起動）。
ローカルとstagingは `npm run doctor -- --base <URL>` で見る。件名に環境名が入る。

## 2. doctorの検査項目

**この表はコードと機械的に突き合わせている**（`src/lib/ops/doctor-doc-sync.test.ts`）。
項目を増やしても表を直さなければテストが落ちる——手で数え上げた一覧は必ず古くなる（ADR-0005／T-M8-87の教訓）。
判定の正本は `src/lib/ops/diagnostics.ts`。

### デプロイ先の状態（`/api/cron/doctor` が返す。毎朝のメールもこれ）

| 検査項目 | 見ているもの |
|---|---|
| Xへの投稿 | `X_POSTING_MODE`。本番で `dry_run` のままなら投稿が1件も出ない（T-M8-147） |
| アプリのURL設定 | `APP_BASE_URL` と実際の配信元の一致。ずれるとメールのリンクとX連携の戻り先が別ドメインを指す |
| 決済（Stripe）の接続先 | 鍵が `live` か `test` か |
| エラーの記録（Sentry） | DSNの種別（未設定／仮の値／有効）と受け先ホスト。**未設定でも画面は正常に見える**（T-M8-162） |
| 生成・投稿の動作 | 直近24時間の成功／失敗件数 |
| 定時実行 | `scheduler_tick` が最後に動いた時刻 |
| ニュースの取得 | 直近48時間の取得件数と、分野ごとの失敗理由（**AIの残高不足などを直せる言葉で出す**・T-M8-163） |
| Xアカウントの連携 | 連携済みアカウントの有無と状態 |
| メール確認が終わっていない登録 | 確認途中で止まっている登録 |
| 止まっている処理 | `running` のまま滞留しているジョブ |
| 今月かかった費用 | 外部APIの当月実績（原則4「費用が見える」） |
| データベースの使用量 | Supabase無料枠に対する使用量 |
| 人間確認（ボット対策） | Supabase側のCAPTCHA有効・Turnstileの設定 |
| プラン管理（Stripe） | Customer Portalでプラン変更・解約ができる設定か |
| 請求額と表示額の一致（Stripe） | 画面の金額とStripeのPriceが一致しているか |
| 決済の受付（Stripeアカウント） | アカウントが本番決済を受け付けられるか。**アプリからは見えない**（T-M8-148） |
| ブログ記事の同梱 | `blog/published/*.md` がデプロイに含まれているか（`outputFileTracingIncludes` 漏れは**本番だけ「準備中」になる**）と、front matter の不備で公開されていない記事（T-M8-184） |

### ローカル実行時だけの追加項目（`scripts/doctor.mjs` が足す）

| 検査項目 | 見ているもの |
|---|---|
| データの保存先 | ローカルSupabaseが起動しているか |
| データ構造の更新 | migrationが適用済みか |
| 溜まったテストデータ | テスト・E2E由来のデータの滞留（T-M8-161の原因） |
| 確認メールの行き先（ローカル） | 確認メールがMailpit等のループバックへ向いているか |
| アプリ／データの状態 | アプリが応答するか、`/api/cron/doctor` へ到達できるか |

## 3. Sentryに入るもの・入らないもの

**列挙はしない**（送信箇所は増減するので、写した一覧は必ず古くなる）。方針だけを正本とする。

- **入る**: アプリが想定していない例外。Server Actions全般（`_helpers.ts` の共通catch）、認証（登録・
  6桁コード確認・再送・パスワード再設定）、Stripe webhook、定時実行、認証proxyのprofile取得失敗（T-M8-159）。
  実際の送信箇所は `recordUnexpectedError` / `captureServerException` の呼び出し元を見る。
- **入らない**: 秘密値・投稿前の入力内容（`redactEvent` が除去）。想定内の失敗（入力検証エラーなど）。
  **AIの残高不足のような「設定・外部要因の異常」も入らない**——例外ではなく状態なので、doctor側が担う。
- **保持期間は90日**（現行プランで固定・短縮不可。要決定D-19）。データ保存先はEU（ドイツ）リージョン。

## 4. 切れる前に気付けないもの

**AIの残高（クレジット）は事前警告を作れない。** 提供元が残高を読むAPIを公開していないため、
アプリ側からは「使おうとして失敗した」時点でしか分からない。
**切れる前に気付く唯一の手段は提供元側の設定**（Anthropic / OpenAI の自動チャージと残高アラート）で、
これは運営者の作業。doctorと毎朝のメールは「切れた後に確実に届く」ところまでを担う。
