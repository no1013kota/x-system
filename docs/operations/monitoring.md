運営者が「いま何が壊れているか」を知る経路と、それぞれが**何を見て何を見ないか**をまとめる。

## 1. 経路は3つ。役割が違う

| 経路 | いつ | 何が分かるか | 運営者の操作 |
|---|---|---|---|
| **毎朝の運営者メール**（T-M8-164） | 毎日8:00 JST以降の最初の `scheduler_tick`。**異常があった日だけ**届く | 下の §2 の全項目のうち `error`／`warn` のもの＋直し方 | **不要**（届くのを待つ） |
| **`npm run doctor`** | 打ったときだけ。**定期実行されない** | §2 の全項目を、正常も含めて一覧 | コマンドを打つ |
| **Sentry** | 例外が起きた瞬間に自動送信 | §3 の「過去に起きた例外」とスタックトレース | アラートメールを設定しておく |

**doctorとSentryは重ならない。** doctorは「**いまの状態**」（設定が正しいか・止まっていないか）、
Sentryは「**過去に起きた例外**」。2026-08-19のAIクレジット切れは前者、
「特定の利用者の操作だけ落ちる」は後者でしか見つからない。

**`doctor` はVercelの定時実行には入っていない**（`vercel.json` の cron は
`news-fetch`／`scheduler_tick`／`metrics-collector`／`follower-snapshot` の4本）。
毎朝のメールは `scheduler_tick` に相乗りしており、**doctor用の定時実行は増やしていない**（原則3）。

**環境ごとの届き方**: 毎朝のメールが届くのは**Vercel Cronが動く環境（本番）だけ**。
stagingは別プロジェクトとして本番デプロイになっていれば届く。ローカルは定時実行が無く、
非productionから外部SMTPへ送らないガードもあるため届かない（要決定D-29＝手動起動）。
ローカルとstagingは `npm run doctor -- --base <URL>` で見る。件名に環境名が入る。

## 2. doctorの検査項目

**この表はコードと機械的に突き合わせている**（`src/lib/ops/doctor-doc-sync.test.ts`）。
項目を増やしても表を直さなければテストが落ちる——手で数え上げた一覧は必ず古くなる（ADR-0005／T-M8-87の教訓）。
判定の正本は `src/lib/ops/diagnostics.ts`。

### デプロイ先の状態（`/api/cron/doctor` が返す。毎朝のメールもこれ）

| 検査項目 | 見ているもの |
|---|---|
| Xへの投稿 | `X_POSTING_MODE`。本番で `dry_run` のままなら投稿が1件も出ない（T-M8-147） |
| アプリのURL設定 | `APP_BASE_URL` と実際の配信元の一致。ずれるとメールのリンクとX連携の戻り先が別ドメインを指す |
| 決済（Stripe）の接続先 | 鍵が `live` か `test` か |
| エラーの記録（Sentry） | DSNの種別（未設定／仮の値／有効）と受け先ホスト。**未設定でも画面は正常に見える**（T-M8-162） |
| 生成・投稿の動作 | 直近24時間の成功／失敗件数 |
| 繰り返している失敗 | 直近24時間で**同じ理由**の失敗が続いていないか、**実行が全部失敗している利用者**がいないか（T-M8-307）。合計件数では、1人の利用者だけが完全に使えない状態が他の人の成功に紛れて見えない |
| 定時実行 | `scheduler_tick` が最後に動いた時刻 |
| ニュースの取得 | 直近48時間の取得件数と、分野ごとの失敗理由（**AIの残高不足などを直せる言葉で出す**・T-M8-163）。**停止の判定は「予定の回が飛んだか」で行う**（T-M8-310）——`news_fetch` は UTC0〜12時の3時間おきで UTC12時→翌0時は予定として12時間空くため、経過時間の固定閾値だと毎晩かならず赤くなる |
| Xアカウントの連携 | 連携済みアカウントの有無と状態。**access tokenの期限切れは警告しない**（1時間ごとの先回り更新と実行時の自動更新で戻るため・T-M8-359）。知らせるのは「要再連携」と「自動更新の許可が無い」＝人が操作しないと直らない場合だけ |
| メール確認が終わっていない登録 | 確認途中で止まっている登録 |
| 止まっている処理 | `running` のまま滞留しているジョブ |
| ホームの閲覧記録 | 本番で直近2日（JST・今日と昨日）にホーム `/` の閲覧が1件も記録されていなければ注意。記録の書き込みが壊れると /admin では「来訪が減った」に見えるため（原則1・T-M8-422）。ローカルでは判定しない |
| 今月かかった費用 | 外部APIの当月実績（原則4「費用が見える」） |
| データベースの使用量 | Supabase無料枠に対する使用量 |
| DB接続の混み具合 | 接続の待ち行列（`db_pool_events`）。直近24時間で待ちが0件なら正常。1件以上で注意、20件以上で異常——**Supabase Proへの移行条件**「pooler接続の枯渇・待ち行列が観測された」（要件01 §9）を判断する材料（T-M8-198） |
| 人間確認（ボット対策） | Supabase側のCAPTCHA有効・Turnstileの設定 |
| プラン管理（Stripe） | Customer Portalでプラン変更・解約ができる設定か。**`enabled` だけでなく中身も見る**（T-M8-238）: 変更先に現行の Price が入っているか（`expand` しないと取得できない）／トライアル中の変更が `continue_trial` か（`end_trial` だと無料期間が即終了して課金される） |
| 請求額と表示額の一致（Stripe） | 画面の金額とStripeのPriceが一致しているか |
| 決済の受付（Stripeアカウント） | アカウントが本番決済を受け付けられるか。**アプリからは見えない**（T-M8-148） |
| 契約イベントの受け取り（Stripe webhook） | Stripe側の購読イベントが `STRIPE_WEBHOOK_EVENT_TYPES` を満たすか・受け口が有効か（T-M8-238）。**購読の選択はダッシュボード側の設定でコードに現れない**。実際に本番・stagingとも `charge.refunded` が抜けており、返金しても招待報酬が取り消されない状態だった |
| 契約の同期（Stripe → アプリ） | **更新日・トライアル終了日を過ぎたのに、その後のStripeイベントを受け取っていない契約の件数**（本番のみ・T-M8-238／T-M8-371）。webhookが届かなくなっても例外は起きず、解約・プラン変更が反映されないまま画面は正常に見える。**無音そのものは異常ではない**——イベントは契約に動きがあったときにしか来ないため、経過時間で判定すると毎日warnが出て本物が埋もれる |
| 招待報酬の振込 | 未払いの振込件数・合計額・最も近い支払期限（T-M8-241）。**振込は運営者の手作業**なので、期限まで7日を切ったら警告・過ぎたらエラーで名指しする（原則3: 手順を記憶に依存させない） |
| ブログ記事の同梱 | `blog/published/*.md` がデプロイに含まれているか（`outputFileTracingIncludes` 漏れは**本番だけ「準備中」になる**）と、front matter の不備で公開されていない記事（T-M8-184） |

## 3. Sentryに入るもの・入らないもの

**列挙はしない**（送信箇所は増減するので、写した一覧は必ず古くなる）。方針だけを正本とする。

- **入る**: アプリが想定していない例外。Server Actions全般（`_helpers.ts` の共通catch）、認証（登録・
  6桁コード確認・再送・パスワード再設定）、Stripe webhook、定時実行、認証proxyのprofile取得失敗（T-M8-159）。
  実際の送信箇所は `recordUnexpectedError` / `captureServerException` の呼び出し元を見る。
- **入らない**: 秘密値・投稿前の入力内容（`redactEvent` が除去）。想定内の失敗（入力検証エラーなど）。
  **AIの残高不足のような「設定・外部要因の異常」も入らない**——例外ではなく状態なので、doctor側が担う。
- **保持期間は90日**（現行プランで固定・短縮不可。要決定D-19）。データ保存先はEU（ドイツ）リージョン。

## 4. 解約理由を読む（SQL）

解約前のアンケートは `cancellation_surveys` に残る（要件02 §3.20）。**Stripeのダッシュボードを
見に行かなくても、自分のDBで読める**。`service_role` に SELECT があるので、Supabase の
SQL Editor でそのまま叩ける。

**理由は複数選べる**（T-M8-294）ので、`unnest(reasons)` で展開して数える。
1件の回答が複数の理由に数えられるため、**合計は回答数より多くなる**。

```sql
-- 理由ごとの件数（直近30日・実際に解約手続きへ進んだ分だけ）
select reason, count(*) as 件数
  from cancellation_surveys, unnest(reasons) as reason
 where created_at >= now() - interval '30 days' and proceeded
 group by reason order by 件数 desc;
```

```sql
-- 自由記述（何を直すべきかは、たいていここに書いてある）
select created_at::date as 日, plan as プラン, reasons as 理由, detail as 記述
  from cancellation_surveys
 where detail is not null
 order by created_at desc limit 50;
```

```sql
-- 確認画面で引き返した人（＝留まった人）の理由。何が刺さって留まったかが分かる
select reason, count(*) as 件数
  from cancellation_surveys, unnest(reasons) as reason
 where not proceeded
 group by reason order by 件数 desc;
```

`proceeded` は**確認画面から解約手続きへ進んだか**。引き返した回答も残しているので、
`proceeded` で絞らないと「留まった人の不満」まで解約理由として数えてしまう。
`plan` は**回答時点**のプランなので、後からプランが変わっても当時の内訳が読める。

**理由の値は変えない**（`src/lib/billing/cancellation-reasons.ts` の定数）。変えると
過去の集計と接続できなくなる。選択肢を増やすのは安全、既存の値を書き換えるのは危険。

## 5. 切れる前に気付けないもの

**AIの残高（クレジット）は事前警告を作れない。** 提供元が残高を読むAPIを公開していないため、
アプリ側からは「使おうとして失敗した」時点でしか分からない。
**切れる前に気付く唯一の手段は提供元側の設定**（Anthropic / OpenAI の自動チャージと残高アラート）で、
これは運営者の作業。doctorと毎朝のメールは「切れた後に確実に届く」ところまでを担う。

## 運営ダッシュボード（/admin・T-M8-373）

事業KPIを見る画面は `https://exosai.net/admin`（**ログイン済みかつ `SUPPORT_EMAIL` と同じメールの利用者だけ**。他の利用者・未ログインには404/ログイン画面）。

| 見えるもの | 出どころ |
|---|---|
| MRR・原価・粗利・契約者数のサマリ | 生データ（profiles・原価台帳）をリクエスト時に集計。**原価は運営負担（`payer='operator'`）だけ**で、利用者負担（BYOK）は参考額として別に出す（T-M8-422）。「登録者（現在）」は退会で減る現在値 |
| 入口ファネル（ホーム→新規登録画面→登録完了・直近30日JST・未ログイン含む） | `page_views`（Cookieなし・日替わりハッシュ・T-M8-378）。**画面遷移だけ数える**（`sec-fetch-dest: document`）。bot・先読み・運営者自身・監視スクリプト（UA `exos-monitoring/…`）は除外（T-M8-422）。ユニークは日次ユニークの合計。3段目「登録完了」は直近30日の登録者数（`/plans` はログイン後なので入口に含めない） |
| ファネル（登録→課金の到達段階） | 生データ。退会者は消えるため「いま残っている人」の数 |
| MRR・登録者・原価・**ホーム来訪者**の推移グラフ | `kpi_daily`（日次スナップショット・400日保持）。来訪者の今日ぶんだけ生の`page_views`から合成（T-M8-379） |
| 流入元（直近30日） | `traffic_sources`（運営者が /admin で登録・追跡URL `/?src=<slug>`）×`page_views.source`・`profiles.signup_source`。ホーム表示・ユニーク・新規登録画面・登録・課金中。Cookie を持たないので、ホームから登録へ直接進んだ人だけが登録に紐づく（T-M8-423） |
| 今月の原価内訳（提供元・処理・利用者別） | 原価台帳（`external_api_usage_events`・400日保持）の運営負担分。利用者別の `user_id` 無しは「運営・共通」（ニュース基盤）と「退会済み利用者」を分ける（T-M8-422） |
| 利用者一覧（メール・登録日・プラン/状態・X連携・生成/投稿数・今月の原価・最終利用） | 生データ。登録の新しい順・最大200人（T-M8-374）。**生成は `generation_jobs` の成功件数**（BYOK も入る。以前は精算行の `delta = 1` を数えていて全員0だった・T-M8-422） |
| 解約アンケート直近10件 | `cancellation_surveys` |

画面上部の「本番 / staging / ローカル」は**環境の切替リンク**（T-M8-374）。DBは環境ごとに分離されているため（deployment.md）、1画面から横断表示はせず**各環境の /admin へ移動して見る**。表示中の環境が黒背景のバッジになる。グラフはカーソル（スマホはタップ）で日付と値が出る。

スナップショットは `scheduler_tick` が日付の変わった直後に1日1回書く（`kpi_snapshot`・要件04参照）。円換算は1ドル=160円（PRD §6.1の事業計画と同じ仮定）。**MRRはトライアルを含まない**（課金が始まっていないため。トライアル人数は別カードで出す）。
