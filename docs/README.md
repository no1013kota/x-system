# ドキュメントマップ

`docs/`はSpace AIの仕様の正本（Single Source of Truth）。実装と食い違った状態を放置しない。

## 正本の構成

| 領域 | 内容 | 更新タイミング |
|---|---|---|
| [PRD](./PRD.md) | 何を作るか・なぜ。機能ID、スコープ、プラン、上限、非機能、成功指標 | 要件・料金・スコープ・上限が変わるとき |
| [要件定義書](./要件定義書.md) | どう作るかの全体像と詳細文書への索引 | 要件詳細の構成・全体像が変わるとき |
| [要件詳細](./requirements/README.md) | システム、DB、課金、job、API、画面仕様 | 画面・処理・DB・API・infraが変わるとき |
| [AI実行・プロンプト設計書](./プロンプト設計書.md) | AI実行ID、ベースmd、prompt、provider adapter、出力検証 | AI実行・prompt・検証・上限計数が変わるとき |
| [運用メモ](./operations/) | launchd運用、Vercel Cron移行などの手順 | 実行基盤・切り替え手順が変わるとき |
| [ADR](./decisions/README.md) | 上記で表現しきれない重要な技術判断 | 技術選定や不可逆な判断を行うとき |

## 仕様の所有ルール

- 機能の有無、プラン差、料金、月間上限はPRDを正本とする。
- DB・API・画面・jobの数値と構造は`requirements/`の担当文書だけで定義し、要件定義書本体には要約だけを書く。
- AI prompt全文とAI出力検証はプロンプト設計書を正本とする。要件詳細には実行順と保存先だけを書く。
- 1つの変更が複数領域へ影響する場合は同じ作業単位で更新する。例: 利用上限変更はPRD、要件03、プロンプト設計書の計数規則を同期する。

## ID体系

| 種別 | ID |
|---|---|
| 機能 | A/L/N/P/S/K/M/O |
| 画面 | SC-01〜SC-11 |
| AI実行 | GEN/NEWS/LRN/MD-MERGE/SUGGEST |
| 開発タスク | `T-*`。`tasks/BACKLOG.md`作成後に運用 |

## 更新ルール

- 文書内versionと変更履歴を正とし、ファイル名にはversionを含めない。
- 仕様変更時は冒頭の更新日と末尾の変更履歴を更新する。表記修正だけならversionは上げず、変更履歴への追記も不要。
- DB変更はmigration、API変更は呼び出し側、prompt変更は検証schemaへの波及を同時に確認する。
- 外部APIの価格・scope・field・limitはリリース前に公式情報を確認する。確認日と採用前提を該当文書へ残す。
- 未決の事業判断はPRD §11へ集約し、要件詳細へ開発優先度メタデータとして重複記載しない。
- コミット前に`/doc-sync`を実行する。コードがまだない領域は「未実装」であることをREADMEまたはバックログに明記する。
- `old/`は参照専用で、同期・編集対象に含めない。
