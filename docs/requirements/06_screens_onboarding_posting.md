### 1.0 用語とパターン選択の共通仕様

- **画面の呼称は「アカウント設定」（旧: 発信設定）「アカウント.md」（旧: ベースmd/ベース.md）で統一する**（2026-08-15 運営者決定・T-M8-102）。**内部名は変えない**——コード識別子・DBカラム（`base_md`・`base_md_versions`）・タブslug・プロンプト内部の表記（`<base_md>`タグ、SYS-GEN/PT-MD-MERGE本文中の「ベースmd」）は従来どおり。プロンプト本文を変えると全パターンの再検証（実費）が必要になるため（「分野:」と同じ理屈）。
- **テーマ選択肢の呼び名は「テーマ」で統一する**（2026-08-03 決定・当時は6つ）。以前は投稿作成・ニュース・通知設定が「分野」、AI設定が「テーマ」と呼んでおり、同じものに2つの名前があった。DBの型名（`news_category`）は変えない。**プロンプト内部の `分野:` も変えない**（利用者に見えず、変更すると全パターンのプロンプト再検証が必要になる）。


- パターン選択はSC-07（投稿作成）とSC-08（スケジュール）で**同じ部品・同じ見た目**を使う（ラジオボタン＋ラベル＋その下に説明文）。同じものを選ぶ操作なので、画面によって見た目や情報量が変わらないようにする。
- **選択肢は利用者ごとのマスタ（`post_patterns`・要件02 §3.21）から引く**（T-M8-129・ADR-0008）。既定6件はXアカウント作成時に自動投入され、利用者は追加・編集・削除できる（既定も削除可）。説明文に添える分量は`max_posts`から画面が組む（説明文に数を書かない。書くと片方だけ直して食い違う・T-M8-33）。
- **設定がどこに効くかを画面に書く**（T-M8-131）。分量・Web検索・参考URLは生成のたびに`<pattern_rules>`としてプロンプトへ渡り、分量は生成後の上限としても効く。投稿作成では選択中パターンの分量を1行で示す。
- 投稿作成の「参考にするURL（任意）」はAIに読ませる題材のURL。**生成した投稿に参考URLを添えるかどうかはプロンプトに書く**（T-M8-132で専用の設定欄をやめた）。
- **分量はプロンプトに書き、そこから読む**（T-M8-132）。DBは総ポスト数（`max_posts`）で持ち、保存時にプロンプトの `Nスレッド目` から決める。画面には読み取った結果を「メイン＋スレッド2（最大3ポスト）」の形で出す。
- **パターンの追加と削除は設定＞パターン管理と投稿作成（SC-07）の両方からできる**（T-M8-130／T-M8-133／T-M8-134）。選んでいる型が要らないと気付くのも投稿作成画面なので、そこで消せるようにする。削除したら選択を先頭のパターンへ戻す。**削除は各パターンのカードの中に置く**（T-M8-134）——リストの外に1つ置く形だと、消したい型をいったん選んでから別の場所のボタンを探すことになる。ボタンは`<label>`の**外**（兄弟）に置き、押しても選択が動かないようにする。読み上げ名にはパターン名を入れる（カードが並ぶため「削除」だけでは対象が分からない）。最後の1件はボタン自体を出さない（サーバーも拒否する）。**SC-08（スケジュール）のカードにも同じ削除を出す**（T-M8-205・運営者の指示 2026-08-22。当初のT-M8-134では出さない判断だったが反転）。削除の確認は簡潔な箇条書き（下書き・履歴は残る／使用中の予約は停止／既定は復元可）で出す。入力欄は**両画面で同じ部品**（`components/post/pattern-fields.tsx`）を使い、追加直後はその型が選択された状態にする。**「パターンを追加」は一覧の最後に、既存パターンと同じパネル形式で置く**（T-M8-331・運営者の指示 2026-08-27。SC-07・SC-08 共通。一覧の外に単独のボタンを置くと「選ぶ」操作と「増やす」操作が別の場所に分かれる）。枠線は破線にして「まだ無いもの」であることを示し、`<label>`ではなく`<button>`にする（ラジオの仲間に見せない）。
- **パターン追加フォームの「参考投稿からAIで作る」**（T-M8-397→T-M8-399・運営者の指示 2026-09-01。プロンプト・投稿作成・スケジュールの3画面共通）。参考投稿を最大3件入れて「AIでプロンプトを生成」を押すと、**名前・説明・生成プロンプトの3欄がすべて生成結果で置き換わる**（空欄だけを埋める形ではない。プレースホルダーは本文の `{名前}` から従来どおり導出）。**記入は本文の貼り付けでもX投稿のURL（`https://x.com/<handle>/status/<id>`・twitter.com／mobile／クエリ付きも可）でもよい**——URLは連携中のXアカウントで本文へ引き直す。X以外のURLだけの行・読めない投稿（非公開・削除・X連携切れ）は**どの行がなぜ読めないか**をトーストに出し（X連携が原因なら設定＞Xアカウントへの導線付き）、読めた分だけで生成しない。保存は利用者が行う。
- **新規作成時のプロンプト欄には雛形を入れておく**（`NEW_PATTERN_PROMPT_TEMPLATE`）。既定パターンは「# タスク／# 手順／# 構成と分量／# 語り口」という決まった形で、生成の質がこの形に依存する。空欄から書き始めさせると指示の抜けたプロンプトになりやすい。雛形に本数は書かない（スレッド数の設定と食い違うため）。引用URLが必須のパターンは予約（SC-08）では選べない。
- 履歴・分析・投稿確認のバッジは**生成時に写した名前**（`drafts.pattern_name`）を出す。パターンを削除しても過去の表示は変わらない。予約はパターンを削除されると停止し、パターン欄は「パターン未設定」と出す（空欄にすると設定漏れか削除かが分からない）。
- **`P1` のようなパターン番号は画面に出さない**（2026-08-03 決定）。利用者にとって意味を持たない記号で、画面の中に答えが無い。IDはURL・DBの値としてだけ使う。
- 選択肢の定義（名前・説明）は**アカウント別マスタ `post_patterns`（DB）が正**で、画面へ渡す形（`PatternOption`）と表示文の組み立ては `src/lib/post/post-patterns-store.ts` を単一の正とする（T-M8-129・ADR-0008 でコード定数 `post-patterns.ts` から移した）。履歴・分析・投稿確認のバッジは**生成時に写した名前**（`drafts.pattern_name`）を出す。**選ぶ画面と表示する画面で名前が違う状態を作らない。**

### 1.1 SC-04 プラン選択

- 認証済みユーザーへスタンダードプラン／プレミアムプラン／エキスパートプランを比較表示し、税込月額、Xアカウント上限、BYOK要否を示す。**表示の形は3枚のプランカード（`PlanPricingCards`）が正本**（T-M8-169・運営者の指示 2026-08-21。参考: tweethunter.io/pricing）。各カードは プラン名・1行説明・価格・CTA・Xアカウント数バンド・「下位プランの全機能に加えて」のチェックリストで構成する。**見せ方はLP `#pricing` と同じ「推奨先行」**（T-M8-424・運営者の依頼 2026-09-04「ホームページの料金に /plans も合わせる」）: 共用の組み立て部品 `PlanPickerRecommendFirst`（`src/components/billing/` の plan-picker-recommend-first。CSS module 同梱）がカードの上に「約N円／日」のキャップ行を密着させ、推奨（プレミアム）だけ brand 帯「まずはこれ」（sr-only でプラン名と「この帯の直下のカード」を読み上げ）＋CTA強調で示す。両隣のキャップ（md以上のみ）は要約1行（BYOKは「自分のAPIキーで使う（API利用料は別）」、エキスパートは「APIキー不要・無制限・Xアカウント3件まで」を `plans.ts` から）。カード内の「おすすめ」バッジは帯が代わるので CSS module で消す（「選ばれています」等の実績表現は使わない・景表法）。両隣のカードはガラス（白60%・影なし）、SP（md未満）は縦積みで推奨カードを先頭（`order:-1`。DOM順・Tab順は据え置き）。h1 はLPの料金セクションと同じ「業界最安価の価格設定」（運営者の指示 2026-09-04・D-56。以前の画面名「あなたの運用に合うプランを選択」と、見出し下の選び方の1文・CTAより上の「はじめての方は7日間無料（カード登録が必要）です。」は同日に削除）。無料の条件（カード登録が必要・期間中解約無料）はカード下の帯（`trialAvailable` で消化済み・残りトライアル中には出さない）と特商法ページが担う。ロゴ／ログアウトの行は全幅（キャップ行・カード・帯と左右の縁を揃える）、料金の背景はLPと同じ brand の radial glow（装飾）。CTA（`CheckoutButton`）はLPの Link と同じ太さ（`text-sm font-bold`）。プラン名の表示はPRD §プランと同じ日本語表記を正とする（コードの `PLANS[].displayName`）。
- BYOK（通常・md）でX API・生成AI APIの利用料がExos AI月額とは別に各提供元から請求されることは、**カード直下の注意ブロックで明示**する（折りたたまない）。カードの特長に書く件数・利用上限（契約期間ごと）は `PLANS` から導出し、画面に数値を書き写さない。
- カードの**下**に**プロモ帯（`CampaignCallout`）**を置く（T-M8-171・運営者の決定 2026-08-21で申込前確認の定型文を畳んだ。位置はT-M8-424でLPに合わせて上から下へ——カードの上は「どれを選ぶか」だけにする。`trialAvailable` は共用部品経由で帯へ渡す）。帯には**「カード登録が必要」「期間中に解約すれば無料」**の2点の開示を必ず残す（景表法の有利誤認回避・無料の条件。`landing-page.test.ts` が画面に出る文字列で固定）。**「初回のみ」は 2026-08-26 に帯から外した**（T-M8-321・運営者の最終レビュー。初回限りの開示はLPのFAQ「はじめてのお申し込みに限り」・特商法ページ・利用規約が担う）。CTAより上の開示は見出し下の1文の末尾「はじめての方は7日間無料（カード登録が必要）です。」の1行（暫定・D-54）。法定事項の全文は`/legal/commercial-transactions`が担う（フッタから常時到達）。

- 申込前の常時表示はプロモ帯（「カード登録が必要」「期間中解約で無料」の2点。「初回のみ」は帯から外した・2026-08-26）と見出し下の1文（「はじめての方は7日間無料（カード登録が必要）です。」）、カード内の価格・API実費に絞る（T-M8-171・運営者の決定）。自動更新・支払時期・解約方法・提供開始の全文は特商法ページ・利用規約が担う。**トライアル消化済み（`trial_used_at`あり）の利用者には「7日間無料」を出さない**（眉ピル・プロモ帯のトライアル文・CTAを出し分ける。有利誤認の回避・T-M8-174レビュー修正）。

- `checkout=canceled`は未完了として再選択を案内する。Checkout successは復帰handlerで未反映時だけ同期した後、`checkout=success&sync=...`として契約情報確認中を表示する。契約の確定表示はprofileを正とし、通常表示ではStripe APIを呼ばない。契約が有効（`trialing`／`active`＝`canExecute`）なユーザーが`/plans`を開いた場合は`/app`へredirectし、決済成功後にこの画面で行き止まりにならないようにする。`incomplete`／`incomplete_expired`はプラン選択、`canceled`等（`canExecute=false`）は再申込導線のため`/plans`に留める。
- 反映待ち（`checkout=success`かつ未反映）の間は**プランカードとCTAを描画せず**、待機カードだけを表示する。カードには所要目安（通常1分ほど）・自動で確認している旨・手動の「状況を再確認」・重複申込を避ける注意とサポート連絡先を含める。数秒間隔で自動再取得し、反映されたら上記redirectでホームへ送る（約1分で自動確認は停止し、手動確認と問い合わせに切り替える）。
- CTAは3プランすべて「7日間無料で利用」（初回`trial_used_at=null`のみ7日trial）。推奨（プレミアム）だけキー色で他はsubtle（T-M8-169）。事前開示のうち常時表示するのは**プロモ帯の2点（カード登録・期間中解約無料）と見出し下の1文、カード行のAPI実費**で、その他（自動更新・支払時期・解約方法・提供開始）は特商法ページ・利用規約が担う（運営者の決定 2026-08-21）。
- 狭い幅ではカードを縦に積み、**画面全体を横に伸ばさない**（App Shellのヘッダーと同じ方針）。以前は横スクロールする比較表で、セル内の視覚的非表示テキスト（`position:absolute`）が位置指定された祖先を持たずページ自体を横へ伸ばす事故があった（T-M7-26）。表を使う場合はスクロールする要素側に位置指定を与える。
- `/legal/commercial-transactions`への新規タブリンクを申込条件に置く。

### 1.2 SC-11 課金・問い合わせ（M1最小実装）

### 1.2.1 SC-11 Xアカウントタブ（M2）

- `/app/settings?tab=api-keys`は、キー登録が不要なプラン（プレミアム・エキスパート）では登録欄を出さず、**代わりに利用枠（契約期間ごと）の残量を表示する**（枠のカードはホーム・課金タブと同じもの。エキスパートは数値を出さず「無制限」・T-M8-168）。「不要です」の一文だけでは何も操作できない行き止まりになるため。
- `/app/settings?tab=x-accounts`の各行から**操作対象を切り替えられる**（2026-08-03 決定）。ヘッダーの切替メニューだけだと、設定画面で一覧を見ている利用者が切替場所を探すことになる。切り替えると下書き・履歴・スケジュール・分析もそのアカウントのものになる（PRD A-6）。切替中の行は「操作中」を出し、切替ボタンは出さない。
- ヘッダーの切替メニューの読み上げ名には**操作中のアカウントを含める**（`aria-label`が中の文字を上書きするため、含めないと支援技術にはどのアカウントを操作中か伝わらない）。
- `/app/settings?tab=x-accounts`は連携済みXアカウントを一覧し、各行に`handle`・表示名・`status`（有効／要再連携／停止中／エラー）・`auth_type`（BYOK＝自分のApp／運営App＝プレミアム・エキスパートプラン）と、現在操作中アカウントの目印を表示する。**X Premium加入アカウントには「X Premium」バッジを出す**（`x_accounts.x_premium`。連携時・「接続を確認」・再有効化のusers/meで更新される・T-M8-219）。**状態は色でも区別する**（`Badge` の tone。色が無いとトークン失効に気付けない）。**「再連携」は対象アカウントを指定して開始する**（`?account=<id>`）——別のXアカウントで認可された場合は新規連携を作らず中断し、理由を表示する（要件05 §3）。同じXアカウントで認可されれば既存行が`active`へ置き換わるので、失効の表示は消える。
- 「Xアカウントを追加」はOAuth開始（`GET /api/x/oauth/start`）へ遷移する。有効アカウント数がプラン上限に達しているときはボタンを無効化し、`有効 N / 上限` 件を表示する。
- BYOK（スタンダード）でX APIキー未登録のときは、追加ボタンをAPIキータブへの導線（「先にX APIキーを登録」）に差し替え、Client IDが必要である旨を併記する（押してから無言でAPIキータブへ戻される事故を防ぐ）。上限到達の表示を優先する。
- `expired`／`error`には再連携導線、`disabled`には再有効化（`enableXAccount`）と再連携を出す。各行の**「接続を確認」**（`refreshXAccountStatus`）はXに問い合わせて連携がまだ使えるかを確かめ、**結果の状態（有効／要再連携…）をトーストで返す**（旧ラベル「状態を更新」は何を更新するのか読めなかった・T-M8-56）。
- **`disabled`（停止中）のアカウントは一覧から畳む**（`<details>`で「停止中のアカウント N件（投稿履歴と実績は残っています）」）。使っていないアカウントが並び続けると、いま動いているものが埋もれる。行は消さない（下書き・履歴・実績が参照する）ので、畳んだ中から再有効化・再連携で一覧へ戻せる。**`expired`／`error` は畳まない**——再連携というやることが残っているので、隠すと気付けない。
- 切断（`disconnectXAccount`）は確認ダイアログを挟み、投稿と自動実行の停止・自動投稿同意の取り消しを説明し、下書き・投稿履歴・実績・アカウント.md等のデータは削除しないことを明示する。
- OAuthからの復帰は`x_connected=1`で成功、`x_oauth_error=<code>`（原因が判別できる場合は`x_oauth_reason=<reason>`も付与）でエラーを表示する。操作の成功後は表示中の一覧を再取得する。
- 連携エラーは戻り先がAPIキータブ等になる場合もあるため、**設定画面の先頭でタブに依らず表示**し、codeとreasonの組み合わせごとに日本語の原因説明と次アクション（APIキー登録／プラン確認／再連携など）を示す。生のエラーコードは表示しない。**token交換の失敗は internal_error に丸めない**（T-M8-63）——`provider_error` + `token_auth_failed`（401/invalid_client。Client Secret不足の可能性をAPIキータブへの導線付きで案内）／`token_grant_invalid`（認可コード期限切れ。最初からやり直せば直る）／reasonなし（X側の通信失敗）に分ける。

### 1.3 重大改定の再同意

- `/app/consent`は画面IDを持たない認証必須の補助画面とし、現行versionと不一致の文書だけを表示する。利用規約への「同意」とプライバシーポリシーの「確認」は別checkboxとし、文書リンクは新規タブで開く。
- 未チェック、画面表示後のversion更新、保存失敗は画面内errorとして留まり、profileを更新しない。同意成功後は`/app`へ戻り、両文書が現行なら同routeへの直接アクセスも`/app`へredirectする。
- 古いversionでもApp Shell、下書き、投稿履歴、分析、設定は閲覧できる。生成・投稿・自動実行の開始時だけ共通実行ガードがこの画面へ誘導する。**この誘導はServer Action共通の`requireExecutionUserId()`（`requireLegalConsent`）が担い、実行を開始するAction（生成6本・スケジュール4本）へ配線する**（T-M8-73。以前は`requireExecutionAccess`が実装されていながらどこからも呼ばれず、版を上げても再同意なしで実行できた＝利用規約の「再同意を求めます」が実装に裏付けられていなかった）。読み取り・停止・削除・キャンセルは対象外とする（同意が切れても止められる／閲覧できる必要がある）。
- **再同意が必要なあいだはヘッダー直下に常設バナーを出し、`/app/consent`へリンクする**（T-M8-134）。実行ガードはActionを弾くだけなので、バナーが無いと利用者は操作して初めて止まっていると気付き、しかも同意画面へ辿り着けない（2026-08-18、運営者がスケジュール保存で行き止まりに入った）。文面は「確認してください」で終えず、**生成・投稿・スケジュール保存が実行できないこと**を明示する。実行系Actionの失敗メッセージ（`legal_consent_required`）も画面上部の案内を指す。同意成功後は`revalidatePath("/app", "layout")`でApp Shellを作り直す（しないとキャッシュから返り、同意済みなのにバナーが残る）。

### 1.4 SC-05 ホーム

`/app`は「いま確認すべきこと・次に起きること・直近の結果」を上から順に並べる。**最上部に指標4カード**を置き、その下へ初期設定ガイド（§3.1、全条件充足で非表示）→確認待ちの下書き→次回の予定→重要ニュース→直近の実績→利用枠（運営キー系プランのみ。リセット日は契約の次回更新日・T-M8-258。エキスパートは数値を出さず「無制限」と、内部ガード到達時の一時停止案内だけを出す・T-M8-168）と並べる。いずれも表示専用で、操作は各画面へ遷移して行う。**確認待ちの下書きは新しい順に最大5件だけ取得・表示し、件数表示（カードタイトルとKPI）は総数のSQL countを使う**——全件取得だとthread/imagesのJSON転送が下書き数に比例して増える（T-M8-67）。超過分は「ほかN件は『すべて見る』から」と明示し、黙って切り捨てない。

- **指標4カード**（フォロワー数／今週の投稿／未確認の下書き／次回の自動実行）。既存の集計から算出し、専用の保存はしない。**「まだ無い」と「取れていない」を区別する**——フォロワー数は記録が1件も無ければ0ではなく「記録なし」と出す（§8の`--`＝取得不能とも区別する）。今週はJSTの月曜起点。

- **次回の予定**: 有効スロットの次回実行を早い順に最大3件表示し、各行に日時（JST）・パターン・自動投稿／下書き作成の別・画像の有無を示す。停止中のスロットと、曜日・時刻から次回を算出できないスロットは除く。
- 初期設定が未完了の間は、予定があっても実行されないことを警告し、§3.1の「次にやること」と同じ設定画面へ誘導する。

## 2. 共通App Shell

- **タブ（設定・投稿・AI設定の`?tab=`遷移）は押した直後に、押したタブへスピナーを出す**（`useLinkStatus`・T-M8-67）。searchParamsのみの遷移では`loading.tsx`が再表示されないため、これが無いとサーバー応答まで画面が無反応になる。PC左ナビ／モバイル下部ナビも、遷移中は行き先リンクのアイコンをスピナーへ切り替える（T-M8-154）。
- **主要ナビとURLタブの先読みは段階化する**（T-M8-154）。表示しただけのリンクはNext.js既定の自動prefetch（動的routeでは最寄りの`loading.tsx`まで）を保ち、hover／キーボードfocus／touchで移動意図が出たリンクだけ`prefetch=true`へ昇格してページ本体とデータの取得をクリック前に始める。全リンクを最初からfull prefetchして未訪問画面のDB取得を一斉実行してはならない。現在地リンクはprefetchしない。
- `/app`と`/plans`は各routeの`loading.tsx`を使い、Server応答前に遷移と読込表示を開始する。最上位のroot `loading.tsx`は置かない（開発モードのnonce付きCSP下でNext.jsが動的に挿入する共通loading chunkが拒否され、ローカルのconsole errorを増やすため）。各`page.tsx`のデータ取得は依存の無いクエリを`Promise.all`で束ね、直列往復を作らない。

### 2.1 操作結果の通知（トースト）

**操作の結果は画面右下のトーストへ集約する。** 同じ結果を画面内とトーストの2か所へ出さない。

  | 種類 | 画面に残す理由 | 例 |
  |---|---|---|
  | 入力検証 | 直す場所の近くに無いと何を直せばよいか分からない。`aria-describedby` も切れる | 見出し構造が不正・文字数超過・本文が空 |

## 3. 初期設定と実行前提

専用のオンボーディングウィザード・進捗保存は持たない。初期設定は設定画面で任意の順に行い、前提条件は各操作の実行時にサーバー側で検証する。

- **反映は保存前の提案**（T-M8-349）。ボタンは「アカウント設定を反映する」で、押すと `md_merge` が結果を `x_accounts.settings_proposal` へ置き、**フォームの各欄がその値で埋まる**（`settings` とアカウント.mdは変わらない）。画面は「参考ソースから作った内容を入れました。まだ保存されていません」を出し、利用者が「アカウント設定を保存」を押したときに確定する（保存で `settings_proposal` は `null` へ戻る）。**押した瞬間に本番の設定が変わると、利用者は中身を見る前に書き換えられてしまう。**
- **分析が終わるまで反映は起票しない**（T-M8-349）。画面は3秒おきに最大3分待ち、それでも分析が終わらなければ「分析がまだ終わっていません。一覧が『反映済み』になったら、もう一度押してください」を出して押し直せる状態へ戻す。サーバー側も分析中は `job_conflict` で拒むが、**そのときの文言はこの状況のもの**にする（既定の「ほかの操作と重なりました。画面を再読み込みしてから…」は、待つべき場面で再読み込みという無意味な行動を指示していた）。
- **参考ソースの一覧はアカウント設定が未保存でも読む**（T-M8-349）。以前は `base_md_version >= 1` を条件にしていたため、登録しても一覧が空のままで「登録できたのか」が画面から分からなかった。
- **学習の反映はボタンで行う**（登録しただけでは設定は変わらない）。参考ソースを登録すると分析だけが走り（`learning_analysis`）、「参考ソースからアカウント設定を作る／更新する」を押すと `md_merge` job が**アカウント設定そのもの**（`x_accounts.settings`）を書き換え、アカウント.mdはそこから作り直される（T-M8-341/344）。**アカウント設定が未保存でも実行できる**——分析だけを材料に初版を作る（分析が1件も無ければ押せない。理由を画面に出す）。
- 押した後は**その画面**に「参考アカウントを読み込んでアカウント設定を作っています」を出し、完了したら**jobの成否を見て**（`learningApplyStatusAction` が直近の反映jobの結果と提案の有無を返す・T-M8-410）、提案が入ったときだけ成功トーストを出して画面を作り直す。失敗したら理由（`generation_jobs.error.message`）と次の一手（もう一度押す／自由入力で作る）を画面に残す（トーストで流さない）。完了時は登録済み一覧も取り直し、分析済みのソースに「開始が遅れています」を残さない。**お知らせ（通知）は出さない**（T-M8-344。押していないのに変わることが無いので、通知で追いかける必要が無い）。

### 3.5 自動投稿への同意

- X OAuth画面でscopeを認可しただけでは、自動投稿への同意完了と表示しない。
- 同意modalは対象アカウント（@handle）・この設定の内容（曜日・時刻・パターン）・初回実行日時・適用範囲（そのアカウントの自動投稿すべて。今後追加するスケジュールを含む）を明示する。同意versionは利用者向けに日付表記（例「2026年7月22日版」）で示し、内部値（`-draft`等の接尾辞を含む）は表示しない。
- SC-08で初めて「そのまま投稿」を選んだとき、自動生成された内容が指定時刻に確認なしでXへ投稿されること、thread途中失敗時は作成済みポストを自動削除し削除後は復元できないこと、投稿内容の責任、停止方法をmodalで説明する。説明文versionと独立した明示checkboxを表示し、同意後だけauto slotを保存できる。
- **SC-08のスロットはSC-07（投稿作成）と同じ生成入力を持つ**（T-M8-135）。予約は「毎週この設定で作る」ものなので、投稿作成でその都度指定していたものを枠に保存できないと同じ結果を再現できない。項目は**参考URL**（`source_url`）・**プレースホルダーの値**（`placeholder_values`。選んだパターンが持つ`{名前}`の分だけ入力欄を出す）・**追加指示**（`instructions`）・**この予約だけの生成プロンプト**（`prompt_override`）。実行時はすべて生成jobの`input`へ投稿作成と同じキー名で渡す（要件02 §3.10・要件04 §7）。
- **SC-08でもパターンを追加でき、生成プロンプトを確認・編集できる**（T-M8-135/203）。予約を組むときに「この型が無い」「この指示を直したい」と気付くのはこの画面なので、設定画面へ往復させると目的（予約を作る）が中断する。入力欄は投稿作成と同じ部品（`components/post/pattern-fields.tsx`・`components/post/prompt-block.tsx`）を使い、**SC-07と同じくインライン表示・追加中はアクティブ選択を外して追加フォームだけを出す**（パターン未確定のまま保存しようとすると理由つきで止める）。プロンプトの編集先は**「この予約にだけ使う」（既定）と「パターンに保存して他でも使う」の2択**——予約は繰り返し実行されるため、投稿作成の「この生成にだけ」とは意味が違うので文言を変える。**両方に残さない**（`prompt_override`を保存したらパターンへは書き戻さず、パターンへ保存したら枠の上書きを外す）。どちらが効いているか分からない状態を作らないため、枠に上書きがあるときは見出しに「（この予約用に変更済み）」と出し、パターンの内容へ戻す操作も置く。プロンプトの確認・編集は全プランで可能（T-M8-168で旧standardの制限を撤廃。未契約だけロック）。パターンを切り替えたら前のパターン向けの編集とプレースホルダーの値は破棄する。**プレースホルダーの入力欄はプロンプト本文の `{名前}` から導出**し、編集で増減するとその場で入力欄も増減する。保存時は本文に実在する名前の値だけを `placeholder_values` へ残す（T-M8-186）。**「本文」は枠の上書き（`prompt_override`）があればその本文**（T-M8-333）——パターン側の宣言だけで判定すると、上書きで足した項目の入力欄が画面に出るのに保存で値が消え、生成では「（未指定）」が差し込まれる（画面には何も出ない）。
- **SC-08のフォームの並び順**は「パターン（末尾にパターンを追加）→生成に使うプロンプト→**プレースホルダー**→**共通の入力（user_input）（テーマ→参考URL→追加指示）**→曜日→時刻→モード」（運営者の指示・2026-08-31。2026-08-18のテーマ先頭を上書き。見出しの文言も運営者の指示 2026-09-01）。プレースホルダーと共通入力の区別が付かなかったため、**それぞれ枠線＋見出し付きのグループ**（`fieldset`/`legend`）で分け、**型に属する入力を先**に置く（T-M8-388）。**「何を作るか」を上から順に決めてから「いつ出すか」を決める**流れは維持。**モードは時刻の下に置く**（T-M8-331）——横に並べると「時刻の設定の一部」に見え、下書きか自動投稿かという別の決めごとが埋もれる。
- SC-08のスロットも**テーマ（必須）**を持つ。選択肢は投稿作成と同じ運用中テーマ＋「その他」（T-M8-100。運用外テーマの既存枠は「（現在の設定）」として保全）。曜日ごとにテーマを変えられる（例: 月曜はAI、木曜は投資）。指定したテーマはスロット一覧の行にバッジで出し、週間プレビューでは`title`/`aria-label`へ含める（編集画面を開かないと分からない状態にしない）。「その他」はバッジを出さない。

## 4. 投稿作成

### 4.1 パターンとスレッド数

**2つの上限がある**（役割が違う）。**単一の正は `post_patterns` の行**（T-M8-129）で、`max_posts`＝生成時に作る総ポスト数の上限、`max_posts_edit`＝編集で許す上限。画面の説明は `max_posts` から自動で組む——説明文に数を書くと片方だけ直して食い違う（2026-08-03、画面がP-1「4〜6ポスト」と説明していたが実際は最大4だった）。

**画面は「スレッド数」で見せる**（0〜7。0はメインポストのみ＝単発。T-M8-130）。`スレッド数 = max_posts - 1`。

既定6件の値（Xアカウント作成時に投入される。利用者は変更・削除できる）:

| 既定パターン | スレッド数（画面） | 生成時の総ポスト数 | 編集で許す上限 | 必須入力 |
|---|---:|---:|---:|---|
| ニュース解説 | 3 | 4 | 6 | なし |
| 自分の考え・意見 | 0 | 1 | 1 | なし |
| ノウハウ・ハウツー | 5 | 6 | 7 | なし |
| トレンド便乗 | 1 | 2 | 5 | なし |
| 引用ポスト | 2 | 3 | 3 | 引用対象X URL（初期OFF） |
| 週次まとめ | 4 | 5 | 7 | なし |

画像生成は独立した投稿パターンではなく、どのパターンにも付与できるオプションとして扱う。

引用ポストは将来の有効化後に全プランで手動生成できる。`FEATURE_QUOTE_POST_ENABLED=false`の間は投稿作成・スケジュールのパターン選択肢と新規生成導線から外す（**設定＞プロンプトのパターン管理には出す**——編集・削除の対象なので隠すと触れなくなる）。判定は`post_patterns.requires_quote_url`で行い、利用者が作った引用型も同じ扱いになる（T-M8-129 U5）。過去のP-5 draftが存在する場合は本文と対象URLを閲覧可とするが、再生成・画像再生成・投稿ボタンを無効化し「引用ポスト機能は現在利用できません」と表示する。有効化後はネイティブ引用ではなく、1ポスト目へ対象X URLを付ける通常投稿としてプレビューし、「URL付き投稿枠を使用」と表示する。

### 4.2 生成入力

- 入力の並びは**パターン → プロンプト → プレースホルダー（パターンの`placeholders`に応じた毎回入力欄。既定の「自分の考え・意見」は`自分の考え`を持つパターンにだけ出る）→ 共通の入力（user_input）（テーマ → 参考URL → 追加指示）→ 生成したあと（モード）→ 画像生成 → 生成ボタン**（運営者の指示 2026-08-31・T-M8-388。テーマ先頭のT-M8-101〔2026-08-15〕を上書き）。プレースホルダーと共通入力は**枠線＋見出し付きのグループ**（「プレースホルダー」「共通の入力（user_input）」。見出しにタグ名 user_input を出すのは運営者の指示 2026-09-01——T-M8-314の「生タグを出さない」より新しい判断）で区別し、プレースホルダーが無い型では前者のグループごと出さない。共通入力は**テーマ（必須）**、参考URL、追加指示、画像生成ON/OFF。テーマの選択肢は**運用中テーマ（最新ニュース画面と同じ・`OPERATED_THEME_IDS`＝定時取得分野由来。現在 AI・Web3・SNS運用・投資・恋愛・美容）＋「その他（追加指示に記載）」**（T-M8-100/189）。保存・検証の語彙は運用6＋旧2＋その他のままで、旧テーマの既存データは表示・編集できる（編集中の運用外テーマは「（現在の設定）」として選択肢に残す）。**「指定なし」は置かない**——既定のまま押されると、選んだつもりで選んでいない状態になる。選んだテーマは題材をそのテーマへ限定する（プロンプト設計書 SYS-GEN）。「その他」はプロンプトへテーマを出さず、追加指示とアカウント.mdに委ねる。画像を作るAIは選ばせず、プロンプト＞「AIモデル設定」の`image`を実行時に解決して使う（選んでも反映されない不整合を作らないため）。画像AIが未設定・キー未登録のときは、その旨と画像なしで作成される旨を添える。
- **選択中パターンのプロンプト編集**（T-M8-92→T-M8-203で全面改定。全プラン・未契約のみロック）: 折りたたみ「生成に使うプロンプト」（アカウント.md/投稿の型/画像生成の3タブ）は廃止し、パターン選択の下に**「パターンを追加」の記入欄と同じUI**（ラベル「生成プロンプト（型名）」＋右上字数＋mono textarea＋プレースホルダー一覧＋説明カラウト）を**インライン**で出す。**アカウント.md・画像プロンプトの編集は設定＞プロンプトへ集約**（`base_md_override`・`image_prompt_override` のAPIは残るがSC-07のUIからは渡さない）。編集すると「**この生成にだけ使う**」（既定。`prompt_override`として渡し保存しない）か「**保存して以後の生成にも使う**」（楽観ロック付き・保存に失敗したら生成を始めない）を選べ、「元に戻す」で破棄できる。型を切り替えると編集は破棄する。上限超過中は生成ボタンを無効化し理由を表示する。**「パターンを追加」中は既存パターンのアクティブ選択を外し、編集欄は追加フォームだけを出す**（編集欄を2つ並べない）。追加中は生成できない（理由を表示）。キャンセルで元の選択へ戻り、「追加」確定でパターン一覧に新しい枠が現れてそれがアクティブになる。**プレースホルダーの入力欄は、いま表示しているプロンプト本文の `{名前}`（`{{...}}`を除く・最大10件）から導出し、編集で増減するとその場で入力欄も増減する**（T-M8-186。**追加フォームを開いている間は追加中の本文から導出**・T-M8-203。値は名前ごと送り、上書きで増やした項目も生成側が本文基準で差し込む）。「{名前} と書くと入力欄が出る」説明は**目立つカラウト**（`PlaceholderCallout`）で出す（投稿作成・スケジュール・設定＞プロンプトで共通。グレー小の一覧は廃止・2026-08-22）。パターンを追加したら**その新パターンが選択された状態になる**。**ニュースからの遷移（`?news=<id>`）では、ニュース解説パターンの選択・`{ニュース}`と参考URL・テーマ＝記事の分野（選べない分野は「その他」・T-M8-386）の自動入力で開く**（記事が保持期限切れなら自動入力なしで開く）。生成時は `news_item_id` を送り作成済みバッジへつながる（T-M8-210）。
- **毎回入力する項目はパターンの`placeholders`から出す**（T-M8-132）。プロンプト内の`{名前}`に対応する入力欄が並び、入力した内容がその位置へ差し込まれる（既定の「自分の考え・意見」は`自分の考え`を持つ）。固定の「意見」欄（`asks_user_opinion`）は廃止した——毎回何を入れたいかは型ごとに違うため、利用者が決められる形にした。引用対象URLは`requires_quote_url`で出し分ける。内部IDでの分岐は残さない。
- **「生成したあと」（モード）を追加指示の下に置く**（T-M8-331・運営者の指示 2026-08-27）。選択肢は**下書きに置く（既定）／すぐに投稿／予約投稿**で、予約投稿は下書き画面と同じ日時指定（`datetime-local`・初期値は現在＋5分）を出す。生成ボタンの文言も選択に合わせて変わる（「ポストを生成する」／「生成してすぐに投稿する」／「生成して予約する」）。**作ったあとどうするかを作る前に決められるようにする**——以前は必ず下書きになり、投稿したい人は生成完了を待って下書きタブへ移動し、もう一度押す必要があった。
  - 日時の判定は下書き画面と同じ純粋層（`lib/draft-schedule.ts`）を画面とサーバーの両方で通す。**素の`datetime-local`値は日本時間として解釈する**（要件05 §5・T-M8-229）。不備は入力のたびに理由を出し、生成ボタンを無効化する（押すまで分からない失敗を作らない）。
  - **すぐに投稿・予約投稿は自動投稿の同意を求める**（要件05 §7）。生成された本文を利用者が見ないままXへ出るため、スケジュール（mode=auto）と同じ同意モーダル（`components/x/automation-consent-modal.tsx`・スケジュールと共用）を生成前に出し、同意を記録してから生成を始める。同意が無いまま送られた場合はサーバーが`automation_consent_required`で受理前に止める（AIの費用を使ったあとで投稿できないと分かる形にしない）。
  - 実装上は生成jobの`input`へ`mode`（`auto`＝すぐに投稿／`draft`）と`scheduled_at`（UTC ISO）で渡す。`scheduled_at`は下書き作成と同じINSERTで`drafts.scheduled_at`に入り、到来したら`scheduled-drafts`のcronが投稿する（要件04）。**予約は投稿へ連鎖させない**（連鎖させると予約時刻より前に出る）。
  - 完了表示も選択で言い分ける（「下書きを作成しました」／「続けてXへ投稿します」／「指定日時の予約として保存しました」）。
- 任意入力が空でも生成可能。ただしP-5の引用対象URLだけは必須。
- ニュース起点生成は`news_item_id`と`source_url`を引き継ぎ、P-1を初期選択する。
- 生成開始後は画面を離れてよい。`generation_jobs`の状態を再訪時に復元する。
- jobが`queued`のまま60秒を超えた場合は「開始が遅れています。自動で再開されます（最大5分）」と進行中扱いで表示する（dispatch失敗は次の`scheduler_tick`が回収する）。`failed`になった場合のみ原因と再試行導線を表示する。
- 進行中は所要目安（通常60〜90秒）・画面を離れてよいこと・完了後の行き先（下書きタブ）・経過時間を表示する。`queued`の間だけ「生成をキャンセル」を出し、`running`では中断できない旨を説明する（要件05 §5 `cancelGenerationJob`）。
- 失敗表示は保存済みの`error.code`/`error.message`を使う（`provider_raw_error`は表示しない）。`usage_limit_exceeded`は再試行を出さず利用状況・プランの確認へ、前提不足（`subscription_required`／`api_key_required`／`x_account_required`／`persona_required`）は該当設定画面へ誘導する。それ以外のみ再試行を出す。
- パターンの説明にはポスト数の目安を併記し、任意入力が空でも生成できること・生成結果が毎回変わることを画面上で伝える。

### 4.3 下書き編集

- ポスト本文の編集、並べ替え、追加、削除を許可する。編集後は1件以上かつ**下書きに写した`drafts.max_posts_edit`**以内に収める（生成時の上限はジョブに凍結した`pattern_spec.max_posts`）。**既定6件の実数値は要件02 §3.21 の表1か所だけに置く**——2か所に数字を書くと片方だけ古くなる（T-M8-139 で実際にそうなっていた）。
- 追加指示付き再生成は元下書きを保持して派生下書きを作る。派生元へのリンクを表示し、ユーザーが採用しない版を破棄できる。
- 生成確定時の本文を`initial_thread`へ保存し、その後の編集では更新しない。`source_job_id`を持つ生成draftが投稿された場合だけ最終本文との差分率を算出し、成功指標の下書き承認率へ使用する。正規化と編集距離の定義は[データモデル §4.7](./02_data_model.md#47-draftsthread)を正とし、AIを使わない失敗draftの複製は集計対象外とする。
- 各ポストは公式`twitter-text`互換の加重文字数で検証する。URLはt.co換算、CJK・絵文字等の重みを含む。
- 文字数超過、$タグ2件以上、NGワード、出典なし、要確認、長め、ポスト数を調整、画像なし（生成失敗）はポストまたは下書き単位の警告として表示する（画面ラベルの正本は `src/lib/post/warning-labels.ts`）。**引用対象が解決できない場合は警告ではなくジョブの失敗として扱う**（§5・要件04 §10 step3）。
- **読みやすさの目標超過（加重240＝約120字）とポスト数の切り詰めも警告として表示する**が、これらは**自動投稿を止めない**（T-M7-41）。契約違反ではなく品質の目印であり、これで予約投稿が黙って止まる方が害が大きい。編集の上限（上記のpattern別最大数）とは別に、**生成時はより短い上限**（P-1=4／P-2=1／P-3=6／P-4=2／P-5=3／P-6=5）へ収め、超過分は途中のポストを落として**スレッドの締めは残す**。
- 自動投稿を阻害する警告がある下書きは手動確認へ切り替え、ユーザーが修正するまで投稿しない。
- **止める警告と止めない警告を下書きのバッジで言い分ける。** 阻害する警告（文字数超過・$タグ2件以上・NGワード・出典なし・要確認）を含むときは「警告あり（自動投稿は停止します）」、止めない警告（長め・ポスト数を調整）と画像生成の失敗だけのときは「確認おすすめ（自動投稿は続きます）」を出す。以前は警告の有無だけを見ていたため、**止まっていない投稿を止まったと伝えていた**（CLAUDE.md 原則1に反する）。警告コードと「止めるかどうか」の対応は `src/lib/post/warning-codes.ts`、画面ラベルは `src/lib/post/warning-labels.ts` が正本で、コードを足してラベルを忘れると `npm run typecheck` が止まる。
- 投稿成功時は下書きを物理削除せず`status = posted`へ変更する。未投稿の「下書き」タブからは消え、「投稿履歴」タブへ移る。
- `status = posted`の本文・順序・引用対象は編集不可。tweet_ids別実績と監査に必要な履歴として表示する。**取得は直近50件まで**とし、上限に達したときは「直近50件を表示しています」と画面に明示する（全件取得は履歴の増加に比例して転送量と画像署名URL発行が増える・T-M8-67）。

## 6. 画像生成・添付

- MVPは生成画像1枚をスレッドの1ポスト目に添付する。
- 生成画像はJPG/PNG/WEBP、5MB以下に正規化し、private Storageへ保存する。下書き画面では表示時に生成する短時間の署名URL（DBへ永続化しない・要件02 §4.8）で添付画像を表示する。
- 画像プロバイダのAPIキーが未登録（BYOKでopenai/googleがともに未登録）の場合は画像再生成操作を非活性にする（PRD §8.2）。
- X投稿直前に`POST /2/media/upload`でmedia idを取得し、1ポスト目の`POST /2/tweets`へ指定する。
- 画像生成またはStorage保存に失敗した場合は、本文を画像なし下書きとして保存し警告する。自動投稿スロットも本文のみで投稿してよい。
- Xへのmedia uploadに失敗した場合は本文を投稿せず、下書きを`failed`にして再試行可能にする。
- 画像アップロードAPIの費用はサービス内利用枠・原価試算に含めない。画像枠は画像生成ジョブ開始時だけカウントする。
- 画像再生成中は既存画像を表示し、新画像の保存成功後に置き換える。下書き破棄時はそのdraft専用pathの生成画像をStorageからbest effortで削除するが、消費済み画像枠は返還しない。失敗draftを複製する場合は画像objectも新draft用pathへcopyし、draft間で同じobjectを共有しない。
- **画像はスレッド内のポストごとに1枚**（T-M8-398・運営者の指示 2026-09-01。旧: 下書き単位で1枚）。下書きカードの各ポストの下に画像パネルを出し、「画像を生成する」（AI・そのポストの本文から）「画像をアップロードする／差し替える」「画像を外す」ができる（`regenerateImageAction` / `uploadDraftImageAction` / `removeDraftImageAction` に `post_local_id`・要件05 §5）。**ポスト内では足すのではなく置き換える**（1ポスト1枚。2枚目を足せる形にすると「画面には2枚あるのに投稿されるのは片方」という説明できない状態になる）。旧データ（`post_local_id`無し）は1ポスト目のものとして扱う。差し替えで不要になった実体はStorageから消す（原則4）。投稿時は各画像が対応するポストへ添付される（要件04 §9）。
  - 受け取りはPNG/JPEG/WEBP・入力20MBまで。中身は生成画像と同じ `normalizeForX` に通す（**申告MIMEは信用できず、Xの5MB上限をここで守らないと投稿の瞬間に初めて失敗する**）。断る理由は画面にそのまま出す。
  - 画像はカードで**生成物か自分のアップロードか**を区別して示す（`provider` が `upload`）。どちらが投稿されるかが分かるようにする。
  - **投稿作成・スケジュールの「画像を生成する」チェックの下に「画像は下書きから自分でアップロードすることもできます。」を出す**——生成の隣で言わないと「画像はAIに作らせるしかない」と受け取られる。

## 7. 投稿実行と部分失敗

- 手動投稿の最終確認と自動投稿の同意文には、thread途中失敗時に作成済みポストを自動削除することと、削除後はX上で復元できないことを明示する。
- 手動投稿は`status=draft`（または未解決の投稿状態がない retryable `failed`）のみ許可する。投稿開始後は下書きの編集・破棄・再生成・再投稿操作を無効化し「投稿中…」を表示する。投稿完了で履歴タブへ移る。投稿の前提はAI生成と異なり課金・Xキー・X連携のみで、文章/画像AIキー・アカウント設定は不要。
- 投稿前に、課金状態、X連携、文字数、警告、premiumの通常投稿枠・URL付き投稿枠残量を再検証する。
- **投稿に失敗した下書き（`status=failed`、またはXへ出す前に差し戻された`status=draft`＋`last_post_error`）は、下書きタブ先頭の赤い専用枠「投稿に失敗した下書き」へ集める**（T-M8-227・運営者の指示 2026-08-22。予約・自動投稿の失敗もここに載る）。各カードは保存済みの失敗理由を表示し、既存の操作（編集・投稿・日時指定予約・新しい下書きとして再試行）でやり直せる。**別タブには分けない**——失敗は見に行かないと気付けない場所に置かず、下書きの操作と同じ場所で完結させる（原則1。通知ベルのエラー通知からの着地先もこのタブ）。
- 文字数超過（`length_exceeded`）がある下書きは手動投稿でもブロックし、投稿ボタンの代わりに理由と編集導線を出す。**X Premium（`x_accounts.x_premium`）のアカウントは上限を加重25,000へ緩和する**（T-M8-221・運営者の指示 2026-08-22。判定は編集保存の再検証と投稿直前の再検証の両方。編集画面は280超のとき「X Premiumのため投稿できます（上限25,000字）」と案内し、25,000超だけをエラーにする。生成は従来どおり280目標のまま）。**Xへ1件も投稿せずに止めた失敗は `draft` のまま保ち（`failed` にしない）、`last_post_error.message` を画面へ出す**（要件04 §10 step2）。`failed` にすると編集も複製もできない行き止まりになり、「編集して短くしてから投稿してください」という案内自体を実行できない。それ以外の警告（NGワード・出典なし・$タグ2件以上・要確認・長め・ポスト数を調整）は投稿確認ダイアログの先頭で「Nポスト目: 内容」の形で要約表示し、利用者が把握したうえで投稿できるようにする。
- 投稿中は`drafts.status='posting'`からも復元し、「投稿中…（この画面を離れても続きます）」を表示する。破棄・再試行が失敗した場合は理由を画面に出す（無音で終わらせない）。作成履歴・未解決があり破棄できない下書きには、その理由と次の手段（新しい下書きとして再試行／残存ポストの確定）を明示する。
- premiumの必要残量はXへ送る最終payloadを通常/URL付きへ分類し、要件03 §7.4の式で各枠を別々に判定する。スケジュールenqueue時はパターン別最大数、生成後の投稿直前は実payloadで再判定する。
- 各ポスト成功直後に`tweet_ids`へ保存し、premiumはtweet_idごとに通常投稿枠またはURL付き投稿枠を1消費する。URLが複数あっても1ポストはURL付き枠1消費とする。
- auto起点ではX API呼び出し直前にも自動投稿同意が有効か確認し、停止・同意version変更済みなら投稿せず下書きとして残す。
- スレッド途中失敗は失敗位置から1回だけ再開する。再失敗時は成功済みポストを逆順削除し、`status = failed`にする。
- 投稿成功分は返還しない。ロールバック削除に成功したtweet_idは元投稿と同じ通常/URL付き枠をさらに1消費し、作成と合わせて同じ枠を2消費とする。削除失敗は追加消費しない。
- 削除できなかったtweet_idはエラー詳細と通知に残し、X上での手動確認を促す。
- 投稿APIの結果が不明で直近投稿から一意に照合できない場合は自動再送せず、`投稿状況をXで確認`として本文、時刻、対象アカウントを表示する。
- failed下書きに未解決のtweet_idまたは作成成否がある間は破棄を禁止し、「Xと再照合」を表示する。再照合後も判定不能ならXへのリンクとサポート連絡先を残す。
- tweet_idを1件以上作成したfailed下書きは直接再投稿しない。全IDの削除・不存在が確認できた後だけ「新しい下書きとして再試行」を表示し、本文等を複製した新draftから投稿する。元draftのtweet_idsと失敗記録は監査用に保持する。

## 8. 投稿実績

- 履歴（SC-07 履歴タブ）は表で示す。列は**投稿日時・型・実行（自動／手動）・内容・形式（単発／スレッド数）・ステータス**。
- 履歴（SC-07 履歴タブ）の「内容」列は**全文をそのまま出す**（折りたたまない・切らない）。スレッドはポスト番号を添えて並べる。この列に求められているのは「何を投稿したか」そのものなので、Xへのリンクは置かない（投稿を開く導線は状態列に1つ）。
- 分析（SC-09）の各投稿には**履歴へのリンクを置かない**。同じ画面の表に各ポストの本文と実績が並ぶため、同じ内容を別画面で開き直す必要が無い。

- `tweet_ids`の各IDを1行として表示し、選択checkpointのimpressions、likes、reposts、profile_clicks、取得日時を示す。既定は**その時点の実績を持つ合算対象ポストが最も多いcheckpoint**（同数なら長い方。1件も無ければ1日）とする。全draft横断で「取得済みの最長」を採ると、古い1件が30日を持つだけで直近の投稿がすべて未取得の表に見えてしまうため。
- 各行はtweet_idの生値ではなく**本文冒頭**で識別し、X上のポストへリンクする（スレッドは`1/3`のように通し番号を添える）。draftカードにも本文冒頭とSC-07履歴への deep-link（`?tab=history&draftId=`）を置く。本文は`tweet_ids`と同順の`thread`から対応付ける。
- 1日/7日/30日のcheckpoint切替を用意する。スレッド合算は同じcheckpointを取得済みの各tweet_idだけで表示時に計算し、別カラムへ重複保存しない。欠損ID数を併記する。
- profile_clicksは所有ポストへのuser context取得が可能な期間だけ表示し、取得不能は`0`ではなく`--`とする。
- 画面表示に内部用語（`checkpoint`・`tweet_id`・`Imp`・画面ID）を使わず、「実績を見る時点」「投稿後1日/7日/30日」「表示回数（インプレッション）」「プロフィール表示」「計測日時」「計測完了」と表記する。まだその時点を計測していないセル・集計は「未取得」と文字で示し、取得不能の`--`と区別する。**`--`が0件ではない旨の説明は、時点切替の行に1回だけ置く**（以前は投稿カードごとに繰り返し、投稿数と同じ回数表示されていた・T-M8-66）。各カードの注記は「未計測なら記録開始時期」「部分計測なら合算した件数の割合」だけとし、全件計測済みなら出さない。
- 投稿後1日・7日・30日に実績を更新する。30日checkpoint後は最終取得値を保持し、更新終了をUIに表示する。
- 部分失敗でX上に残ったtweet_idも1行ずつ実績を収集・表示し、「不完全なthread」と明示する。rollback削除済みIDは監査履歴には表示するが実績集計から除外する。
- 実績一覧はactive Xアカウントの直近90日（30日checkpoint回収期間＋余裕）に投稿された`posted`と、`remaining_tweet_ids`を持つ`failed`のdraftを新しい順に表示する。同じ集計を期間（日数）指定でcheckpoint別合計（tweets/impressions/likes/reposts/profile_clicks）にまとめたものは、SC-01の「直近の実績」（7日）が使う。いずれもServer Componentからの読取でServer Actionは置かず、別カラムにも保存しない（要件05 §9）。
- フォロワー推移はSC-09内の1セクションとし、`follower_snapshots`の日次値を期間切替（7日/30日/90日）で折れ線表示する。欠損日は点を作らず実日付でx配置してスキップ（gap）を表す。未収集期間は空状態（フォロワー数は毎日自動で記録され、連携直後は次の毎時起動で最初の点が付く旨）を表示する。記録は毎時cron（契約が有効な利用者のみ・T-M8-257）の1入口だけ（「分析を開始」ボタンからの記録はT-M8-403で廃止）で、X APIは履歴を提供しないため記録が無い日は欠測（gap）のまま埋めない。外部ライブラリを増やさずinline SVGで描画し、色以外の状態表現（点マーカー・数値サマリ・データ表併記）でアクセシビリティを確保する。
- 通知から `?draftId=` 付きで開いたとき、**その下書きが開いたタブに無ければ行き先を出す**（T-M8-115）。投稿されて履歴へ移っていれば「履歴に移っています」＋履歴へのリンク、破棄・別アカウントなら「見つかりませんでした」。**黙って通常の一覧を出さない**——通知を押すのは数時間〜数日あとで、対象が残っていないことが普通に起きるため。
- 分析レポートはSC-09内の1セクション（表示のみ。生成の起点は**分析レポート欄の右上の「分析を開始」ボタン**・T-M8-255。ページヘッダに置くとフォロワー推移にも掛かる操作に見えるため、対象であるレポート欄の中に置く（運営者の指示 2026-08-23）。2026-08-15〜08-23の毎朝8:00 JST自動生成は廃止した）。ボタンは分析jobの起票だけを行い（要件05 §9。フォロワー数の記録は毎時cronだけ・T-M8-403）、結果は成功・失敗ともトーストで返す。実行中（queued/running）はボタンを「分析中…」で無効化し、レポート欄にも「分析中…」バッジを出す。完了後は最終更新日時を出す。説明文は「「分析を開始」を押すと、Xへ投稿したポスト（このアプリで作った投稿に限りません）の直近7日分を取得・分析します」。表示内容は**番号付きの3段**（T-M8-114）: ①まとめ（content＝良かった投稿の特徴）②良かった投稿（**投稿の本文冒頭・表示回数/いいね/リポスト/返信・投稿日時・型/テーマのバッジをその場に出し**、右上に「Xで開く」ボタンを置く。開かずに何の投稿か分かるようにする。保存済みタイムラインに無い投稿は本文を出さずリンクと理由だけにする）③良かった投稿に近づくプロンプト設定（見出し文言は運営者の指示 2026-08-22。推奨の型・テーマ・画像有無。**画面表記**（パターン名・`postThemeLabel`）で示し、内部キー（p3/ai等）は出さない。2026-08-18 以降はPT-SUGGESTがパターン名を返し、それ以前のレポートに残る内部IDだけ`legacyPatternLabel`で当時の名前へ直す）④**2つの編集提案**（T-M8-106）: (a)アカウント.mdへの編集提案（理由＋全文・コピー＋設定＞プロンプト＞アカウント.mdへのリンク。現行md未作成のアカウントでは出ない）(b)投稿作成プロンプト（そのまま貼れる形・コピー＋設定＞プロンプトへのリンク）。全文とコピーは全プランに出す（T-M8-168で旧standardの出し分けを撤廃。未契約は対象外）。承認・却下・自動反映の操作は持たない。**AIが書いた本文（総評・良かった理由・推奨の理由）は日本語へ直してから出す**（T-M8-114・`humanizeReportText`）: 渡したデータの項目名（`impressions`・`likes`等）と型の内部ID（`p1`。2026-08-18 より前のレポート）をAIがそのまま書き写すため、「表示41回」「ニュース解説」へ置き換え、本文に紛れた投稿ID（17〜20桁）は「ある投稿」に言い換える。**貼り付けて使う成果物（アカウント.md改訂案・生成プロンプトの全文）には掛けない**（利用者が保存する内容を書き換えないため）。プロンプト側（PT-SUGGEST）でも日本語で書くよう指示するが、守られない前提で画面側を最後の関門にする。旧形式（軸ベース・evidence.formatなし）の行は総評と根拠1文だけの縮退表示にする（次回の実行で置き換わる）。**SC-09の並びは 分析レポート → 投稿ごとの実績 → フォロワー数の推移**（2026-08-15・運営者の指示。レポートがこの画面の主目的で、フォロワー推移は補助情報のため最後）。ページh1・ナビは「投稿分析」。

## 9. アカウント設定の補足

- SC-11のタブURLは`/app/settings?tab=<slug>`とし、課金は`billing`、問い合わせは`support`をcanonical slugとする。未契約（`incomplete`／`incomplete_expired`）でもこの2タブだけはroute guardを通過できる。
- 問い合わせはMVPでは`matsubuz.10@gmail.com`（`SUPPORT_EMAIL`）へのメールリンクとし、専用問い合わせテーブル・フォームは作らない。
- セルフサービスのアカウント削除機能はMVP対象外とし、SC-11に削除ボタン、削除API、削除進捗を置かない。法令上必要な開示、訂正、利用停止、消去等の請求は`SUPPORT_EMAIL`で受け付け、本人確認と法務確認のうえ運営が個別対応する。
- X切断時はtoken revokeをbest effortで実行後、保存tokenをnull、statusを`disabled`にし、自動投稿も停止して全auto slotを無効化する。下書き・履歴等のデータは削除しない。
- プラン変更でdisabledになったXアカウントは、件数上限に空きがあればSC-11から再有効化できる。tokenまたはOAuth App種別が無効なら再連携を要求する。
- アカウント.md/プロンプト編集タブは全プランで更新可能（T-M8-168）。システム共通promptは編集対象にしない。
- **プロンプト画面（`/app/prompts`）の3区分は同じ形で扱う**（T-M8-332・運営者の指示 2026-08-27）。**アカウント.mdと画像生成プロンプトも複数持てる**（投稿作成プロンプト＝パターンは以前から複数持てた）。正本は要件02 §3.29 `prompt_presets`。
  - 各区分は「説明＋件数＋再読み込み」の1行→カードの一覧（2カラム）→**一覧の最後の「追加」パネル**という同じ並びにする。カードの中身も名前→本文（右上に字数）→操作ボタンで揃える。共通部品は `components/prompt/prompt-list-parts.tsx`。区分ごとに操作を探し直させない。
  - **使用中は区分ごとに1件**。カードに「使用中」「控え」のバッジを出し、切り替えは「使用中にする」で行う。**追加しただけでは切り替わらない**（押した覚えのない切り替えを起こさない）。**使用中は削除できない**（先に別のものを使用中にする）。
  - 使用中の内容は生成が読む置き場へ同じtxで写す（アカウント.md→`x_accounts.base_md`／画像→`prompt_templates`）。アカウント.mdの切り替え・保存は**版として履歴に残る**ので、切り替える前へいつでも戻せる。学習の反映中は保存できない（理由を表示）。
  - **持てる件数の上限**（T-M8-350・運営者の指示 2026-08-28）: アカウント.md **5件**／投稿作成プロンプト **20件**（既定6件を含む）／画像生成プロンプト **5件**。数えるのは**Xアカウント1件あたり**（プロンプトはXアカウントに紐づくため、ここ以外に数えられる単位が無い）。**残数は「n / 上限件」で一覧の先頭に出し**、上限に達したら「追加」を無効化して理由を添える。サーバー側でも検証する（画面だけの制限は迂回できる）。
  - **アカウント.mdはアカウント設定が未保存でも作れる**（T-M8-350）。1本目はアカウント設定の保存で自動的に作られるが、そこで画面を止めない——自由入力で足せることを案内し、新規作成の本文には**6見出しだけの雛形**を入れる（白紙から書かせると「保存できない理由が見出しの形」という、書いてみるまで分からない失敗になる）。
- 生成時は常に現行base_mdを正とする。手動編集したセクション1〜4は、次にアカウント設定フォームを保存するとフォーム値で上書きされるため、保存前に差分警告を表示する。
- 学習ソース削除中は対象アカウントの生成操作を一時停止し、アカウント.md更新後に再開する。削除失敗時はソースを元に戻して再試行を表示する。
- 学習ソースの分析が失敗した状態では、失敗と分かる表示に加えて**次の操作**を示す。参考アカウント／参考投稿は削除して再登録する。
