### 1.1 SC-04 プラン選択

- 認証済みユーザーへStandard／MD／Premiumをカード形式で比較表示し、税込月額、Xアカウント上限、BYOK要否を示す。Standard／MDはX API・生成AI APIの利用料がSpace AI月額とは別に各提供元から請求されることを、カード内と画面末尾の両方へ明示する。
- PremiumはAPIキー不要であることと、通常投稿200件、URL付き投稿20件、文章生成100回、画像生成20枚の月間枠を表示する。
- プランボタンより前に、税込月額、初回だけの7日trial、開始時のカード登録、trial後の月次自動更新、初回／毎月の支払時期、Customer Portalからの期間末解約、Checkout後の提供開始時期を再掲する。
- プラン選択は`plan`だけを`POST /api/stripe/checkout`へ送り、成功時のHTTPS URLへ遷移する。送信中はボタンを無効化し、API・通信・不正URL時は画面内エラーを表示して同画面で再試行できる。
- `checkout=canceled`は未完了として再選択を案内する。Checkout successは復帰handlerで未反映時だけ同期した後、`checkout=success&sync=...`として契約情報確認中を表示する。契約の確定表示はprofileを正とし、通常表示ではStripe APIを呼ばない。
- `/legal/commercial-transactions`への新規タブリンクを申込条件に置く。正式な法務3ページと全体footerはT-M6-14／15で仕上げるまで、同routeに法務確認前の暫定版であることを明示する。

### 1.2 SC-11 課金・問い合わせ（M1最小実装）

- `/app/settings?tab=billing`はprofileの現在プラン、`subscription_status`、JSTの`current_period_end`、`cancel_at_period_end`を表示する。Customerがあれば「お支払い方法・プランを管理」から`POST /api/stripe/portal`を呼び、返されたHTTPS URLへ遷移する。Customer未作成時はボタンを無効化し、`/plans`導線を表示する。
- Portalは`/api/stripe/return?source=portal`へ戻り、復帰handlerで未反映時だけ同期してから`portal=return&sync=...`を付ける。画面は「契約情報を確認しています」と表示し、表示値はprofileを正とする。通常表示ではStripeへ問い合わせない（要件03 §3）。
- `/app/settings?tab=support`は`SUPPORT_EMAIL`への`mailto:`リンクを表示する。未契約ユーザーも課金・問い合わせの2タブへ到達できる。Xアカウントタブは§1.2.1、通知・プロフィールタブは§1.2.2（ともにM2で追加）。

### 1.2.1 SC-11 Xアカウントタブ（M2）

- `/app/settings?tab=x-accounts`は連携済みXアカウントを一覧し、各行に`handle`・表示名・`status`（有効／要再連携／停止中／エラー）・`auth_type`（BYOK＝自分のApp／運営App＝Premium）と、現在操作中アカウントの目印を表示する。
- 「Xアカウントを追加」はOAuth開始（`GET /api/x/oauth/start`）へ遷移する。有効アカウント数がプラン上限に達しているときはボタンを無効化し、`有効 N / 上限` 件を表示する。
- `expired`／`error`には再連携導線、`disabled`には再有効化（`enableXAccount`）と再連携を出す。各行から状態更新（`refreshXAccountStatus`）もできる。
- 切断（`disconnectXAccount`）は確認ダイアログを挟み、投稿と自動実行の停止・自動投稿同意の取り消しを説明し、下書き・投稿履歴・実績・ベースmd等のデータは削除しないことを明示する。
- OAuthからの復帰は`x_connected=1`で成功、`x_oauth_error=<code>`でエラーを表示する。操作の成功後は表示中の一覧を再取得する。

### 1.2.2 SC-11 通知・プロフィールタブ（M2）

- `/app/settings?tab=notifications`は表示名（`updateProfile`）、通知の種別×channel（`updateNotificationConfig`）、ニュース設定（`updateNewsConfig`）を編集する。
- 通知は6種別（ニュース・下書き作成・投稿完了・エラー・課金・利用枠）ごとにアプリ内／メールのON/OFFを切り替える。
- ニュース設定は分野・インパクトを各1件以上、表示件数を1〜100で保存する（要件02 §4.2）。ニュース欄には、JST 9:00〜20:00の取得時刻ごとに最大1件へ集約され、条件一致の新着が0件の時刻には届かないことを明示する（要件06 §3.4）。
- 未設定・不正な`notification_config`／`news_config`は§3.4の既定値へフォールバックして表示する。

### 1.3 重大改定の再同意

- `/app/consent`は画面IDを持たない認証必須の補助画面とし、現行versionと不一致の文書だけを表示する。利用規約への「同意」とプライバシーポリシーの「確認」は別checkboxとし、文書リンクは新規タブで開く。
- 未チェック、画面表示後のversion更新、保存失敗は画面内errorとして留まり、profileを更新しない。同意成功後は`/app`へ戻り、両文書が現行なら同routeへの直接アクセスも`/app`へredirectする。
- 古いversionでもApp Shell、下書き、投稿履歴、分析、設定は閲覧できる。生成・投稿・自動実行の開始時だけ共通実行ガードがこの画面へ誘導する。

## 2. 共通App Shell

- PCは左ナビ、モバイルは下部ナビまたはドロワーを使用する。ナビ項目はホーム、ニュース、投稿、スケジュール、分析、AI設定の6つ。
- ヘッダーにアクティブXアカウント、通知、アカウント設定を置く。Xアカウント切替後は各画面の一覧・集計を再取得する。
- 決済停止、X連携失効、BYOKキー無効はヘッダー直下の常設バナーで表示し、解決画面へリンクする。
- M2のApp ShellはPC幅で固定左ナビ、モバイル幅で固定下部ナビを表示し、SC-05〜10の6 routeへ遷移する。ヘッダーには現在のactive Xアカウント表示枠、通知ベル、SC-11導線を置く。各操作は最低40pxの操作領域と`focus-visible`を持つ。後続機能の実装前は各routeへ共通の空状態を表示し、App配下の読込状態とerror boundaryの再試行状態を共通部品化する。
- M1で先行した契約バナーはApp Shell内へ維持する。`past_due`／`unpaid`／`paused`は既存データを覆わず、生成・投稿・自動実行の停止理由とCustomer Portalボタンを表示する。Customer未作成時と`canceled`は`/plans`へ誘導する。通知設定がOFFでも非表示にしない。`trialing`はJSTのtrial終了日を表示し、`active`では課金バナーを表示しない。
- BYOKとプレミアムをまたぐプラン変更後は、Developer Appが変わるためXの再連携を常設バナーで要求する。再連携まで生成結果の閲覧・編集は許可し、投稿と自動実行は停止する。
- モバイルで必須とする操作は、下書き全文確認、本文編集、投稿、破棄、通知確認。複雑なプロンプト編集は閲覧可能とし、編集はPC推奨表示にできる。
- 読み込み中、空、失敗、権限不足、上限到達の各状態を画面単位で用意する。エラーは再試行可否と解決先を併記する。

## 3. 初期設定と実行前提

専用のオンボーディングウィザード・進捗保存は持たない。初期設定は設定画面で任意の順に行い、前提条件は各操作の実行時にサーバー側で検証する。

### 3.1 共通方針

- 初期設定はSC-10（AI設定）とSC-11（アカウント設定）の各タブで行う。専用画面・専用フローは作らない。
- 生成・投稿・スケジュール・学習の各操作は、実行時にServer Actionが前提条件をDBと外部接続状態で検証する。不足時は実行せず、エラーコード・不足項目・設定画面への遷移先を返し、画面はエラーメッセージと「設定へ」ボタンを表示する。
- 前提条件が不足している間、ホーム（SC-05）に「初期設定ガイド」カードを表示する。不足項目（X APIキー／X連携／文章AIキー／発信設定）をチェックリストで示し、各項目から該当設定画面へ遷移できる。全条件充足で自動的に非表示になる。
- 学習ソース登録は任意。参考アカウントは最大3件（各直近20ポスト）、参考投稿は最大10件、自分の過去投稿は直近100件を対象とする。
- ベースmdはL-4〜L-7フォームの初回保存時にテンプレートから初版を機械生成する（`base_md_version` 0 → 1。セクション5〜6は空欄で開始し、学習ソースの分析結果で追記される）。

### 3.2 実行前提（プラン別）

生成・投稿系の操作は次の前提をすべて満たす場合だけ実行できる。

| 前提 | BYOK（standard/md） | premium | 不足時のエラー |
|---|---|---|---|
| 現行規約 | 利用規約同意・privacy確認済み | 同左 | `legal_consent_required` |
| 契約 | `subscription_status`が`trialing`/`active` | 同左 | `subscription_required` |
| X APIキー | 登録・形式検証済み | 不要 | `api_key_required` |
| X連携 | `x_accounts.status = active` | 同左（運営App経由） | `x_account_required` |
| 文章AIキー | `text` providerのキーが`valid` | 不要（運営Claude） | `api_key_required` |
| 画像AIキー | 画像ON時のみOpenAI/Googleのキーが`valid` | 不要（運営キー。未設定providerは選択不可） | `api_key_required` |
| 発信設定 | L-4〜L-7の必須項目保存済み（`base_md_version >= 1`） | 同左 | `persona_required` |

エラーの`details`には不足項目の一覧と設定画面のパスを含める（要件05 §2.2）。

X APIキー登録画面（SC-11の`api-keys`タブ）には、XとAnthropic／OpenAI／Googleの登録・差し替え・疎通確認・即時削除を置く。秘密値入力はpassword controlとし、保存後に入力を空へ戻して、Client ID／APIキーの末尾4文字、Client種別、検証状態、最終確認時刻だけを表示する。Developer Consoleで登録する`APP_BASE_URL + X_OAUTH_REDIRECT_PATH`のcallback URL、必要scope 5種、credits・自動チャージ・spending limitの確認先をテキスト手順と差し替え可能な画像枠で表示する。premiumではキー入力フォーム自体を表示せず、ユーザーのX Developer App資格情報・AI APIキーが不要なことを案内する。文章生成・リサーチproviderは運営設定のClaude（SC-10でread-only表示）、画像providerはOpenAI/Geminiのうち運営キーが利用可能なものから選べる。

### 3.3 発信設定の必須項目

| 要件 | 必須項目 |
|---|---|
| L-4 ペルソナ | 発信者、対象読者、提供価値 |
| L-5 テーマ | 主テーマを1件以上。副テーマ・自由入力は任意 |
| L-6 トーン | 文末、一人称、絵文字方針、ハッシュタグ上限、スレッド番号方針 |
| L-7 NG | NGワード・トピック・自由ルールはいずれも空で可。既定の安全ルールは常に適用 |

### 3.4 初期値

- `notification_config`: アプリ内は全種別ON。メールはニュースの時間単位ダイジェスト、下書き、エラー、課金、利用枠をON、投稿完了をOFF。
- `news_config`: 6分野すべて、インパクト高・中、20件表示。
- `tone`: です・ます調、絵文字は1ポスト1個まで、ハッシュタグ0件、スレッド番号あり。
- スケジュールは初期作成しない。ユーザーが明示的に作成するまで自動生成・自動投稿は行わない。

ニュース通知設定には、ニュースがJST 9:00〜20:00の取得時刻ごとに最大1件へ集約され、設定条件に一致する新着が0件なら届かないことを表示する。SC-06の一覧は既定で過去7日分（`news_items`をpublished_at基準で表示。保持は40日・要件01 §9）を表示し、`news_config`の分野・インパクト・表示件数で絞り込む。通知から遷移した場合は対象時間窓を適用し、ダイジェスト掲載外を含む該当ニュースを一覧できるようにする。

### 3.5 自動投稿への同意

- X OAuth画面でscopeを認可しただけでは、自動投稿への同意完了と表示しない。
- SC-08で初めて「そのまま投稿」を選んだとき、自動生成された内容が指定時刻に確認なしでXへ投稿されること、thread途中失敗時は作成済みポストを自動削除し削除後は復元できないこと、投稿内容の責任、停止方法をmodalで説明する。説明文versionと独立した明示checkboxを表示し、同意後だけauto slotを保存できる。
- SC-08とSC-11に「自動投稿をすべて停止」を置く。実行時は当該Xアカウントのauto slotを即時無効化し、未投稿のauto jobも停止する。下書きまでのslotと手動投稿は継続できる。
- 自動投稿の目的または対象操作を大きく変更した場合は説明文versionを更新し、既存auto slotを停止して再同意を求める。

### 3.6 SC-10 発信設定フォーム

- `/app/ai-settings`は`persona`（発信設定）を既定タブとし、`purposes`（AI用途・§3.6）、`learning`（学習ソース・§9）、`base-md`（§3.7）、`prompts`（§3.8）のタブを持つ。Xアカウント未連携時は各タブで共通の空状態（Xアカウント設定への導線）を表示する。
- 発信設定はactive Xアカウント単位でL-4〜L-7を編集する。ペルソナ3項目と主テーマは必須、テーマはマスタ選択と自由入力、toneは§3.4の初期値、NG 3分類は改行区切り入力で空を許可する。入力エラーは該当labelと関連付けて表示する。
- `base_md_version >= 1`で現行mdのセクション1〜4が保存settingsと異なる場合、またはフォームを編集した場合は、保存前に「1〜4を上書きし5〜6は保持する」と明示する。保存成功時はActionが返したversionを即時表示し、Server Componentも再取得する。
- `purposes`はXアカウント未連携でもprofile単位で編集できる。standard／mdの文章providerには`valid`なAnthropic／OpenAI／Googleだけ、画像providerにはそのうちOpenAI／Googleだけを表示する。Premiumの文章providerは「運営Claude（変更不可）」とread-only表示し、画像providerは運営キーが存在するOpenAI／Googleだけを表示する。選択肢がない場合は画像生成OFFを明示し、BYOKではAPIキー設定への導線を表示する。

### 3.7 SC-10 ベースmdエディタ

- `base-md`タブはactive Xアカウントの現行base_mdをテキスト編集する。文字数カウンタ（5,000字上限）を表示し、`updateBaseMdManual`（現行versionを`expected_version`として送る）で保存する。保存成功はActionが返したversionを即時表示し、Server Componentも再取得する。
- エラーは種別ごとに表示する。6見出し構造違反・字数超過は保存前提の入力エラー、version競合（409）は「別の場所で更新された」旨と再読み込み導線、学習ジョブrunning中は編集不可表示にする。
- 変更履歴（version・change_source・summary・日時）を新しい順で一覧表示し、各版から確認ダイアログを挟んで`rollbackBaseMd`（指定版の内容で新versionを作成）を実行できる。
- standardプランではタブ内容をロック表示にし、プラン変更（`/plans`）への導線を出す。`base_md_version = 0`（初版未生成）は発信設定タブへ誘導する。
- 手動編集したセクション1〜4は発信設定フォーム保存で上書きされる旨を常時注意表示する。ベースmd編集はPCでの操作を推奨し、モバイルでは閲覧を主とする。

### 3.8 SC-10 プロンプトエディタ

- `prompts`タブはactive Xアカウントの生成プロンプト（`p1`〜`p4`／`p6`／`image`）をkind選択して編集する。`p5`（引用ポスト）は`FEATURE_QUOTE_POST_ENABLED=false`の間は選択肢に表示しない。
- 各kindに上書き有無（既定/カスタム）のバッジと文字数カウンタ（8,000字上限）を表示する。「保存」（`updatePromptTemplate`。listが返した`updated_at`を`expected_updated_at`として送る）と「システム既定に戻す」（`resetPromptTemplate`。確認ダイアログを挟む）を操作でき、リセットは上書きがある場合のみ有効にする。
- 楽観lock競合（409）は「別の場所で更新された」旨と再読み込み導線を出す。空文字・字数超過は保存前の入力エラーとして表示する。
- standardプランではタブ内容をロック表示にし、プラン変更（`/plans`）への導線を出す。システム共通プロンプト（SYS-GEN・文字数調整等）は編集対象にしない旨を明示する。プロンプト編集はPCでの操作を推奨し、モバイルでは閲覧を主とする。

## 4. 投稿作成

### 4.1 パターンと最大ポスト数

| パターン | 用途 | ポスト数 | 必須入力 |
|---|---|---:|---|
| P-1 | ニュース解説 | 4〜6 | なし |
| P-2 | 自分の考え・意見 | 1 | なし |
| P-3 | ノウハウ・ハウツー | 4〜7 | なし |
| P-4 | トレンド便乗 | 3〜5 | なし |
| P-5 | 引用ポスト | 1〜3 | 引用対象X URL（初期OFF） |
| P-6 | 週次まとめ | 5〜7 | なし |

P-7画像生成は独立した投稿パターンではなく、P-1〜P-6に付与するオプションとして扱う。

P-5は将来の有効化後に全プランで手動生成できる。`FEATURE_QUOTE_POST_ENABLED=false`の間はパターン選択肢と新規生成導線を非表示にする。過去のP-5 draftが存在する場合は本文と対象URLを閲覧可とするが、再生成・画像再生成・投稿ボタンを無効化し「引用ポスト機能は現在利用できません」と表示する。有効化後はネイティブ引用ではなく、1ポスト目へ対象X URLを付ける通常投稿としてプレビューし、「URL付き投稿枠を使用」と表示する。

### 4.2 生成入力

- 共通入力は参考URL、追加指示、画像生成ON/OFF、画像provider。
- P-2のみ「自分の考え」、P-5のみ引用対象URLを追加表示する。
- 任意入力が空でも生成可能。ただしP-5の引用対象URLだけは必須。
- ニュース起点生成は`news_item_id`と`source_url`を引き継ぎ、P-1を初期選択する。
- 生成開始後は画面を離れてよい。`generation_jobs`の状態を再訪時に復元する。
- jobが`queued`のまま60秒を超えた場合は「開始が遅れています。自動で再開されます（最大5分）」と進行中扱いで表示する（dispatch失敗は次の`scheduler_tick`が回収する）。`failed`になった場合のみ原因と再試行導線を表示する。

### 4.3 下書き編集

- ポスト本文の編集、並べ替え、追加、削除を許可する。編集後は1件以上かつP-1=6、P-2=1、P-3=7、P-4=5、P-5=3、P-6=7のpattern別最大数以内に収める。
- 追加指示付き再生成は元下書きを保持して派生下書きを作る。派生元へのリンクを表示し、ユーザーが採用しない版を破棄できる。
- 生成確定時の本文を`initial_thread`へ保存し、その後の編集では更新しない。`source_job_id`を持つ生成draftが投稿された場合だけ最終本文との差分率を算出し、成功指標の下書き承認率へ使用する。正規化と編集距離の定義は[データモデル §4.7](./02_data_model.md#47-draftsthread)を正とし、AIを使わない失敗draftの複製は集計対象外とする。
- 各ポストは公式`twitter-text`互換の加重文字数で検証する。URLはt.co換算、CJK・絵文字等の重みを含む。
- 文字数超過、NGワード、出典不足、引用対象不明、画像失敗はポストまたは下書き単位の警告として表示する。
- 自動投稿を阻害する警告がある下書きは手動確認へ切り替え、ユーザーが修正するまで投稿しない。
- 投稿成功時は下書きを物理削除せず`status = posted`へ変更する。未投稿の「下書き」タブからは消え、「投稿履歴」タブへ移る。
- `status = posted`の本文・順序・引用対象は編集不可。tweet_ids別実績と監査に必要な履歴として表示する。

## 5. 引用ポスト

- `x.com`または`twitter.com`の投稿URLから数値IDを抽出し、`quote_url`と`quote_tweet_id`の両方をdraftへ保存する。
- 生成前に対象ポストを取得し、取得不能・削除済み・アクセス不能の場合はジョブを失敗させる。
- `quote_url`は本文編集欄と分けて固定表示し、1ポスト目の送信payloadでは本文末尾へ改行付きで合成する。合成後の加重文字数を表示し、URL部分だけを削除する編集は許可しない。
- 投稿時は1ポスト目を対象URL付きの通常投稿として送り、`quote_tweet_id`をAPIへ指定しない。2ポスト目以降は直前の自分のtweet_idへのreplyとする。
- 引用対象URLの差し替えは`status = draft`の間だけ許可し、差し替え時に対象を再取得する。

## 6. 画像生成・添付

- MVPは生成画像1枚をスレッドの1ポスト目に添付する。
- 生成画像はJPG/PNG/WEBP、5MB以下に正規化し、private Storageへ保存する。下書き画面では表示時に生成する短時間の署名URL（DBへ永続化しない・要件02 §4.8）で添付画像を表示する。
- 画像プロバイダのAPIキーが未登録（BYOKでopenai/googleがともに未登録）の場合は画像再生成操作を非活性にする（PRD §8.2）。
- X投稿直前に`POST /2/media/upload`でmedia idを取得し、1ポスト目の`POST /2/tweets`へ指定する。
- 画像生成またはStorage保存に失敗した場合は、本文を画像なし下書きとして保存し警告する。自動投稿スロットも本文のみで投稿してよい。
- Xへのmedia uploadに失敗した場合は本文を投稿せず、下書きを`failed`にして再試行可能にする。
- 画像アップロードAPIの費用はサービス内利用枠・原価試算に含めない。画像枠は画像生成ジョブ開始時だけカウントする。
- 画像再生成中は既存画像を表示し、新画像の保存成功後に置き換える。下書き破棄時はそのdraft専用pathの生成画像をStorageからbest effortで削除するが、消費済み画像枠は返還しない。失敗draftを複製する場合は画像objectも新draft用pathへcopyし、draft間で同じobjectを共有しない。

## 7. 投稿実行と部分失敗

- 手動投稿の最終確認と自動投稿の同意文には、thread途中失敗時に作成済みポストを自動削除することと、削除後はX上で復元できないことを明示する。
- 手動投稿は`status=draft`（または未解決の投稿状態がない retryable `failed`）のみ許可する。投稿開始後は下書きの編集・破棄・再生成・再投稿操作を無効化し「投稿中…」を表示する。投稿完了で履歴タブへ移る。投稿の前提はAI生成と異なり課金・Xキー・X連携のみで、文章/画像AIキー・発信設定は不要。
- 投稿前に、課金状態、X連携、文字数、警告、premiumの通常投稿枠・URL付き投稿枠残量を再検証する。
- premiumの必要残量はXへ送る最終payloadを通常/URL付きへ分類し、要件03 §7.4の式で各枠を別々に判定する。スケジュールenqueue時はパターン別最大数、生成後の投稿直前は実payloadで再判定する。
- 各ポスト成功直後に`tweet_ids`へ保存し、premiumはtweet_idごとに通常投稿枠またはURL付き投稿枠を1消費する。URLが複数あっても1ポストはURL付き枠1消費とする。
- auto起点ではX API呼び出し直前にも自動投稿同意が有効か確認し、停止・同意version変更済みなら投稿せず下書きとして残す。
- スレッド途中失敗は失敗位置から1回だけ再開する。再失敗時は成功済みポストを逆順削除し、`status = failed`にする。
- 投稿成功分は返還しない。ロールバック削除に成功したtweet_idは元投稿と同じ通常/URL付き枠をさらに1消費し、作成と合わせて同じ枠を2消費とする。削除失敗は追加消費しない。
- 削除できなかったtweet_idはエラー詳細と通知に残し、X上での手動確認を促す。
- 投稿APIの結果が不明で直近投稿から一意に照合できない場合は自動再送せず、`投稿状況をXで確認`として本文、時刻、対象アカウントを表示する。
- failed下書きに未解決のtweet_idまたは作成成否がある間は破棄を禁止し、「Xと再照合」を表示する。再照合後も判定不能ならXへのリンクとサポート連絡先を残す。
- tweet_idを1件以上作成したfailed下書きは直接再投稿しない。全IDの削除・不存在が確認できた後だけ「新しい下書きとして再試行」を表示し、本文等を複製した新draftから投稿する。元draftのtweet_idsと失敗記録は監査用に保持する。

## 8. 投稿実績

- `tweet_ids`の各IDを1行として表示し、選択checkpointのimpressions、likes、reposts、profile_clicks、取得日時を示す。既定は取得済みの最長checkpointとする。
- 1日/7日/30日のcheckpoint切替を用意する。スレッド合算は同じcheckpointを取得済みの各tweet_idだけで表示時に計算し、別カラムへ重複保存しない。欠損ID数を併記する。
- profile_clicksは所有ポストへのuser context取得が可能な期間だけ表示し、取得不能は`0`ではなく`--`とする。
- 投稿後1日・7日・30日に実績を更新する。30日checkpoint後は最終取得値を保持し、更新終了をUIに表示する。
- 部分失敗でX上に残ったtweet_idも1行ずつ実績を収集・表示し、「不完全なthread」と明示する。rollback削除済みIDは監査履歴には表示するが実績集計から除外する。

## 9. アカウント設定の補足

- SC-11のタブURLは`/app/settings?tab=<slug>`とし、課金は`billing`、問い合わせは`support`をcanonical slugとする。未契約（`incomplete`／`incomplete_expired`）でもこの2タブだけはroute guardを通過できる。
- 問い合わせはMVPでは`matsubuz.10@gmail.com`（`SUPPORT_EMAIL`）へのメールリンクとし、専用問い合わせテーブル・フォームは作らない。
- セルフサービスのアカウント削除機能はMVP対象外とし、SC-11に削除ボタン、削除API、削除進捗を置かない。法令上必要な開示、訂正、利用停止、消去等の請求は`SUPPORT_EMAIL`で受け付け、本人確認と法務確認のうえ運営が個別対応する。
- X切断時はtoken revokeをbest effortで実行後、保存tokenをnull、statusを`disabled`にし、自動投稿も停止して全auto slotを無効化する。下書き・履歴等のデータは削除しない。
- プラン変更でdisabledになったXアカウントは、件数上限に空きがあればSC-11から再有効化できる。tokenまたはOAuth App種別が無効なら再連携を要求する。
- ベースmd/プロンプト編集タブはmd/premiumだけ更新可能。システム共通promptは編集対象にしない。
- 生成時は常に現行base_mdを正とする。手動編集したセクション1〜4は、次に発信設定フォームを保存するとフォーム値で上書きされるため、保存前に差分警告を表示する。
- 学習ソース削除中は対象アカウントの生成操作を一時停止し、ベースmd更新後に再開する。削除失敗時はソースを元に戻して再試行を表示する。
