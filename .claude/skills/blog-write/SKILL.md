# blog-write：テーマを掘って下書きを書く

テーマや参考URL（両方でもよい）を受け取り、**調べて → 固有の学びを1つ決めて → 書く**。成果物は `blog/drafts/<slug>.md` の下書き1本。形式の正本は `blog/README.md`（先に読む）、実例は `blog/published/hello-exos-ai-blog.md`。
**このスキルは公開しない。** `draft: true` のまま保存して終わる。`draft` を外してコミットするのは `/blog-publish`。

## 手順

### 0. 入力を受け取る（無ければ先にヒアリング）

**引数が無い（または曖昧な）ときは、書き始める前に次の2点を1回のメッセージでまとめて聞く**（小出しにしない・T-M8-193）:

1. **テーマ** — 何について書くか（1行でよい）
2. **参照リンク** — 参考にしてほしいURL（任意・複数可・「なし」も可）

回答が来たら下の表に従って進める。引数でテーマやURLが渡されていればヒアリングは飛ばす。

| 入力 | 扱い |
|---|---|
| テーマ（自由文） | 「誰が・何に困っていて・読後に何ができるか」を1行にして範囲を絞る |
| 参考URL（1つ以上） | WebFetch で読み、**事実・数字・主張だけ**を箇条書きにメモする。文章は写さず、見出し構成もなぞらない |
| 読めない・薄い | 読めない（403・JS描画・空）か主張を1つも取れないURLは引用元にしない。**確認は挟まず**報告欄に残してテーマで進める |

`grep -rh "^title:" blog/published blog/drafts` で既存記事の title を一覧し、同じ主張の記事があれば書かずにそのファイルを案内して終わる。

### 1. 掘る（書く前に5つの問いへ箇条書きで答える。応答に出してよい）

| 問い | 答えるべきこと |
|---|---|
| なぜ | その定説が成り立つ**前提**は何か。前提が崩れるのはどんな場面か |
| どうやって | 手順に落とすと何ステップか。どこで詰まるか |
| 反例 | 逆の結果になった例・やめた方法。成功例だけを並べない |
| 数字 | 回数・時間・費用・文字数・反応数。**出典か実測日付き**で書き、無いものは「未計測」と書く（作らない） |
| 自分の運用 | Exos AI で実際にどうしているか。`docs/プロンプト設計書.md`（プロンプトと検証）・`docs/PRD.md`・`tasks/BACKLOG.md`（決定の経緯）・実装を読んで拾う。内部の経緯・未公開機能・費用の内訳は記事に書かない |

答えから**学び（insight）を1文**にする。形は「〜と思われがちだが、実際は〜。理由は〜」。目安は2つ: (1) 実測・反例・条件のどれかに根づいている。(2) 「Exos AI」「自分」を消して他社ブログに貼っても成り立つなら一般論。出てこなければ、不足している実例・数字を**1回にまとめて**運営者に聞く（小出しにしない）。

### 2. 構成する

学びを読者向けの主張1文「○○を△△すると□□になる」にする。これが `description` の元で、`title`・冒頭3行も同じ主張を指す。長さは **1,500〜3,000字**。見出しは `##` を主とし `###` は1段まで。節名はテーマに合わせて変えてよいが、役割と順番は守り、主張に効かない節は削る。

- `## 結論` — 主張と理由を3行以内。最初に書く
- `## なぜそうなるのか` — 前提と仕組み（§1「なぜ」）
- `## 具体例` — 手順・プロンプト・設定値・数字（§1「どうやって」「数字」「自分の運用」）
- `## やらないこと・落とし穴` — 反例と、その条件（§1「反例」）
- `## まとめ` — 持ち帰り1つ＋読者が次にやること1つ

### 3. 書く（文体）

文体は**目安**であって検査ではない（禁止語の機械チェックは無い。2026-08-23に上乗せ分を撤廃）。
守るのは表の1行目——**自社サービスの効果を約束しない**。ここだけは景品表示法の問題になる。

| する | しない |
|---|---|
| 1文1内容。専門用語はその場で言い換える | **Exos AI の効果を約束する**（「必ず伸びる」「フォロワー○倍」「保証」「No.1」）。他社事例や一般論の紹介は制限しない |
| 数字・手順・プロンプト・設定値で具体化する | 具体を書かずに終える |
| 断定には根拠（実測・出典・仕組み）を隣に置く。誤ると読者が損をする話は特に | 根拠のない断定 |
| 参考URLは自分の言葉で要約。引用は `> 引用文 — [出典名](URL)` | 段落単位の転載、個人が特定できる情報 |
| 事実と意見は**語尾で**分ける（「〜と報じられた」「〜による」／「〜と考えている」「〜だと思う」） | 「（意見）」「（事実）」「（筆者の見立て）」のような**注記で分ける**（AIが書いた印象になる。使わない） |
| 太字は約物の外に置く: `は「**配る**」へ`・`**git**（ギット）は` | `は**「配る」**へ`・`**git（ギット）**は`（「」（）が太字の内側にあると太字にならず `**` が画面に残る。§4 の検証で止まる） |

### 4. 保存して検証する

- slug: 主張を表す英小文字3〜5語をハイフンで（例 `posting-time-is-not-the-lever`）。小文字英数字とハイフンのみ・80字以内。日付・連番は入れない
- `blog/drafts/<slug>.md` に保存（**下書きフォルダ**。`blog/` 直下や `published/` に置かない・T-M8-193）。front matter に書けるキーは `title`（80字以内）／`description`（200字以内・1〜2文）／`date`（今日 `date +%F`）／`updated`／`draft: true`／`tags`（既存記事と表記を揃える）／`image`（アイキャッチ。次の手順で生成する）の7つだけ（他は検証で弾かれる）
- 本文は `##` から始める（`#` は書かない）。生HTMLは書かない。画像は `public/blog-images/` に置き `/blog-images/<name>.png` で参照する
- **アイキャッチを作る**: `npm run blog:eyecatch -- <slug>`。1200×630 の PNG（題名・タグ入り）が `public/blog-images/eyecatch/<slug>.png` にでき、front matter へ `image:` が書き足される。**生成した PNG を Read で開き**、日本語が □（豆腐）になっていないか・題名が切れていないかを見る。`title` を変えたら実行し直す
- **図を描く**: 本文に**手順・比較・時系列・構造**の説明があれば図にする（目安は「読者が頭の中で表や矢印を組み立てないと分からない段落」。文章は残してよいが、図が主で文章は補足にする）。作り方:
  1. SVG を `blog/diagrams/<slug>-<name>.svg` に書く。幅 1200、`font-family="Hiragino Sans, Noto Sans JP, sans-serif"`、色はブランドの `#7d1f75`（線・見出し・矢印）と `#f4e8f3`（塗り）を基調に白地。要素は3〜6個に絞り、矢印の向きと順番が一目で分かる形にする。**図は本文幅（約720px）とスマホ（375px）に縮小されて表示される**（0.6倍・0.31倍。SNS運用者はスマホ閲覧が多い）ので、次を守る（読者レビュー 2026-09-05）:
     - **最小の文字は 40px 以上**（日付・補足の小さい文字も。スマホで 12px になる下限。22px だとスマホで約7pxになり読めない。手順2の `blog:diagram` が下回ると止める）
     - **長い説明文は図に入れず本文へ**（1行 20 字まで。時系列は「日付＋タグ」と短文の2段に折り、説明の続きは本文に任せる）。事実を並べる図に「まだ加速」のような意見を混ぜない（意見は深掘りへ）
     - **横に3つ以上並べない**（縦積みか2列まで。横4列は縮小後に1箱が約90pxになる）。手順が多いときは縦に流し、比較は上下に積む
     - 注記に「700px」「幅2px」のような**実寸を書かない**（縮小後の画面では合わなくなる）。「報告の棒はいいねの468倍の長さ」のように比率で書く
  2. `npm run blog:diagram -- blog/diagrams/<slug>-<name>.svg <slug>-<name>.png` で `public/blog-images/<slug>-<name>.png`（2倍密度）にする
  3. 本文へ `![図の説明](/blog-images/<slug>-<name>.png)` で貼る。alt は「図1」ではなく図が伝える内容を1文で書く（読み上げでも意味が通るように）
  4. PNG を Read で開き、豆腐・文字の重なり・はみ出しを確認する。続けて、手順2が出力する**スマホ幅（375px）のプレビュー**（一時ディレクトリ。パスは実行結果に出る）も Read で開き、拡大せずに文字が読めるかを見る。読めなければ縦積みにするか文字を大きくして1からやり直す
- `npm run blog:check -- <slug>.md` を実行し、`📝 <slug>.md  下書き（draft: true）` と末尾の `✅ 不備なし` を確認する。`❌` なら表示された理由を直して再実行。**太字にならない `**`**（「」（）などの約物が太字の内側にある書き方）はここで行番号つきで止まる——約物を太字の外へ出す（`は**「配る」**へ` → `は「**配る**」へ`）

### 5. 自己チェックして報告する（全部 Yes になるまで直す）

**セルフレビューは必ず2周する**（1周で両方を見ようとすると片方が抜ける・運営者の依頼 2026-09-05）:

1. **1周目＝事実と構成**: 下のチェックの前半（学び・結論・具体例・約束・出典・長さ）。数字と出典を1つずつ元に当たり、見出しだけで流れが追えるかを見る
2. **2周目＝読み物として**: 本文を**頭から声に出して読むつもりで**通し、つっかえる文・長すぎる文・意味が2通りに取れる文と、**前提知識が無いと分からない箇所（ハイコンテキスト）**を直す。読者は Exos AI の中身も開発の用語も知らない前提で、初出の用語はその場で言い換える。下の「AIっぽさ」の項目はこの周で見る

- [ ] §1 の学びが本文に**1文で**入っている（読者がその1文だけ覚えて帰れる）
- [ ] 結論が冒頭にあり、見出しだけで流れが追える。`title`・`description`・冒頭3行が同じ主張を指す
- [ ] 具体例（手順・数字・プロンプト・設定値）が1つ以上ある。未計測は未計測と書いてある
- [ ] 自社サービスの効果を約束していない（曖昧語の grep は不要・2026-08-23に撤廃）
- [ ] 誤っていたら読者に損をさせる断定に出典か実測が付き、事実と意見が語尾で分かれている。参考URLの文章を写していない
- [ ] `title` 80字以内・`description` 200字以内・本文 1,500〜3,000字
- [ ] 図にすべき箇所（手順・比較・時系列・構造）を図にし、アイキャッチ（`image`）がある（§4）
- [ ] **AIっぽさを除いた**。次に当てはまる箇所を書き直した:
  - 太字にならない `**` が残っている（`npm run blog:check` で止まる。約物を太字の外へ）
  - 「（意見）」「（事実）」のような注記で事実と意見を分けている → **注記は使わない**。語尾で示す（「〜と考えている」「〜と報じられた」）
  - 「〜することができます」「重要なのは」「まとめると」「言い換えれば」「〜と言えるでしょう」の多用（各1回まで。言い切りに直す）
  - 段落の冒頭で直前の見出しを言い直している（見出しの次の文は本題から始める）
  - 太字が多すぎる（1段落に2つまで。強調が増えるほど何も強調されない）
  - 箇条書きだけで文章の無い節（項目の間の「なぜ」が消える。文章で1つつなぐ）
  - 「——」（ダッシュ）が記事全体で3回以上ある（句点で切るか、括弧に）
  - 読者が知らない内部用語（タスクID・スキル名・ファイル名・機能の内部名・社内の略語）を説明なしに使っている

報告: 作ったファイル（記事・アイキャッチ・図）／記事の主張1行／確認してほしい点（未計測の箇所・運営者しか知らない実例・読めなかったURL）／次に実行するコマンド `/blog-publish <slug>.md`。

## ルール

- **公開しない。** `draft` を外さない。コミットも `git add` もしない。
- 1回で書くのは1記事。テーマが2つあれば分けて、どちらを先にするか聞く。
- 記事・報告は日本語。コードブロック内のプロンプトや設定値は実物のまま載せる。
