# blog-write：テーマを掘って下書きを書く

テーマや参考URLを受け取り、**調べる → 学びを1つ決める → 読者目線で書く → 図とアイキャッチを作る → 2周見直す**。成果物は `blog/drafts/<slug>.md` の下書き1本（形式の正本は `blog/README.md`。先に読む）。
**公開はしない。** `draft: true` のまま終える（公開は `/blog-publish`）。

## 0. 入力

引数が無い・曖昧なら、**テーマ**（1行）と**参照リンク**（任意・複数可・「なし」も可）を1回のメッセージでまとめて聞く。引数で渡されていれば聞かない。

| 入力 | 扱い |
|---|---|
| テーマ | 「誰が・何に困っていて・読後に何ができるか」を1行にして範囲を絞る |
| 参考URL | WebFetch で読み、事実・数字・主張だけを箇条書きにメモする。文章は写さず、見出し構成もなぞらない |
| 読めない（403・JS描画・空）か主張を1つも取れないURL | 引用元にしない。確認は挟まず、報告に残してテーマで進める |

`grep -rh "^title:" blog/published blog/drafts` で既存記事を見て、同じ主張の記事があれば書かずにそのファイルを案内して終わる。

## 1. 掘る（5つの問いに箇条書きで答える。応答に出してよい）

| 問い | 答えるべきこと |
|---|---|
| なぜ | 定説が成り立つ前提。前提が崩れる場面 |
| どうやって | 手順に落とすと何ステップか。どこで詰まるか |
| 反例 | 逆の結果になった例・やめた方法。成功例だけを並べない |
| 数字 | 回数・時間・費用・文字数・反応数。出典か実測日付き。無ければ「未計測」と書く（作らない） |
| 自分の運用 | Exos AI で実際にどうしているか（`docs/プロンプト設計書.md`・`docs/PRD.md`・`tasks/BACKLOG.md`・実装から拾う）。内部の経緯・未公開機能・費用の内訳は書かない |

答えから**学びを1文**にする（「〜と思われがちだが、実際は〜。理由は〜」）。実測・反例・条件のどれかに根づき、「Exos AI」「自分」を消すと成り立たない固有の内容であること。出てこなければ、不足している実例・数字を1回にまとめて運営者に聞く。

## 2. 構成する（読者目線）

学びを読者向けの主張1文「○○を△△すると□□になる」にし、`title`・`description`・冒頭3行が同じ主張を指すようにする。

- **title（80字以内）**: 読者が得る**メリット**が分かる言葉で、読者の目線から書く。目を留める**注目のワード**（具体的な数字・固有名・「無料」「3コマンド」・「〜しても伸びない」型の意外性）を1つ入れる。数字は実測か出典のあるものだけで、効果の約束になる数字・語は §3 の禁止に従う。運営者の作業名（「〜を実装」「〜の改善」）や内向きの語は使わない。例: 「投稿の時間帯は本当に効くのか」→「投稿時間を変えても伸びない人が、先に直す1つのこと」
- **description（200字以内・1〜2文）**: 主張と、読後にできることを1文ずつ
- **本文（1,500〜3,000字が目安。運営者が長さを指定したらそれに従う）**: `##` 主体、`###` は1段まで。節名はテーマに合わせて変えてよいが、役割と順番は守り、主張に効かない節は削る
  - `## 結論` — 最初に書く。**記事の要約**で、主張・理由・読者が次にすることがこの節だけで分かる（3〜6行。要素が多ければ表にし、表は行数に数えない）
  - `## なぜそうなるのか` — 前提と仕組み
  - `## 具体例` — 手順・プロンプト・設定値・数字
  - `## やらないこと・落とし穴` — 反例と、その条件
  - `## まとめ` — 持ち帰り1つ＋次にやること1つ

## 3. 書く

読者目線で、**具体的・分かりやすく・簡潔・構造的**に。文体は目安であって検査ではない（禁止語の機械チェックは足さない）。守るのは表の1行目（景品表示法）。

| する | しない |
|---|---|
| 1文1内容。専門用語は初出でその場で言い換える（読者は Exos AI の中身も開発用語も知らない） | **Exos AI の効果を約束する**（「必ず伸びる」「フォロワー○倍」「保証」「No.1」）。他社事例・一般論の紹介は制限しない |
| 数字・手順・プロンプト・設定値で具体化する | 具体を書かずに終える。同じことを2か所で言う |
| 断定には根拠（実測・出典・仕組み）を隣に置く。誤ると読者が損をする話は特に | 根拠のない断定 |
| 段落は要点1つ。手順は番号付き、比較は表 | 箇条書きだけの節。1段落に要点を3つ詰める |
| 参考URLは自分の言葉で要約。引用は `> 引用文 — [出典名](URL)` | 段落単位の転載、個人が特定できる情報 |
| 事実と意見は語尾で分ける（「〜と報じられた」／「〜と考えている」） | 「（意見）」「（事実）」のような注記（AIが書いた印象になる） |
| 太字は約物の外に置く（`は「**配る**」へ`・`**git**（ギット）は`） | `は**「配る」**へ`・`**git（ギット）**は`（太字にならず `**` が画面に残る。§4 の検証で止まる） |

## 4. 保存・画像・検証

- slug: 主張を表す英小文字3〜5語をハイフンで（例 `posting-time-is-not-the-lever`）。小文字英数字とハイフンのみ・80字以内。日付・連番は入れない
- `blog/drafts/<slug>.md` に保存（`blog/` 直下や `published/` に置かない）。front matter は `title`／`description`／`date`（今日 `date +%F`）／`updated`／`draft: true`／`tags`（既存と表記を揃える）／`image` の7つだけ（他は検証で弾かれる）。本文は `##` から始め（`#` は書かない）、生HTMLは書かない。画像は `public/blog-images/` に置き `/blog-images/<name>.png` で参照する
- **アイキャッチ**: `npm run blog:eyecatch -- <slug>` → `public/blog-images/eyecatch/<slug>.png` ができ、`image:` が書き足される。PNG を Read で開き、豆腐（□）・題名の切れを見る。`title` を変えたら作り直す
- **図**: 手順・比較・時系列・構造の説明（読者が頭の中で表や矢印を組み立てないと分からない段落）は図にする。図が主、文章は補足
  1. SVG を `blog/diagrams/<slug>-<name>.svg` に書く。幅 1200、`font-family="Hiragino Sans, Noto Sans JP, sans-serif"`、色は `#7d1f75`（線・見出し・矢印）と `#f4e8f3`（塗り）、白地。要素は3〜6個、矢印の向きと順番が一目で分かる形
  2. 本文幅（約720px）とスマホ（375px）に縮小される前提で描く: **最小の文字 40px 以上**（日付・補足の小さい文字も。`blog:diagram` が下回ると止める）、**1行 20 字まで**（説明の続きは本文へ。時系列は「日付」と「具体的な短文1〜2行」にし、「規制」「配る」のような分類語だけの札は置かない）、**横に3つ以上並べない**（縦積みか2列。手順は縦に流し、比較は上下に積む）、実寸の注記（「700px」など）を書かず比率で書く、事実の図に意見を混ぜない
  3. `npm run blog:diagram -- blog/diagrams/<slug>-<name>.svg <slug>-<name>.png` → `public/blog-images/`（2倍密度）にでき、`![図が伝える内容を1文で](/blog-images/<slug>-<name>.png)` で貼る（alt は「図1」ではなく、読み上げでも意味が通る1文）
  4. PNG と、スマホ幅（375px）プレビュー（一時ディレクトリ。パスは実行結果に出る）を Read で開き、豆腐・重なり・はみ出しが無く、拡大せずに文字が読めるか見る。読めなければ縦積みか文字拡大で1からやり直す
- `npm run blog:check -- <slug>.md` で `📝 <slug>.md  下書き（draft: true）` と `✅ 不備なし` を確認する。`❌` なら理由を直して再実行（太字にならない `**` は行番号つきで止まる）

## 5. セルフレビュー（必ず2周。全部 Yes になるまで直す）

**1周目＝事実と構成**（数字と出典を1つずつ元に当たる。見出しだけで流れが追えるか）
- [ ] 学びが本文に1文で入っている。`## 結論` だけ読めば要点が全部つかめる
- [ ] `title` は読者のメリットが分かり、注目のワードが1つある。`title`・`description`・冒頭3行が同じ主張を指す
- [ ] 具体例（手順・数字・プロンプト・設定値）が1つ以上ある。未計測は未計測と書いてある
- [ ] Exos AI の効果を約束していない。誤ると読者が損をする断定に出典か実測が付き、事実と意見が語尾で分かれている。参考URLの文章を写していない
- [ ] 図にすべき箇所を図にし、アイキャッチ（`image`）がある。`title` 80字以内・`description` 200字以内・本文 1,500〜3,000字（運営者の指定があればそれ）

**2周目＝読み物として**（頭から声に出して読むつもりで通す）
- [ ] つっかえる文・長すぎる文・2通りに取れる文・前提知識が要る箇所（ハイコンテキスト）を直した。初出の用語はその場で言い換えた
- [ ] 同じことを2か所で言っていない。無くても成り立つ補足を削った
- [ ] AIっぽさが無い: 「（意見）」型の注記（語尾で示す）／「〜することができます」「重要なのは」「まとめると」「言い換えれば」「〜と言えるでしょう」の多用（各1回まで。言い切りに直す）／見出しの言い直しから始まる段落（本題から始める）／太字の多用（1段落2つまで）／箇条書きだけの節（間の「なぜ」を文章で1つつなぐ）／「——」が3回以上（句点で切るか括弧に）／説明なしの内部用語（タスクID・スキル名・ファイル名・機能の内部名・略語）／太字にならない `**`（`blog:check` で止まる）

報告: 作ったファイル（記事・アイキャッチ・図）／記事の主張1行／確認してほしい点（未計測・運営者しか知らない実例・読めなかったURL）／次に実行するコマンド `/blog-publish <slug>.md`。

## ルール

- 公開しない。`draft` を外さない。コミットも `git add` もしない
- 1回で書くのは1記事。テーマが2つあれば分けて、どちらを先にするか聞く
- 記事・報告は日本語。コードブロック内のプロンプト・設定値は実物のまま載せる
