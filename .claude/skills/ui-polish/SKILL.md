# ui-polish：画面の実装と仕上げ

既存デザインシステムを守って実装し、**実ブラウザで完成状態まで**確認する。実装だけで完了にしない。

## 手順

1. **正本と既存を読む**
   - 仕様: `docs/PRD.md`／`docs/requirements/06_screens_onboarding_posting.md`／関連API要件
   - 既存: 対象route・親layout・`src/components/ui/`・`src/app/globals.css`・`components.json`
   - **既存コンポーネントとデザイントークンを最優先。任意値を増やさない。** 新規部品が要るときは shadcn MCP でレジストリを検索してから作る。
2. **方針を一言で決める** — 目的・主利用者・最優先アクション・情報階層。新規画面は美的方向を1つ選び、既存更新は現行システムとの一貫性を優先。
3. **実装する** — App Router／Server・Client境界／Tailwind 4／shadcn/ui の既存構成に従う。
4. **実ブラウザで検証する**（下の§検証）
5. **報告** — 方針／再利用・追加した部品とトークン／確認した幅・テーマ・状態／修正点／未解消事項。**未解消があれば完了扱いにしない。**

## 実装の決まり

| 対象 | 決まり |
|---|---|
| 色・余白・角丸・影 | CSS変数か既存ユーティリティを使う（直値を書かない） |
| 状態 | hover / focus-visible / disabled / loading / empty / error / success を該当分すべて |
| アクセシビリティ | 主要導線はWCAG 2.2 AA（キーボード・明瞭なfocus・label・色以外の状態表現） |
| モーション | `prefers-reduced-motion` を尊重 |
| 仕様変更 | 画面挙動を変えたら**同じ作業単位で**正本docsを更新 |

## 操作結果の通知は `useToast()`（要件06 §2.1）

画面内へ独自の成功／失敗メッセージを足さない。判断は3つだけ。

- **成功も必ず出す。** 無言で終わると、成功したのか何も起きなかったのか区別できない（原則1）。
- **トーストに載せないのは3種類**: 入力検証／ボタンを伴う案内／恒常表示・画面状態。理由と例は要件06 §2.1の表。
- **インライン通知を消すのとトーストを足すのは同じコミットで行う。** 片方だけだと「2か所に出る」か「どこにも出ない」になる。`useToast()` は Provider の外で呼んでも例外を投げない no-op なので、**呼んでいるのに何も出ない事故が静かに起きる**。移行した画面ごとに `e2e/toast.spec.ts` へ「実際に出る」テストを1件足し、`show()` を消すと落ちることを確認する。

## 検証（実ブラウザ）

| 項目 | やること |
|---|---|
| 起動 | `npm run dev` ＋ **`http://127.0.0.1:3000`**（X OAuthが `localhost` を許さない。HMRは `allowedDevOrigins` で許可済み） |
| ランタイム | Next.js DevTools MCP でランタイム／ビルド／Hydrationエラーを確認 |
| 認証必須画面 | テストユーザーでログインして開く（storage-stateは playwright-cli 参照） |
| 画面幅 | Playwright CLIで Desktop 1440 / Tablet 768 / Mobile 390 のスクショ |
| 生成物 | **本物のデータを載せて描画を確認。** 要素の存在ではなく実際に読み込めたこと（画像なら `naturalWidth>0`）。CSP違反・署名URL・デコード失敗は実物でしか出ない（T-M7-22で生成画像がCSPに弾かれ、ローカルでは必ず非表示だった） |
| 潰すもの | 横スクロール・重なり・文字切れ・focus/label欠落・色依存の状態・コンソールエラー・レイアウトシフト |

修正したら同条件で再確認する。**スクショ／traceはコミットしない。**
