# UI polish

Space AIの仕様と既存デザインシステムを守りながら、意図のあるUIを実装し、実ブラウザで完成状態まで確認する。

## 1. 正本と既存UIを確認する

1. 対象画面に対応する `docs/PRD.md`、`docs/requirements/06_screens_onboarding_posting.md`、関連するAPI要件を読む。
2. 対象ルート、親layout、近接画面、`src/components/ui/`、`components.json`、`src/app/globals.css`を確認する。
3. 既存コンポーネントとデザイントークンを優先し、同じ役割の部品や任意値を増やさない。
4. shadcn MCPが利用可能なら、コンポーネントを新規作成する前に公式レジストリを検索する。取得したコードはプロジェクト要件に合わせて調整する。

## 2. デザイン方針を定義する

実装前に、次を短く言語化する。

- 画面の目的と主利用者
- 最優先アクションと情報階層
- 既存画面から継承する視覚ルール
- この画面で強調する一つの特徴

新規画面では明確な美的方向を一つ選ぶ。既存画面の更新では独自方向を追加せず、現在のシステムとの一貫性を優先する。装飾量ではなく、タイポグラフィ、余白、整列、コントラスト、状態表現の精度で品質を上げる。

## 3. 実装する

- App Router、Server／Client Component境界、Tailwind CSS 4、shadcn/uiの既存構成を守る。
- 色、フォント、余白、角丸、影はCSS変数または既存ユーティリティを使う。繰り返す任意値はトークン化する。
- PCを基準にしつつ、スマートフォンで閲覧、下書き確認、投稿操作が完了できるようにする。
- 通常、hover、focus-visible、disabled、loading、empty、error、successのうち該当状態を実装する。
- 主要導線はWCAG 2.2 AAを目標とし、キーボード操作、明瞭なfocus、フォームlabel、色以外の状態表現を備える。
- モーションは意味のあるフィードバックに限定し、`prefers-reduced-motion`を尊重する。
- 要件や画面挙動を変更した場合は、同じ作業内で正本ドキュメントを更新する。

## 4. 実ブラウザで検証する

実装だけで完了にしない。

1. 開発サーバーを起動し、Next.js DevTools MCPが利用可能ならランタイムエラー、ビルドエラー、Hydration Errorを確認する。
2. Playwright CLI Skillで対象画面を開き、少なくとも次の幅でスクリーンショットを取得する。
   - Desktop: 1440px
   - Tablet: 768px
   - Mobile: 390px
3. ライト／ダークテーマが対象なら両方確認する。
4. 該当する主要状態と操作を再現し、キーボードでも主要導線を通す。
5. 次を目視・構造の両面で確認する。
   - 横スクロール、重なり、文字切れ、意図しない改行
   - 情報階層、余白、整列、コントラスト
   - focus欠落、label欠落、色だけに依存した状態
   - コンソールエラー、失敗リクエスト、レイアウトシフト
6. 問題を修正し、同じ条件でもう一度確認する。未解消事項がある場合は完了扱いにせず明示する。

## 5. 完了報告

次を簡潔に報告する。

- 採用したデザイン方針
- 再利用・追加したコンポーネントとトークン
- 確認した画面幅、テーマ、状態
- 修正した視覚・操作上の問題
- 未検証または未解消の事項
