# security-audit：穴を探して、確かめて、直すか判断を仰ぐ

**推測を報告しない。** セキュリティの指摘は「ありそう」で書くと嘘が混ざり、本物の指摘まで信用されなくなる。**必ず攻撃者の手順を1本書き、コードで到達を確かめてから**報告する。

**勝手に方針を変えない。** 穴の埋め方には「実装で閉じる」ものと「運営者が決める」ものがある（利用者に見える挙動が変わる・外部サービスの設定が要る・利便性とのトレードオフ）。下の「§ 直すか、判断を仰ぐか」で機械的に振り分ける。

## 前提（このリポジトリの守り方）

既に**検査で守っている**ものがある。これらは「無い」ではなく「**検出器が生きているか**」を見る。

| 守り | 正本 | 破れたときの症状 |
|---|---|---|
| 行の越境（RLS・GRANT） | `src/lib/db/rls.db.test.ts`・`service-role-grants.db.test.ts` | 他人のデータが見える／`authenticated` が直接書ける |
| 利用者どうしの干渉 | `src/lib/ops/tenant-isolation.db.test.ts` | 1人の大量投入で他人が止まる |
| 外向き副作用 | `src/lib/ops/outbound-channels.ts` ＋ `.test.ts` | 非productionから本物のX投稿・SMTP・課金が出る |
| cronの認可 | `src/app/api/cron/route-auth.test.ts` | 秘密無しでcronが叩ける |
| Server Actionの到達性 | `src/app/actions/server-action-reachability.test.ts` | 呼ばれない `"use server"` が残り攻撃面になる |
| 環境ごとの鍵 | `src/lib/ops/env-secret-usage.test.ts` | ローカルの鍵で本番を叩く |
| CSP（nonce） | `npm run check:csp-nonce` | prerenderでscriptが動かず**200のまま画面だけ壊れる** |
| 秘密値の露出 | `provider_raw_error` を返さないクエリ・`toUserFacingError` | providerの生文言・鍵がブラウザへ出る |

## 見る場所（この順で。上ほど事故が重い）

1. **認可（誰のデータか）** — Server Action / API route の入口で「本人か」を確かめているか。
   所有権は**SQLの where 条件**に入っているか（アプリ側の突き合わせだけだと競合で抜ける）。
   `x_account_id` や `draft_id` を受け取る経路は、**そのIDが本人のものか**を毎回確かめているか。
2. **費用の出る経路** — AI・X API・SMTP・Stripe。契約ガード（要件04 §4.1）を通るか。
   **入口だけでなく実行時（`leaseJob`）でも見ているか**（queued のまま状態が変わる）。
3. **秘密値** — トークン・APIキー・`CRON_SECRET`・`APP_ENCRYPTION_KEY`。
   ログ・エラー本文・DB・応答・**Sentryのcontext**へ出ていないか。暗号化して保存しているか。
4. **入口の検査** — Origin（CSRF）・署名（Stripe webhook）・state（OAuth）・Turnstile・
   zodの `.strict()`（未知フィールドを黙って受けない）。
5. **境界の値** — 利用者が渡す ID・URL・`next`・ファイル名。オープンリダイレクト、
   SSRF（外部URLを取りに行く経路）、パストラバーサル。
6. **AIへの入力** — 利用者の文字列がプロンプトへ入る経路。**出力を信用してDB・外部APIへ流していないか**
   （生成された投稿ID・URL・JSONをそのまま使っていないか）。
7. **時間差** — 「確認してから実行するまで」に状態が変わる経路（TOCTOU）。契約・上限・所有権。

## 直すか、判断を仰ぐか

見つけた穴ごとに上から当てる。

| 条件 | どうする |
|---|---|
| **明確な穴**で、直しても利用者から見た正常系の挙動が変わらない（検査の追加・条件の追加・値の秘匿） | **直す**。回帰テストを同じコミットで足す |
| 直すと**利用者に見える挙動が変わる**（できていたことができなくなる・文言が変わる） | **要決定へ**（暫定案つき）。勝手に締めない |
| **外部サービスの設定**が要る（Stripe・Supabase・Cloudflare・Xの管理画面） | **要決定へ**。手順を書いて運営者に依頼する |
| 方針そのものの変更（列挙対策の可否・保持期間・公開範囲） | **要決定へ**。判断の材料を3点以上並べる |
| **本番データの露出が疑われる**（既に漏れた可能性） | **止めて報告**。調査手順を示し、勝手に消さない・勝手に通知しない |
| 反証できた（到達不能・既に守られている） | **報告に「棄却」として残す**。理由も書く（次に同じ指摘を繰り返さないため） |

## 手順

0. **緑を確認**: `npm run typecheck && npm run lint && REQUIRE_DB=1 npx vitest run`。緑でなければ先に報告する。
1. **範囲を決める**: 引数があればそこ。無ければ「§ 見る場所」の1〜7を順に。
   直近の差分（`git log --oneline -20`）に**新しい入口**（route・Action・cron・外部呼び出し）が
   増えていれば最優先で見る。
2. **候補を出す**: 各候補に *攻撃者の手順 / 対象 file:line / 到達の根拠 / 影響 / 深刻度*。
3. **反証する（必須）**: 候補ごとに「どこかの層で止まらないか」をコードで確かめる。
   **止まるなら棄却**。ここを飛ばした報告は出さない（過去、6件中2件が誤検出だった）。
4. **振り分け**: 「§ 直すか、判断を仰ぐか」で分ける。
5. **直す**: 1件ずつ。**回帰テストを先に書く**（穴を再現するテスト → 直す → 緑）。
   検証は `CLAUDE.md`「変更影響 → 必須の検証」の該当行。
6. **要決定を書く**: `tasks/BACKLOG.md` の「要決定」へ `**D-<番号>: <論点>**` で、
   **案A/案B＋推奨**を添える。実装は待つ。
7. **報告**: 直した穴／要決定へ回した穴／**棄却した候補と理由**／見なかった範囲。

## やってはいけないこと

- **検査を消して「直した」ことにする**（落ちるテストを消す・条件を緩める）。
- **秘密値を報告・コミット・テストへ書く**。再現手順は値を伏せて書く。
- 本番・stagingのデータで試す。攻撃の再現は**ローカルのテストデータ**で行う。
- 反証していない指摘を報告に混ぜる。
- 「多層防御」を理由に、**利用者の利便性を落とす変更**を勝手に入れる（要決定へ）。

## Definition of Done

- [ ] 候補すべてに**反証**を通した（棄却は理由つきで報告に残した）
- [ ] 直した穴には**穴を再現する回帰テスト**がある
- [ ] 判断が要るものは「要決定」へ案つきで起票した（実装していない）
- [ ] `CLAUDE.md`「変更影響 → 必須の検証」の該当行を実行した
- [ ] 秘密値を報告・コード・テストへ書いていない
- [ ] `/doc-sync` 実行済み（方針に触れたら正本へ書き戻した）
