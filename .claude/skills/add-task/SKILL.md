# add-task：要望をタスクに変える

利用者の言葉（「〜したい」「〜が使いにくい」「〜が動かない」）を**着手可能なタスク**として `tasks/BACKLOG.md` へ起票する。`/dev-loop` はここに起票されたものを実行する。

**このスキルは実装しない。** コードは1行も変えず、BACKLOG（と必要なら「要決定」）だけを更新する。

## 手順

### 0. 重複を先に潰す（必須）

`git log --oneline -15` と `tasks/BACKLOG.md` を読む。**既に `done`／`todo`／`blocked` にある要望を二重に起票しない**（過去に完了済みタスクの重複実装で別タスクの成果を消す事故があった）。同じものがあれば起票せず、そのタスクIDを案内して終わる。

### 1. 要望を1文にする

「**誰が・どの画面で・何ができるようになるか**」の形にする。読み取れない情報は推測で埋めず、**着手に必要な最小限だけ**質問する（デザインの細部・将来の拡張は聞かない）。

### 2. 正本と照合する（この順）

| 確認 | 該当したら |
|---|---|
| PRD §3.2「MVPでやらないこと」に該当するか | **起票せず終わる。** スコープ外である旨と、進めるならPRD改定が必要であることを伝える |
| どの機能ID（A/L/N/P/S/K/M/O）・画面（SC-01〜11）・AI実行に紐づくか | 紐づく正本が無い＝**新しい仕様**。PRDまたは要件詳細の改定をタスクに含める |
| 既存実装で既に満たせていないか | 使い方を案内して終わる |

### 3. 大きさを決める

**1タスク = 1コミットで完了できる大きさ。** 画面追加・DB変更・AI実行の追加が同時に必要なら分ける。

| サイズ | 目安 |
|---|---|
| S | 半日以内 |
| M | 1日 |
| L | それ以上＝分割を検討。**L のまま起票するのは、分割すると途中状態で動かなくなる場合だけ** |

### 4. 書式どおり起票する

```
### <ID>: <タスク名> `todo`
- 参照: <docsの該当ID・節> / 依存: <タスクID または なし> / サイズ: <S|M|L>
- 完了条件:
  - <動作で確認できる形で書く>
  - <異常系・空状態も1行入れる>
- メモ: <なぜ必要か・実装時の注意・既知の制約>
```

| 項目 | 決まり |
|---|---|
| ID | 該当マイルストーン節の連番の次。節の**新設はユーザーに確認してから** |
| 配置 | 該当節の末尾。優先度が高ければ節内で上げてよい（上ほど優先） |
| 完了条件 | 「〜を改善する」ではなく「〜が表示される」「〜が保存される」。**`/dev-loop` がテストの根拠にする** |
| 参照 | docsの具体的な節。書けないなら仕様が無いということなので、正本の追記もタスクに含める |

### 5. 判断が要るものは「要決定」へ

費用・外部サービスの契約・法務・スコープの広がり・利用者に見える仕様の選択は**勝手に決めない**。`## 要決定・外部準備(ユーザー作業)` へ `**D-<番号>: <論点>**` として追記し、**可能なら案A/案Bと推奨**を添える。タスクの `依存` にその要決定を書く。

### 6. 不具合の場合

「再現手順」「実際に起きたこと」「期待する動作」を完了条件へ落とす。原因が分かっていればメモへ書く。**原因不明のまま「調査する」だけのタスクにしない**（調査は `/dev-loop` の中で行う）。

### 7. コミットと報告

- BACKLOG（と要決定）だけを `git add`。`git status` でコード未変更を確認する
- メッセージ: `chore(backlog): <要望の要約>を起票`
- 報告: タスクID／サイズ／完了条件の要点／新たな要決定／**次に実行するコマンド**（`/dev-loop <ID>`）

## ルール

- **実装しない。**「ついでに直す」もしない。コードを変えたくなったらそれは `/dev-loop` の仕事。
- **推測で仕様を作らない。** 判断が要るものは要決定へ回し、暫定案を添える。
- 1回で起票するのは**関連する1つの要望**まで。複数言われたら分けて起票し、それぞれ独立して着手できる形にする。
- タスク名・完了条件・メモは日本語で書く。
