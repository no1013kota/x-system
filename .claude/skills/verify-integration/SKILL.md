# verify-integration：統合テスト

変更に関係する境界だけを選び、実際のローカルSupabaseを含む統合動作を検証する。単体テスト、ブラウザE2E、外部サービスへのlive書き込みの代わりにはしない。

## 手順

1. **影響範囲を決める**
   - タスク、関連する`docs/`、`git diff`、変更ファイルを読む。
   - DB制約、RLS、API契約、状態遷移、冪等性、同時実行など、今回守る契約を先に列挙する。
   - 変更と無関係な広い環境変更や修正を行わない。
2. **接続先の安全を確認する**
   - 秘密値を表示せず、SupabaseとPostgreSQLの接続先がローカルのテスト環境であることを確認する。
   - 既定では`127.0.0.1`または`localhost`のローカルSupabaseだけへ書き込む。
   - Preview・本番DBで`reset`、`drop`、`truncate`、seed再投入、破壊的migration検証を行わない。
   - `supabase db reset`は専用の破棄可能なローカル環境で、クリーン適用の確認が必要な場合だけ使う。ユーザーが同じ依頼で明示していなければ、実行前に承認を得る。
3. **前提を整える**
   - `supabase status`でローカルスタックを確認し、必要なDBテストが自動skipされない状態にする。
   - 必要ならローカルSupabaseを起動する。ネットワーク取得や権限追加が必要なら承認を得る。
   - テストデータは一意な識別子を使い、既存の利用者データや別タスクの変更を上書きしない。
4. **対象テストを選ぶ**
   - migration・テーブル・RLS変更: schema、seed、RLS、別ユーザー拒否、制約のDBテスト。
   - Server Action・API変更: 認証、入力検証、所有権、Origin、署名、DB反映のテスト。
   - job・Cron変更: lease、状態遷移、冪等性、再試行、stale回収、deadline、同時実行のDBテスト。
   - 課金・利用量変更: Webhook重複、イベント順序、契約状態、利用枠の原子的更新のDBテスト。
   - X・AI adapter変更: モックを使った契約と記帳を検証し、live疎通はこのスキルで行わない。
   - `rg`で実装と対応する`*.db.test.ts`、route/actionテストを探し、必要なケースがなければ追加する。
5. **段階的に実行する**
   - 最初に変更対象へ近いテストを絞って実行する。
   - 境界をまたぐ変更では、関連するDBテスト群とAPI・jobテスト群を実行する。
   - 共通基盤、schema、認証、RLSを変更した場合は`npm test`まで実行して退行を確認する。
   - 失敗時は原因を特定し、依頼範囲の実装またはテストだけを修正して再実行する。
6. **検証の完全性を確認する**
   - pass件数だけでなく、fail、skip、todoを確認する。
   - 必須の`*.db.test.ts`が1件でもskipされた場合は統合テスト合格としない。
   - テスト後に作成データ、lock、実行中jobが残っていないことを確認する。
   - ログとエラー出力にAPIキー、token、暗号鍵、Cookie、個人情報が含まれていないことを確認する。
7. **報告する**
   - 使用した環境、検証した契約、実行結果、skip、未検証事項を簡潔に報告する。
   - 「合格」は必要な統合テストがすべて実行され、failと必須skipが0件の場合だけ使う。
   - 環境不足で実行できない場合は、単体テスト成功と統合テスト未実施を明確に分ける。

## ルール

- テストを通す目的でRLS、認可、署名検証、冪等guardを弱めない。
- Preview・本番データへ書き込まない。外部サービスの実課金・実投稿・実メール送信を行わない。
- ユーザーの既存変更を消さず、今回作成したテストデータだけを後片付けする。
