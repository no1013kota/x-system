# verify-e2e：E2Eテスト

ユーザー操作から画面・サーバー・DBの結果までを検証する。**確認範囲を超えた合格を報告しない。**

## 手順

1. **シナリオを決める** — タスク・docs・`git diff` から「開始状態 → 操作 → 期待する画面／DB・jobの最終状態」を書く。変更に直結する最小シナリオ＋壊れやすい主要経路。
2. **基盤を選ぶ** — リポジトリ管理のPlaywrightを優先。無ければ探索的確認でよいが「自動E2E合格」とは呼ばない。
3. **安全を確認する** — 下表。1つでも外れたら止める。
4. **データを用意する** — 専用テストユーザー＋実行ごとの一意ID。作成IDを記録。DB全体をresetせず他者データに触らない。
5. **実行する** — 表示だけでなくURL・入力・二重送信防止・エラー表示・最終状態。console error・失敗request・予期しないredirectも見る。
6. **後片付け** — 今回作成分だけ削除。失敗時も試み、残ったらID付きで報告。
7. **報告** — 自動か探索的か／環境／シナリオ／結果／証拠／未検証事項。

## 安全な既定（`e2e/fixtures/guard.ts` が起動前に検査）

| 項目 | 値 |
|---|---|
| `APP_ENV` | `development` |
| `X_POSTING_MODE` | `dry_run` |
| Supabase / baseURL | ローカル（`127.0.0.1`） |
| AI | モックまたはテストキー |
| Stripe | test / sandbox |
| メール | Mailpit |

**やらない**: 本番接続、X実投稿、実課金、第三者への実メール。秘密値をスクショ・trace・ログ・報告に残さない。

## 落とし穴（実際に踏んだもの）

- **fixtureで「済んだ状態」を作ると、その状態にする行為自体が未検証で残る。** 例: `x_accounts` を直接insertすると連携の入口を一度も通らない。連携・登録・課金など入口がある機能は、飛ばした経路を別ケースで1回通す。外部サービスへは行かず、リダイレクト先（Location）や発行cookieの検証で止めてよい。
- **生成物は実データで描画するところまで見る。** 画像・グラフ・ニュースカード・分析表。要素の存在では足りず、**実際に読み込めたこと**（画像なら `naturalWidth>0`）を確認する。CSP違反・署名URLの失効・レイアウト崩れ・デコード失敗はブラウザで実物を描画したときにしか出ない。実例: 生成画像プレビューが `img-src` に弾かれローカルでは**必ず**非表示だったが、E2Eが画像を持つ下書きを一度も描画しておらず気付けなかった（T-M7-22）。
- **jobはローカルで自動進行しない。** worker（`/api/jobs/run`）か該当cron routeを明示的に叩き、完了は**期限付きで**pollする（無制限に待たない）。
- **1件目のtimeoutを「flaky」と即断しない。** `src/**` 編集直後はroute初回コンパイルで60秒を超えうる。編集を挟まず再実行して緑かを見る。
- **flakyを無条件retryで隠さない。** 原因と再現条件を先に探す（`CLAUDE.md`「変更影響 → 必須の検証」§3）。

## 変更別に見る経路（該当のみ）

| 変更 | 通す経路 |
|---|---|
| 認証 | signup → 確認メール → login → logout → recovery → 保護route |
| フォーム | 正常／validation／二重送信／loading／再試行 |
| 投稿 | 生成 → job完了 → 下書き編集 → dry-run投稿 → 履歴 |
| 予約・Cron | slot登録 → 到来処理 → dry-run → 同tick再実行の非重複 |
| 課金 | test環境で契約状態と画面権限 |
| UI | 狭い幅／キーボード／label／focus |

## ルール

- live外部サービスが必要になったら停止し、承認手順へ引き継ぐ。
- 認証・課金・同意・投稿安全策を迂回しない。
- 「E2E合格」は自動シナリオが全assertion通過したときだけ。探索的確認は「確認済み（自動回帰は保証しない）」と書く。
