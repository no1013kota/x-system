# verify-e2e：E2Eテスト

ユーザー操作から画面・サーバー・DBの結果までを、ローカルまたは明示された安全環境で検証する。自動E2Eと探索的確認を区別し、確認範囲を超えた合格を報告しない。

## 手順

1. **シナリオ**: タスク・関連docs・`git diff`・変更画面から、開始状態→操作→期待する画面／DB・jobの最終状態を定義。変更に直結する最小シナリオ＋壊れやすい主要経路を選ぶ。
2. **基盤**: リポジトリ管理の自動E2E（Playwright等）があれば優先。無ければ利用可能なブラウザ操作スキルで探索的に確認してよいが「自動E2E合格」とは呼ばない。再現可能な検証ができないなら必要な基盤を未検証事項として報告する。
3. **安全**: `APP_ENV=development`・`X_POSTING_MODE=dry_run`・ローカルSupabase・`http://127.0.0.1:3000`。X=dry-run、AI=モック/テストキー、Stripe=test/sandbox、メール=Mailpit。本番・X実投稿・実課金・第三者への実メールは実行しない。秘密値を入力記録・スクショ・trace・ログ・報告に残さない。
4. **データ**: 専用テストユーザーと実行ごとの一意ID。最小fixtureだけ作り作成IDを記録。DB全体をresetせず他者データを変更しない。**fixtureで「済んだ状態」を作ると、その状態にする行為自体が未検証のまま残る**（例: x_accountsを直接insertすると連携の入口を一度も通らない）。連携・登録・課金など「入口」がある機能は、fixtureで飛ばした経路を別ケースで必ず1回通す。外部サービスへは行かず、リダイレクト先（Location）や発行cookieの検証で止めてよい。
5. **実行**: 表示だけでなくURL・入力・二重送信防止・エラー表示・最終状態を確認。job はローカルで自動進行しないので worker（`/api/jobs/run`）や該当cron routeを明示的に叩いて進め、完了は期限付きでpollする（無制限に待たない）。console error・失敗request・予期しないredirectも見る。失敗時はスクショ/trace/再現手順を保存（秘密値を含めない・コミットしない）。
6. **変更別の経路**（該当のみ）: 認証=signup/確認メール/login/logout/recovery/保護route。フォーム=正常/validation/二重送信/loading/再試行。投稿=生成→job完了→下書き編集→dry-run投稿→履歴。予約・Cron=slot登録→到来処理→dry-run→同tick再実行の非重複。課金=test環境で契約状態と画面権限。UI=狭い幅/キーボード/label/focus。
7. **後片付け**: 今回作成分だけ削除/無効化。失敗時も試み、残データをID付きで報告。
8. **報告**: 自動E2Eか探索的か・環境・シナリオ・結果・証拠・未検証事項。「E2E合格」は自動シナリオが全assertion通過時のみ。探索的は「確認済み（自動回帰は保証しない）」と明記する。

## ルール

- live外部サービスが必要なら停止し承認手順へ引き継ぐ。認証・課金・同意・投稿安全策を迂回しない。flakyを無条件retryで隠さず原因と再現性を調べる。
