# verify-e2e：E2Eテスト

ユーザー操作の開始から画面・サーバー・DBの結果までを、ローカルまたは明示された安全なテスト環境で検証する。自動E2Eと探索的なブラウザ確認を区別し、確認範囲以上の合格を報告しない。

## 手順

1. **シナリオを決める**
   - タスク、関連する`docs/`、`git diff`、変更画面を読む。
   - 開始状態、操作、期待する画面、DB・jobの最終状態を定義する。
   - 変更に直接関係する最小シナリオと、壊れやすい主要経路を選ぶ。
2. **E2E基盤を確認する**
   - `package.json`、設定ファイル、`e2e/`、テスト用fixtureを調べ、リポジトリ管理されたPlaywright等の自動E2Eを優先する。
   - 自動E2E基盤がなければ、利用可能なブラウザ操作スキルで探索的に確認してよい。ただし結果を「自動E2E合格」やリリースゲート合格と表現しない。
   - 基盤不足で再現可能な検証ができない場合は、必要なテスト基盤・fixture・シナリオを未検証事項として報告する。
3. **環境の安全を確認する**
   - 既定では`APP_ENV=development`、`X_POSTING_MODE=dry_run`、ローカルSupabase、`http://127.0.0.1:3000`を使う。
   - Xはdry-run、AIはモックまたは明示されたテストキー、Stripeはtest/sandbox、メール確認はMailpitを使う。
   - 本番、X live投稿、実課金、第三者への実メール送信をこのスキルから実行しない。
   - 秘密値を画面入力の記録、スクリーンショット、trace、ログ、報告へ残さない。
4. **データを準備する**
   - 専用テストユーザーと実行ごとの一意な識別子を使う。
   - 必要最小限のfixtureだけを作り、作成したIDを記録する。
   - DB全体をresetせず、既存利用者や別タスクのデータを変更しない。
5. **シナリオを実行する**
   - 自動E2Eがあれば対象シナリオを絞って実行し、必要に応じて主要回帰シナリオも実行する。
   - 探索的確認では、表示だけでなくURL、入力、送信防止、エラー表示、最終状態を確認する。
   - job完了待ちは状態を期限付きでpollし、無制限に待たない。
   - ブラウザのconsole error、失敗したnetwork request、予期しないredirectも確認する。
   - 失敗時はスクリーンショット、trace、再現手順を保存する。ただし秘密値を含む証拠は保存しない。
6. **変更に応じた経路を確認する**
   - 認証変更: signup、確認メール、login、logout、recovery、保護route。
   - 画面・フォーム変更: 正常入力、validation、二重送信防止、loading、失敗後の再試行。
   - 投稿変更: 生成、job完了、下書き編集、dry-run投稿、履歴反映。
   - 予約・Cron変更: slot登録、到来処理、dry-run投稿、同じtick再実行時の非重複。
   - 課金変更: Stripe test環境またはモックで契約状態と画面権限を確認する。
   - 主要UI変更: 狭い画面幅、キーボード操作、ラベル、focus、主要ブラウザの必要範囲を確認する。
7. **後片付けする**
   - 今回作成したユーザー、下書き、job、予約、fixtureだけを削除または無効化する。
   - 失敗時も後片付けを試み、残ったデータをID付きで報告する。
8. **報告する**
   - 自動E2Eか探索的確認か、環境、ブラウザ、実行シナリオ、結果、証拠、未検証事項を報告する。
   - 「E2E合格」はリポジトリ管理された自動シナリオが全assertionを通過した場合にだけ使う。
   - 探索的確認は「確認済み」と表現し、自動回帰を保証しないことを明記する。

## ルール

- live外部サービスが必要になったら停止し、外部疎通用の承認付き手順へ引き継ぐ。
- テストを通すために認証、課金、同意、投稿安全策を迂回しない。
- flakyな失敗を無条件retryで隠さず、原因と再現性を調べる。
