# refactor：システム全体の安全なリファクタリング

外部から見た振る舞い・仕様・公開API/契約を変えずに、内部品質（重複・複雑度・境界・型・命名・デッドコード・テスト容易性）を上げる。**全体を一度に書き換えない。** dev-loop と同様バックログ駆動で、1回の実行で扱うのは1単位のみ（WIP=1）。仕様変更を伴うものはリファクタではないので dev-loop 側で扱う。

## 大原則（必ず守る）

1. **振る舞い保存**: 外部挙動・DB/APIの契約・画面仕様・プロンプト出力・エラー契約を変えない。変わるならリファクタではない＝中止してユーザーに報告する。
2. **テストが安全網**: 着手前に全テストが緑であることを確認する。緑でない状態からは始めない。対象の挙動を守るテストが薄い箇所は、**先に特性テスト（characterization test）を別コミットで追加**してからリファクタする。
3. **小さく・可逆に**: 1単位＝1つの一貫した変更。無関係な変更を混ぜない。単位ごとに検証し、緑にできなければ直すか revert する。
4. **仕様の正本を守る**: docs/ が参照する構造（ファイル名・公開関数・型名・DBテーブル等）を変えたら /doc-sync で追随する。表現しきれない横断的判断は docs/decisions/ に ADR を残す。
5. **規約・秘密情報**: 実キーを混入しない。応答・コミット・ドキュメントは日本語、コード識別子・コメントは英語。`git add -A` を使わず、`git status` で無関係な変更の巻き込みを防ぐ。

## 手順

0. **現状同期**: `git log --oneline -15`、`tasks/BACKLOG.md`、`tasks/REFACTOR_PLAN.md`（あれば）を読む。`npm run typecheck` → `npm run lint` → `npm test` が緑であることを確認する。緑でなければまずそれを解消するかユーザーへ報告し、リファクタは始めない。

1. **監査（Discovery）**: `tasks/REFACTOR_PLAN.md` に承認済みで未着手の候補があればこの手順を飛ばす。無ければ対象範囲（引数があればその領域、無ければ全体）を「## リファクタの観点」に沿って監査し、候補を洗い出す。範囲が広い場合は「## Workflow の活用」に従い並列監査してよい。各候補に *file:line / 種類 / 期待効果 / リスク / 推定規模 / 影響するテスト* を記録する。

2. **優先度付けと計画（要承認）**: 価値が高く低リスクなものから並べ、`tasks/REFACTOR_PLAN.md` に一覧化する。**全体リファクタは影響が大きいため、実行前にユーザーへ計画を提示して承認を得る。** 判断が要る項目は「要決定」として暫定案を添える。承認前に実装へ進まない（`--audit` は本手順で停止）。

3. **1単位を実行（WIP=1）**: 承認済み計画の最上位の未着手項目を1件選ぶ。テストが薄ければ特性テストを先に追加（別コミット）。その後、振る舞いを変えずに改善する。項目に書かれていない範囲へ広げない。

4. **検証**: `npm run typecheck` → `npm run lint` → `npm test` →（構造変更や設定変更を伴うなら）`npm run build`。すべて緑にする。差分が外部挙動・契約・スナップショットを変えていないことを確認し、ローカルで実際に動く経路があれば動作確認する（/verify があれば使う）。

5. **ドキュメント同期**: /doc-sync を実行する。純粋な内部改善で外部仕様に影響が無い場合も「影響なし」を理由付きで記録する（黙って省略しない）。docs が参照する構造を変えた場合は更新、横断的な技術判断は ADR を追加する。

6. **完了処理**: `tasks/REFACTOR_PLAN.md` の該当項目を done にし、要点と後続への注意を1〜2行メモする。`refactor(<scope>): 概要` 形式でコミットする（例 `refactor(stripe): checkout/portalの共通処理を統合`）。関連ファイルのみ明示的に `git add` し、メッセージ末尾に `Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>` を付ける。

7. **報告**: 実施内容・主要な判断・検証結果・次候補・新たな要決定を簡潔に報告する。連続実行は `/loop /refactor`。全項目が done、または安全に進められる候補が尽きたら停止し理由を述べる。

## リファクタの観点（監査チェックリスト）

- **重複**: コピペされたロジック・定数・型の共通化（Single Source of Truth 化）。
- **複雑度**: 長大な関数・深い分岐の分割、早期return、責務分離。
- **境界・依存**: レイヤ違反（UIからDB直結等）、循環依存、`server-only`／クライアント境界の乱れ。
- **型**: `any`・不要な `as`・非null断定の削減、判別可能ユニオン化、DB enum と TS 型のドリフト解消。
- **命名・一貫性**: 命名規約・ファイル配置・エラーハンドリング様式・レスポンス形の統一。
- **デッドコード**: 未使用の export・依存・フラグ・分岐の削除。
- **テスト容易性**: 副作用の注入化（純粋関数への抽出）、薄い箇所への特性テスト追加。
- **パフォーマンス**（挙動を変えない範囲）: 明白なN+1・不要な再計算・重い同期処理の是正。

## やってはいけないこと

- 全体の一括書き換え・大規模な同時変更（必ず小単位へ分割する）。
- 外部挙動・DB/API契約・画面仕様・プロンプト出力の変更（それは機能変更＝ dev-loop で扱う）。
- テストを緑にしないままのコミット、スナップショット・契約テストの安易な書き換え。
- 承認前の全体リファクタ着手、無関係な変更の混在、`git add -A`。
- PRD §3.2（MVPでやらないこと）に反する方向への「改善」。検出したら実装せずユーザーへ警告する。

## Workflow の活用（任意）

監査（手順1）や広域の機械的置換は、ユーザーが多エージェント実行（ultracode／workflow）に opt-in している場合に限り Workflow で並列化してよい。「領域 × 観点」でfan-outして候補を集約→重複排除→リスク検証、という流れにする。実行フェーズ（手順3〜6）は必ず1単位ずつ検証ゲートを通し、複数単位を無検証で並行適用しない。

## Definition of Done

- [ ] 外部挙動を変えていない（テスト緑・契約/スナップショット不変を確認）
- [ ] `/doc-sync` 実行済み（更新した、または影響なしを理由付きで確認）
- [ ] `tasks/REFACTOR_PLAN.md` のステータスと実装メモを更新した
- [ ] `refactor(<scope>): …` かつ Co-Authored-By 付きでコミットした
