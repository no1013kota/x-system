# dev-loop：開発サイクル1回転

バックログ駆動で**1タスクだけ**を完了させる（WIP = 1）。

## 手順

### 0. 現状を正本から確認する（必須）

`git log --oneline -15` と `tasks/BACKLOG.md` を読む。**記憶より git log と BACKLOG を信頼する。**

> コンテキスト圧縮をまたぐと記憶上の進捗が実際とずれる。過去に**完了済みタスクを重複実装し、`git add -A` で別タスクの成果を削除する事故**が起きた。コミット前は必ず `git status` を見て、無関係な変更を巻き込まない。

### 1. タスクを選ぶ

| 状況 | すること |
|---|---|
| `doing` がある | それを再開 |
| 引数でID指定 | それを選ぶ |
| どちらも無い | 依存がすべて `done` の最優先 `todo` を1件（上にあるものほど優先） |
| `todo` が1件も無い | **実装を始めず停止。** `/add-task <やりたいこと>` で起票できることを伝える |

選んだら `doing` に更新する。「要決定」でブロックされていれば飛ばし、**全部ブロックなら停止**して必要な決定を列挙する。

### 2. 正本を読む

タスクの参照ID（機能A-1／画面SC-05／AI実行GEN-P1 等）の該当節を `docs/` から読む。どの文書が何を定義するかは `docs/README.md`。

### 3. 実装と単体テスト

- 完了条件を満たす**最小の実装**。タスクに無いスコープへ広げない。
- 正常系だけでなく、変更に関係する**異常系と境界値**を含める。
- 不具合修正は**修正前に失敗する再現テストを先に**追加する。
- 実装詳細ではなく公開される入出力・状態遷移・エラーを検証する。カバレッジ率をテスト品質の代わりにしない。
- テスト追加が不要な変更（docs・コメント・機械的な設定）なら、その理由をステップ6で報告する。
- 出た仕様疑問は暫定判断で進めてよいが、**必ずステップ5でdocsへ残す**。

### 4. 検証

**手段は `CLAUDE.md`「変更影響 → 必須の検証」で決める**（その場の判断で選ばない。新規実装か既存更新かでも分けない）。

- §1の表 — 触った層の該当行を**すべて**実行。実行しなかった行は理由を報告する
- §2「いつ回すか」 — 毎コミットで build・E2E まで回さない（CIが同じものをpush時に回すため二重実行）
- §3「落とし穴」 — 必ず読む（パイプが終了コードを捨てる／新規ファイルはstage前は「実在しない」扱い／E2E1件目のtimeout）

**このループ固有の注意**:

- 実装中は変更対象に近いテストを絞って反復し、失敗したら直してから進む。
- 完了前に `npm run typecheck && npm run lint && REQUIRE_DB=1 npx vitest run`（実測 約40秒）。
- **pass件数だけ見ない。** fail・skip・todo を確認する。`*.db.test.ts` のskipを統合テスト成功として扱わない。
- 該当スキル（`/verify-integration`・`/verify-e2e`）が使えないなら同等の検証を行い、代替内容と未検証事項を報告する。

### 5. docs同期

`/doc-sync` を実行する。**これを省略した完了は完了ではない。**

### 6. 完了処理と報告

- BACKLOG を `done` にし、後続へ影響する判断・注意点を1〜2行メモする
- 新たなユーザー判断事項は「要決定」へ追記（可能なら暫定案を添える）
- タスクIDを含むメッセージでコミット（例 `feat(T-M1-01): メール認証を実装`）
- 報告: 完了したタスク／主要な判断／次のタスク／新たな要決定

## ルール

- 外部要因（アカウント未作成・キー未発行等）で完了できないなら `blocked` にし、理由をBACKLOGへ書いて次へ進む。
- **振る舞いを変えたのに単体テストが無い状態を完了扱いにしない。**
- 必要な統合テスト・E2Eが未実施なら、単体テストだけで完了扱いにしない。環境不足なら未検証事項として明示する。
- テストが通らない状態でコミットしない。
- Definition of Done は `CLAUDE.md`。
