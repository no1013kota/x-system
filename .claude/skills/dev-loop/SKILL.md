# dev-loop：開発サイクル1回転

バックログ駆動で1タスクを完了させる。1回の実行で扱うのは1タスクのみ（WIP = 1）。

## 手順

0. **現状の同期（必須・記憶より正本を信頼）**: 着手前に必ず `git log --oneline -15` と `tasks/BACKLOG.md` のステータスを読み、**実際にコミット済み／`done` の内容**を確認する。会話がコンテキスト圧縮をまたいでいる場合、記憶上の進捗と実際の状態がずれていることがある（過去に、完了済みタスクを重複実装し `git add -A` で別タスクの成果を削除する事故が発生）。記憶とBACKLOG／git logが食い違う場合は**必ず正本（git log・BACKLOG）を優先**する。また、コミット前は必ず `git status` で意図しない削除・変更が混ざっていないか確認し、`git add -A` で無関係ファイルを巻き込まない。
1. **タスク選択**: `tasks/BACKLOG.md` を読む。
   - `doing` のタスクが既にあればそれを再開する
   - 引数でタスクID指定があればそれを選ぶ
   - いずれもなければ、依存タスクがすべて `done` の最優先（上にあるものほど優先）の `todo` を1件選ぶ
   - 選んだタスクを `doing` に更新する
2. **ブロック確認**: 「要決定」セクションに選択タスクをブロックする項目があればそのタスクをスキップし、次の非ブロックタスクを選ぶ。**全タスクがブロックされていれば何もせず停止し、必要な決定事項を列挙してユーザーに報告する**（/loop 実行中ならループも停止する）。
3. **コンテキスト読込**: タスクに紐づく要件ID（機能 A-1等／画面 SC-05等／AI実行 GEN-P1等）の該当セクションを、docs/ の正本（PRD／要件定義書と`requirements/`の該当詳細／プロンプト設計書）から読む。どの文書が何を定義するかは docs/README.md 参照。
4. **実装と単体テスト**: 完了条件を満たす最小の実装と、その変更で追加・変更される振る舞いを保護する単体テストを書く。タスクに書かれていないスコープへ勝手に広げない。
   - 正常系だけでなく、変更に関係する異常系と境界値を含める。
   - 不具合修正では、可能な限り修正前に失敗する再現テストを先に追加する。
   - 実装詳細ではなく、公開される入出力・状態遷移・エラーを検証する。カバレッジ率をテスト品質の代わりにしない。
   - ドキュメント・コメント・機械的な設定変更だけでテスト追加が不要な場合は、その理由をステップ8で報告する。
   - 実装中に出た仕様疑問は暫定判断で進めてよいが、判断内容を必ずステップ6でドキュメントに残す。
5. **検証**:
   - 実装中は変更対象に近いテストを絞って反復実行し、失敗したら直してから先へ進む。
   - 完了前に `npm run typecheck`、`npm run lint`、`npm test` を実行し、既存テストを含めて退行がないことを確認する。
   - pass件数だけでなく、fail・skip・todoを確認する。`*.db.test.ts`のskipは統合テスト成功として扱わず、変更対象に関係する場合は環境を整えて実行するか、未検証理由を報告する。
   - 追加検証は**その場の判断ではなく CLAUDE.md「変更影響 → 必須の検証」の対応表**で決める。新規実装か既存更新かでは分けない。該当行が複数あればすべて実行し、実行しなかった行は理由を報告する。
   - DB、migration、RLS、Server Action、API Route、認証、課金同期、job、Cronを変更した場合は`/verify-integration`を実行する。
   - 認証、画面遷移、フォーム、投稿生成、下書き、予約投稿、分析、設定、課金など主要なユーザーフローを変更した場合は`/verify-e2e`を実行する。生成物（画像・グラフ・カード）を描画する画面は**実データで描画するところまで**見る。
   - **AI provider・プロンプト・出力schema・tool定義に触れたら `npm run check:providers` ＋ 実物を1周**（該当パターンを1回実行し、DBの成果物まで確認）。テストが緑でも外部境界はモックされており未検証であることを前提に置く。2026-07-28、この層を見ずに完了扱いにした結果、生成・画像・ニュースの4系統が同時に壊れたまま利用者の手動操作で発見された（T-M7-15/20/21/22/24）。
   - 両方に該当する場合は両方実行する。該当スキルが利用できない場合は同等の検証を行い、代替内容と未検証事項を報告する。
   - **外部サービスの扱いは2つに分ける**。(a) 取り返しがつかない・第三者に影響するもの（X実投稿・実課金・第三者への実メール・本番DBへの書き込み）は自動実行せず、ユーザーの明示的な依頼と承認がある別手順へ分離する。(b) AI providerへの生成呼び出しは**費用が発生するだけで副作用が無い**ため上の必須検証に含める。ただし実費が出るので、自動実行の可否と1周あたりの上限額が決まるまで（BACKLOG D-10）は**実行前にユーザーへ確認**する。
6. **ドキュメント同期**: /doc-sync を実行し、該当ドキュメントを更新する。
7. **完了処理**:
   - BACKLOG のステータスを `done` にし、後続タスクに影響する判断・注意点があれば実装メモとして1〜2行追記する
   - 新たに出たユーザー判断事項は「要決定」セクションに追記する（可能なら暫定案を添える）
   - タスクIDを含むメッセージでコミットする（例: `feat(T-M1-01): メール認証を実装`）
8. **報告**: 完了したタスク・主要な判断・次に着手するタスク・新たな要決定事項を簡潔に報告する。

## ルール

- 完了条件を満たせない外部要因（アカウント未作成、キー未発行等）があれば `blocked` にして理由をBACKLOGに記録し、次のタスクへ進む。
- 振る舞いを追加・変更したのに対応する単体テストがない状態を、原則として完了扱いにしない。
- 必要な統合テストまたはE2Eテストが未実施の場合、単体テストだけでタスクを完了扱いにしない。環境不足で実行不能なら未検証事項として明示する。
- テストが通らない状態でコミットしない。
- Definition of Done は CLAUDE.md 参照。ドキュメント同期（ステップ6）を省略した完了は完了ではない。
