# ドキュメントマップ

`document/` はこのプロダクトの仕様の正本（Single Source of Truth）。実装と食い違った状態を放置しない。
仕様に影響する実装変更を行ったら、下表に従って同じ作業単位内で該当ドキュメントを更新する（詳細ルールは `/doc-sync` スキルと `CLAUDE.md` 参照）。

| ドキュメント | 内容 | 更新タイミング |
|---|---|---|
| `PRD_SpaceAI_v1.0.md` | 要件定義（何を作るか・なぜ・スコープ・料金） | 要件・スコープ・料金・プラン内容が変わったとき。末尾の変更履歴に必ず追記 |
| `architecture.md` | システム構成・技術スタック・外部連携・横断的関心事 | 構成要素・インフラ・依存サービス・認証やジョブ等の仕組みが変わったとき |
| `data-model.md` | データモデル（エンティティ・スキーマ・リレーション） | スキーマ変更時（マイグレーションと同時に更新） |
| `api-spec.md` | 内部API仕様（エンドポイント・リクエスト/レスポンス） | エンドポイントの追加・変更・削除時 |
| `screens.md` | 画面一覧・画面仕様・画面フロー | 画面の追加・削除・UIフロー変更時 |
| `decisions/` | ADR（技術・設計判断の記録） | 重要な判断をしたとき。1判断 = 1ファイル。過去のADRは上書きせず、新しいADRで置き換える（Superseded） |

## 運用ルール

- 各ドキュメント（PRD除く）の冒頭にステータス（`Draft` / `確定`）と最終更新日を記載し、更新時に日付を更新する。
- PRDはファイル名にバージョンを含む。軽微な改訂は同一ファイルを編集して変更履歴を更新し、メジャー改訂（v2.0）時のみ `git mv` でリネームする。
- どのドキュメントに書くか迷ったら: **Why（なぜ作るか）→ PRD** / **What・How（構造と仕組み）→ architecture / data-model / api-spec / screens** / **判断の経緯 → decisions/**。
- ドキュメントには仕様レベルの記述を書く。コードの逐語的な説明は書かない（コードを読めばわかることは書かない）。
