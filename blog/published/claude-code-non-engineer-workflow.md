## 結論

非エンジニアがClaude Codeでアプリを壊さずに作り続けるのに要るのは、上手な頼み方ではなく、**決めたことを会話の外のファイルに書き、Claudeが毎回それに従って動く仕組み**だ。Claude Codeは会話が終わると忘れ、人間は手順を忘れるからだ。私はこの仕組みで、コードを書けないまま課金や自動投稿を含むWebアプリを1人で公開・運用している。

ファイルは次の4つ。どれも文字だけのファイルで、私のプロジェクトではフォルダに直接置いている（キットでは手順書だけプラグインとして入るので、フォルダには現れない）。

| ファイル | 役割 |
|---|---|
| CLAUDE.md（約束） | Claudeが会話のたびに自動で読む指示書。「非エンジニアが1人で運用する」ための5原則と、「どこを触ったら何を検証するか」の対応表を書く |
| docs/（仕様書） | 仕様のいちばん正しい版。会話が終わっても残り、コードを変えたら同じ作業の中で直す |
| tasks/BACKLOG.md（作業キュー） | やることを上から順に1本に並べ、Claudeは上から1件ずつ取る。AIが決めてはいけないことは「要決定」に溜め、自分がまとめて決める |
| スキル（手順書） | `/add-task` `/dev-loop` など、決まった作業を毎回同じ手順で進めるコマンド。やることだけでなく止まる条件も書く |

![あなたが日本語で頼み、Claude Codeが4つのファイル（CLAUDE.md・手順書・docs・BACKLOG）を読んで作り、報告する図](/blog-images/claude-code-non-engineer-workflow-four-tools.png)

日々の使い方は、`/add-task` で要望を一覧に足し、`/dev-loop` で1件ずつ作らせ、報告と画面を自分で確かめる、の往復だ。コードは読まない。中でも効くのが検証の対応表で、「テストは全部緑なのに本番では動かない」事故を防ぐ。

この4点を誰のプロジェクトでも使える形に直し、Claude Codeの「プラグイン」（後から足せる拡張機能）として配る。コマンド3つ（登録・インストール・`/docdd:init`）で入り、中身は[配布元のGitHub](https://github.com/no1013kota/claude-docdd-dev-kit)で読める。先に手を動かしたい人は、最後の「キットの使い方」へ。

## この記事の前提

- 対象は、プログラミング経験がない、またはほぼ無い人。ターミナル（文字でパソコンに指示を出す黒い画面。Claude Codeはここで動く）に1行打つことには挑戦してもらう。
- 必要なものは[Claude Code](https://code.claude.com/)とgit（無ければ手順0でClaudeが入れ方を案内する）。
- 本文に出るgit（ギット）はファイルの変更履歴を残す道具、コミットは「ここまでの作業を1つの記録にする」操作。どちらもClaudeが実行する。テストは、コードが期待どおりに動くかを機械で確かめる小さなプログラムで、全部通ると「緑」、1つでも失敗すると「赤」と表示される。
- コマンドは、プラグインで入れると `/docdd:add-task` のように頭に `docdd:` が付く。説明では短く `/add-task` と書き、実際に打つ手順では正確な形で書く。

## なぜ「頼み方」ではなく「ファイルに書く」なのか

Claude Codeは会話（セッション）が終わると忘れる。公式ドキュメントにも「各セッションはまっさらな状態から始まる」とある（[Memory](https://code.claude.com/docs/en/memory)）。昨日決めたルールを、今日のClaudeは知らない。

人間の側にも弱点がある。非エンジニアは「正しい確認手順」を知らないし、知っても忘れる。たとえば、DB（アプリのデータの置き場）の構造を変えたら、利用者が使っている本番のDBにも同じ変更を適用しなければならない。忘れると画面が壊れる。

だから、決めたことはファイルに書いて会話の外に置く。4つのうちCLAUDE.mdとスキルはClaude Codeが公式に用意している置き場で、仕様書と作業キューは私が足したものだ。

## 4つのファイルを1つずつ

フォルダに置くとこうなる。

```
あなたのプロジェクト/
├── CLAUDE.md              ← 約束。Claudeが毎回読む
├── docs/                  ← 仕様書。「何を作るか」「どう作ったか」のいちばん正しい版
├── tasks/BACKLOG.md       ← 作業キュー。やること一覧と「要決定」
└── .claude/skills/        ← 手順書。プラグインで入れる場合、このフォルダは作られない
```

### 1. CLAUDE.md（約束）: 毎回言い直していたことを書く場所

Claudeが会話を始めるたびに必ず読む指示書だ。公式の推奨は「同じ修正を2回言ったら書く」（[Memory](https://code.claude.com/docs/en/memory)）。

キットのCLAUDE.mdの柱は2つある。1つ目は冒頭の5つの原則で、「このアプリは非エンジニアが1人で運用する」ことをClaudeに伝える。私のプロジェクトで実際に事故を減らしてきた。

1. **黙って壊れない**。失敗は必ず記録し、通知や状態確認のコマンドに載せる。「エラーは出ないが何も起きない」が一番怖い。
2. **原因が開発知識なしで辿れる**。「ログを読んでください」で終わらせず、画面かコマンド1つで分かる形にする。
3. **手順を人間の記憶に頼らない**。忘れると壊れる手順は、1コマンドにまとめるか、忘れたら止まる形にする。
4. **費用が見える**。AIや外部サービスの従量課金は、使った額と上限を運営者が把握できるようにする。
5. **判断はまとめて求める**。細かい質問を小出しにさせず、「要決定」という欄に整理して出させる。

もう1つの柱が「変更影響 → 必須の検証」の対応表で、後で説明する。注意は1つだけで、書きすぎないこと。公式も「肥大したCLAUDE.mdは、肝心の指示を無視される原因になる」と警告している（[Best practices](https://code.claude.com/docs/en/best-practices)）。消しても困らない行は消す。

### 2. docs/（仕様書）: 「言った言わない」をなくす

仕様が会話の中にしかないと、次の会話のClaudeはコードから仕様を推測する。推測は少しずつずれ、3週間後には「そんな機能だったっけ？」になる。キットでは仕様書を主に3つに分ける。

| 文書 | 答える質問 | 例 |
|---|---|---|
| `docs/PRD.md` | 何を作るか | 「メールで登録できる」「投稿を予約できる」 |
| `docs/requirements/` | どう作るか | 画面の項目、DBの列、エラー時の文言 |
| `docs/decisions/`（ADR＝決定の記録） | なぜそう決めたか | 「なぜこのDBサービスにしたか。捨てた案は何か」 |

決まりは1行、「コードを変えたら、同じ作業の中で仕様書も直す」。これをClaudeに守らせるのが `/doc-sync` という手順書で、コミットの前に毎回実行させる。Claudeが直したコードと仕様書を見比べ、ずれを仕様書へ書き戻す。もう1つ、手で書き写した箇所は必ず古くなるので、仕様書が指すファイルの実在と更新日を機械で確かめる検査を2本同梱した。

### 3. tasks/BACKLOG.md（作業キュー）: 今やることを1か所に

思いついた順にチャットへ投げると、Claudeは目の前の依頼に全力を出し、前回の後始末を忘れる。だから、やることの並びを1本にする。

使うコマンドは2つだけだ。思いついたら `/add-task ○○したい`。Claudeが仕様書と照らし合わせ、実装はせずに、タスクとして一覧の末尾に書き足す。作らせるときは `/dev-loop`。Claudeが一覧の一番上から1件だけを取り、実装、検証、仕様書の更新、コミットまでを終えて報告する。作業中のタスクは常に1件以下、1タスク＝1コミットと決めてある。

BACKLOGにはもう1つ「要決定」という欄がある。料金・外部サービスの契約・利用者に見える文言など、AIが勝手に決めてはいけないことをここに溜めさせ、自分がまとめて決める。

### 4. スキル（手順書）: 毎回同じ手順をコマンドにする

Claude Codeでは、決まった手順を書いたファイルをスキルと呼び、会話の中で `/名前` と打つと呼び出せる（[Skills](https://code.claude.com/docs/en/skills)）。キットに入れたスキルのうち、中心になるのは次の9本だ。

| コマンド | 役割 |
|---|---|
| `/add-task` | 要望をタスクに変える（実装しない） |
| `/dev-loop` | タスクを1件、完了まで進める |
| `/doc-sync` | コードと仕様書のずれを直す |
| `/verify-integration` | DBなど、複数の部品をまたぐ変更を実物で検証する |
| `/verify-e2e` | 実際のブラウザで、利用者と同じ操作を通しで確認する |
| `/ui-polish` | 画面を作り、画面幅・状態・アクセシビリティを確認する |
| `/refactor` | 動きを変えずに中身を整理する |
| `/security-audit` | セキュリティの穴を探す（推測で報告させない） |
| `/maintenance` | 定期点検（週次。月1回は月次も） |

スキルには「やること」だけでなく「やってはいけないこと」も書く。`/dev-loop` には「テストが通らない状態でコミットしない」、`/security-audit` には「攻撃者の手順を1本書き、コードで到達を確かめてから報告する」とある。AIは頼まれたことに全力を出すぶん、止まる条件を手順書に埋めておかないと走りすぎる。

## 一番大事な表「変更影響 → 必須の検証」

CLAUDE.mdのもう1つの柱が次の対応表だ（抜粋。キット版には行がもう少しある）。左が「Claudeが今回どこを触ったか」、右が「その場合に必ずやる確認」。

| 触った層 | 必須の検証 |
|---|---|
| DBの構造や、DBに読み書きする処理 | 偽物のDBに差し替えず、実際のDBに書き込んで確かめるテスト |
| 外部AI・外部サービスの呼び出し | 受理されるかの検査 ＋ 実物で1周（実際のサービスを呼び、成果物まで見る） |
| 画面 | 実データを描画するブラウザテスト |
| メール送信・課金など外向きの副作用 | 開発環境から本物が飛ばないことの確認 |
| 定時処理 | 実際に1回動かして、結果の中身まで見る |

表にする理由は、「テストが全部緑なのに、本番では動かない」が実際に起きるからだ。私のプロジェクトでは、単体テスト1,000件以上とブラウザテストがすべて緑のまま、Web検索付きの文章生成・画像生成・ニュース取得・画像プレビューの4系統が同時に壊れていたことがある。原因は、テストが外部のAIサービスやブラウザを「モック」（本物のふりをする偽物）で置き換えていたこと。本物の側で仕様が変わっても、モックは決まった返事を返し続けるので、テストでは原理的に検出できない。

![モックのテストと「実物で1周」の比較図。モックは本物の仕様が変わっても緑のまま、実物で1周は本物を呼んで成果物まで見る](/blog-images/claude-code-non-engineer-workflow-mock-vs-real.png)

この失敗から、検証のやり方をその場の判断で選ばず、表で機械的に決めることにした。Claudeは表に従って「今回はDBを触ったので実際のDBでテストを回します」と自分で判断する。実物で1周には実費がかかる（私の場合1周約0.3ドル）ので、上限を超えたら止まって報告するようCLAUDE.mdに書いてある。あなたが覚えるのは「表に従わせる」ことだけでいい。

## 1日の流れ（実例）

私の平日の開発は、だいたいこの往復だ。

![1日の開発の往復。要望を言う → /add-task で一覧へ → /dev-loop で実装・検証・仕様書更新・コミット → 報告を読み画面を触る → 次の要望](/blog-images/claude-code-non-engineer-workflow-daily-loop.png)

```
あなた:  /docdd:add-task 設定画面のタブが少なくて寂しいので、分けたい
Claude:  （仕様書と照らして、実装はせずに一覧へ）
         T-42として一覧に書き足しました。
あなた:  /docdd:dev-loop
Claude:  （実装 → 表どおりに検証 → /doc-sync → コミット）
         T-42を完了しました。タブを4つに分け、ブラウザでの通し確認・仕様書更新済みです。
あなた:  （画面を見て）タブ名は「通知」より「お知らせ」にしてください。
Claude:  （直して再検証してコミット）
```

コードは読まず、画面と報告を読む。報告には、実行した検証と、できなかった検証とその理由が入るので、不安な点だけ追加で確認を頼めばいい。慣れてきたら `/loop /docdd:dev-loop` で連続して回し、たまった「要決定」だけまとめて答える使い方もできる（`/loop` はClaude Code本体の機能）。

## 非エンジニアが実際に踏む落とし穴（と、キットでの対策）

1. 手元では動くのに、公開先で壊れる。公開先だけ設定値が違っていた、はよくある事故で、手元のテストが緑でも防げない。「反映しました」の報告には「公開先で画面を開いて確認した」まで含めさせる。
2. AIの「できました」を素通しにしない。対策は (a) 検証の表に従わせる、(b) 画面を自分で触る、の2つで、コードを読む必要はない。読めないコードを眺めるより、触った画面の違和感の方がずっと当たる。
3. 仕様の判断を任せない。AIは「もっともらしい仕様」を作るのが得意で、それが一番怖い。線引きは「利用者に見えるか」だ。料金・文言・削除の挙動は「要決定」で自分が決め、名前の付け方やライブラリ（部品として使う既製のプログラム）の選定のような見えないものは任せてよい。

## キットの使い方（最初の30分）

### 手順0（まだプロジェクトが無い人だけ）

1. ターミナルを開く（Macは画面右上の虫めがねで「ターミナル」を検索、Windowsはスタートメニューで「PowerShell」）。ここから先の操作は、すべてこの画面で行う。
2. Claude Codeが未インストールなら、公式の[クイックスタート](https://code.claude.com/docs/en/quickstart)を済ませる。ターミナルで `claude` と打てば起動する状態になればよい。
3. 好きな場所に空のフォルダを作る。名前は半角英数で、空白を入れない（例: myapp）。ここがアプリ一式（プロジェクト）の置き場になる。
4. ターミナルに半角で `cd `（cdの後に空白1つ）と打ち、作ったフォルダをターミナルの窓へドラッグ＆ドロップしてEnter。ターミナルの「今いる場所」がそのフォルダになる。
5. `claude` と打って起動し、日本語で「○○のWebアプリを作りたい。土台の準備と、gitでの管理の開始までお願いします」と頼む。Claudeがアプリの骨組みを作り、変更履歴の記録を始める。gitが無いパソコンでは入れ方を案内してくれ、初めてのgitでは記録に使う名前とメールアドレスを聞かれることがあるので答える。

すでに自分のプロジェクトがある人は、そのフォルダで `claude` を起動して手順1から。gitで管理していなければ、手順3でClaudeが止まって勧めてくるので始めてもらい、`/docdd:init` をもう一度打つ（記録が始まるだけで、いまあるファイルの中身は変わらない）。

### 手順1〜5（全員）

Claude Codeの中で、次のコマンドを順に打つ。

1. `/plugin marketplace add no1013kota/claude-docdd-dev-kit` と打つ。キットの配布元（GitHub上の公開された置き場）をClaude Codeに登録する。GitHubのアカウントは要らない。
2. `/plugin install docdd@claude-docdd-dev-kit` と打つ。どの範囲に入れるか（User／Project／Local）を英語で聞かれたら、User（自分の全プロジェクトで使う）を選ぶ。最後に「Run /reload-plugins to activate.」と表示されたら、そのとおり `/reload-plugins` と打つ（再起動は要らない）。入ったかどうかは `/plugin` と打つと開く画面の「Installed」で分かる。手順1・2はどのフォルダで起動していてもよい。
3. `/docdd:init` と打つ（頭の `docdd:` を忘れない。何も付かない `/init` はClaude Code本体の別のコマンドで、キットとは無関係のCLAUDE.mdを作ってしまう）。この手順3だけは、自分のプロジェクトのフォルダ（一番上の階層）でClaude Codeを起動した状態で打つ。別の場所で起動していたら、`exit` で終了し、そのフォルダで `claude` を起動し直す。Claudeは次の順に進める。
   - `CLAUDE.md`・`docs/`・`tasks/`・検査スクリプト（仕様書の検査2本と、使っている部品の脆弱性検査1本）・許可設定（`.claude/settings.json`）・外部ツールの設定（`.mcp.json`）を置く。既にあるファイルは上書きしない（例外は、本体の `/init` が作ったCLAUDE.mdだけ。キットのものへ置き換えるか1回聞かれ、元は `CLAUDE.md.bak` に残る）。
   - 許可設定により、この先Claudeはファイルの編集とgitのコミットを確認なしで進める（編集のたびに確認してほしければ、Claudeに「.claude/settings.json の defaultMode の行を消して」と頼む）。
   - プロジェクト名や使っている道具など、穴埋めに必要なことを1回のメッセージでまとめて聞いてくる。分かる範囲で答える。道具は「調べて」と答えればClaudeがファイルから推定する。分からない箇所は `<...>` の穴のまま残り、報告に「未記入」として載る。後から直せばよい。
   - 作ったファイルをgitに登録し、コミットしてよいか確認してくるので、内容を見て許可する。
4. 手順3で答えた「やること」「やらないこと」が `docs/PRD.md` に入っている。読み返して、足りなければ自分の言葉で直す（最初は箇条書きで十分。ここだけは人間の仕事）。ファイルの開き方が分からなければ、Claudeに「PRDのやることを、次の内容に書き換えて: ……」と頼んでもよい。
5. `/docdd:add-task` の後ろに、最初に作りたい機能を日本語で書いて打つ（例: `/docdd:add-task メールアドレスで登録できるようにしたい`）。一覧に載ったら `/docdd:dev-loop` と打つ。

注意点は3つ。

- 作業中、Claudeはファイルの編集とコミット以外のコマンドを実行する前に「このコマンドを実行してよいか」と英語で確認してくる。内容をざっと見てEnterで許可すれば進む。分からないものは「これは何をするの？」と日本語で聞けば説明してくれる。Next.jsで作っているなら、次に起動したとき「.mcp.json のサーバーを使うか」と聞かれる（それ以外では聞かれない）。キットの手順書が使う道具なのでYesでよい。
- プラグインとして入れた手順書（スキル）は、利用者側では書き換えられない。自分のプロジェクトに合わせて直したくなったら、Claudeに「docdd プラグインの手順書を .claude/skills/ に写して」と頼めば自分のファイルになる（正確な頼み方とプラグインの外し方は配布元のREADMEにある）。
- キットは出発点で、育てて完成する。Claudeが同じ間違いを2回したらCLAUDE.mdに1行足す。同じ手順を2回説明したら、Claudeに「この手順をスキルにして」と頼んで自分のスキルにする。キット自体の新しい版は `/plugin` の画面（Installed）から受け取れる。

## まとめ

AIとの開発で信じていいのは、記憶ではなくファイルだ。毎回読まれる約束（CLAUDE.md）、いちばん正しい版としての仕様書（docs）、1本の作業キュー（BACKLOG）、止まる条件まで書いた手順書（スキル）の4点で、Claude Codeは「忘れない同僚」になる。

まず試してほしいのは、キットを入れて `/docdd:init` を打ち、最初の1件を `/docdd:add-task` と `/docdd:dev-loop` で作らせることだ。Claudeが同じ間違いを2回したらCLAUDE.mdに1行足す。次の会話から、Claudeはそれを読んで動く。
