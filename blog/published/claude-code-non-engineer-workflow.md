## 結論

非エンジニアがAIでアプリを作るとき、成否を分けるのは「上手な頼み方」だと思われがちだ。だが実際に効くのは**忘れても壊れない仕組み**の方だ。理由は単純で、AI（Claude Code）は会話が終わると内容を忘れ、人間（自分）は手順を忘れるから。この記事では、私が1人でX運用アプリ「Exos AI」を作り続けるために使っている仕組み——**約束（CLAUDE.md）・仕様書（docs）・作業キュー（BACKLOG）・手順書（skills）の4点セット**——を、誰のプロジェクトでも使える形に直して配布する。

📦 **配布ファイル**: [claude-code-dev-kit.zip（約31KB）](/blog-files/claude-code-dev-kit.zip) — この記事で説明する4点セットの雛形。中身はすべてテキストファイルで、開いて読める。**先に手を動かしたい人は、最後の「キットの使い方」へ飛んでもらって構わない。**

## この記事の前提

- **対象**: プログラミング経験がない、またはほぼ無い人。ターミナル（黒い画面）に1行コマンドを打つことには挑戦してもらう。
- **必要なもの**: [Claude Code](https://code.claude.com/)（AnthropicのAIコーディング環境。ターミナルで動く）だけ。GitHubアカウントは必須ではない——コードのバックアップや公開が必要になったときに作ればよい。
- **書かないこと**: Claude Codeのインストール手順そのもの（公式の[クイックスタート](https://code.claude.com/docs/en/quickstart)が正確）。特定のアプリの作り方。
- 用語を2つだけ先に。**git（ギット）**は「ファイルの変更履歴を記録する仕組み」で、Claude Codeが裏で使う。**コミット**は「作業内容をひとまとまりの記録として保存するgitの操作」。この2つはClaudeが実行してくれるので、意味だけ分かっていればいい。
- 私は非エンジニア出身で、この仕組みでWebアプリを開発・公開し、課金・自動投稿・AI生成を含む機能を1人で運用している。ここに書くのは**実際に運用している仕組み**で、理想論ではない。

## なぜ「頼み方」ではなく「仕組み」なのか

Claude Codeは優秀だが、2つの前提がある。

1. **会話（セッション）が終わると忘れる。** 公式ドキュメントにも「各セッションはまっさらな状態から始まる」とある（[Memory](https://code.claude.com/docs/en/memory)）。昨日決めたルールは、今日のClaudeは知らない。
2. **会話が長くなると精度が落ちる。** これも公式が明言している——「文脈が埋まるほど性能は落ちる」（[Best practices](https://code.claude.com/docs/en/best-practices)）。

人間側にも前提がある。**非エンジニアは「正しい確認手順」を知らないし、知っても忘れる。** 「公開する前にテストを回す」「データの置き場（データベース）の構造を変えたら反映の操作をする」——エンジニアなら体で覚えていることを、私たちは覚えていられない。

だから答えは「毎回うまく頼む」ではなく、**忘れる前提で外部に置く**ことになる。Claude Codeにはそのための公式の置き場が2つある。

| 置き場 | 何を置くか | いつ読まれるか |
|---|---|---|
| **CLAUDE.md** | プロジェクトの約束ごと（ルール・コマンド・構成） | **毎回のセッション開始時に自動で** |
| **skills（.claude/skills/）** | 決まった手順（`/コマンド名` で呼ぶ手順書） | 呼んだときだけ |

この2つに「仕様書（docs）」と「作業キュー（tasks/BACKLOG.md）」を足した4点が、配布キットの中身だ。

## 4点セットの全体像

```
あなたのプロジェクト/
├── CLAUDE.md              ← 約束。Claudeが毎回読む
├── .claude/skills/        ← 手順書。/add-task /dev-loop などのコマンド
├── docs/                  ← 仕様書。「何を作るか」「どう作ったか」の正本
└── tasks/BACKLOG.md       ← 作業キュー。やること一覧と「要決定」
```

それぞれの役割を、**なぜそれが要るのか**（失敗の形）から説明する。

### 1. CLAUDE.md — 「毎回言い直すこと」を書く場所

CLAUDE.mdは、Claudeがセッション開始時に必ず読む指示書だ。公式の推奨は「同じ修正を2回言ったら書く」「短く・具体的に」（[Memory](https://code.claude.com/docs/en/memory)）。

キットのCLAUDE.mdで一番大事なのは、冒頭の**5つの原則**だ。これは「非エンジニアが運用する」ことをClaudeに伝えるための原則で、私のプロジェクトで実際に事故を減らしてきた。

1. **黙って壊れない** — 失敗は必ず記録し、通知や状態確認コマンドに載せる。「エラーは出ないが何も起きない」が一番怖い。
2. **原因が開発知識なしで辿れる** — 「ログを読んでください」で終わらせない。画面かコマンド1つで分かる形にする。
3. **手順を人間の記憶に依存させない** — 忘れると壊れる手順は、1コマンドに畳むか、忘れたら止まる形にする。
4. **費用が見える** — AIや外部APIの従量課金は、実績と上限を運営者が把握できるようにする。
5. **判断はまとめて求める** — 細かい質問を小出しにさせず、「要決定」に整理して提示させる。

もう1つの柱が「**変更影響 → 必須の検証**」という対応表だ（後述）。

書くときの注意は1つだけ。**書きすぎない。** 公式も「Bloated CLAUDE.md files cause Claude to ignore your actual instructions（肥大したCLAUDE.mdは、肝心の指示を無視される原因になる）」と警告している。行ごとに「これを消したらClaudeは間違えるか？」と自問し、消しても困らない行は消す。

### 2. docs/ — 仕様書。「言った言わない」をなくす正本

非エンジニア開発で最初に崩壊するのはここだ。仕様が会話の中にしかないと、次のセッションのClaudeは**コードから仕様を推測する**。推測は少しずつずれ、3週間後には「そんな機能だったっけ？」になる。

キットでは仕様書を3つに分ける。

| 文書 | 質問 | 例 |
|---|---|---|
| `docs/PRD.md` | **何を**作るか | 「メールで登録できる」「投稿を予約できる」 |
| `docs/requirements/` | **どう**作るか | 画面の項目、データベース（以下DB）の列、エラー時の文言 |
| `docs/decisions/`（ADR＝決定の記録） | **なぜ**そう決めたか | 「なぜこのDBサービスにしたか。捨てた案は何か」 |

そして最重要ルールを1行で言うと、**「コードを変えたら、同じ作業の中で仕様書も直す」**。これをClaudeに守らせるのが `/doc-sync` という手順書（スキル）だ。コミット（前提の節で説明した、gitの保存の操作）の前に、毎回実行させる。

経験から1つ付け加えると、**「一覧」や「数値」を手で書き写すと必ず古くなる**。私のプロジェクトでは、仕様書に書いたファイルパスが実在するか・仕様書の表とDBの列が一致するか、を機械で突き合わせる小さな検査をClaudeに作らせている。キットのdocs/README.mdにその考え方を書いた。

### 3. tasks/BACKLOG.md — 作業キュー。「今なにをやるか」を1か所に

やりたいことを思いついた順にチャットへ投げると、Claudeは目の前の依頼に全力を出し、**前回の依頼の後始末を忘れる**。だからキューを1本にする。

- 思いついたら `/add-task ○○したい` — Claudeが仕様書と照合し、**実装せずに**タスクとして起票する
- 作らせるときは `/dev-loop` — キューの一番上から**1件だけ**を「実装→検証→仕様書更新→コミット」まで完了させる
- **WIP=1**（作業中は常に1件以下）。1タスク＝1コミット

もう1つ、BACKLOGには「**要決定**」という欄がある。料金・外部サービスの契約・利用者に見える仕様など、**AIが勝手に決めてはいけないこと**をここに溜めさせ、自分がまとめて決める。これが原則5の実装だ。

### 4. .claude/skills/ — 手順書。「毎回同じ手順」をコマンドにする

スキルは `.claude/skills/<名前>/SKILL.md` に置いたMarkdownの手順書で、`/名前` で呼び出せる（[Skills](https://code.claude.com/docs/en/skills)）。キットには9本入れた。

| コマンド | 役割 |
|---|---|
| `/add-task` | 要望をタスクに変える（実装しない） |
| `/dev-loop` | タスクを1件、完了まで進める |
| `/doc-sync` | コードと仕様書のずれを直す |
| `/verify-integration` | DB・APIなど境界をまたぐ変更の検証 |
| `/verify-e2e` | 実際のブラウザで通し確認 |
| `/ui-polish` | 画面の実装と、画面幅・状態・アクセシビリティの確認 |
| `/refactor` | 動きを変えずに中身を整理する |
| `/security-audit` | セキュリティの穴を探す（推測で報告させない） |
| `/maintenance` | 週1回の定期点検 |

ポイントは、**スキルの中に「やってはいけないこと」まで書く**こと。たとえば `/dev-loop` には「テストが通らない状態でコミットしない」、`/security-audit` には「攻撃者の手順を1本書き、コードで到達を確かめてから報告する（推測を報告しない）」と書いてある。AIは頼まれたことに全力を出すぶん、**止まる条件**を手順書に埋めておかないと走りすぎる。

## 一番大事な表 —「変更影響 → 必須の検証」

キットのCLAUDE.mdの中心は、この対応表だ（下の表は抜粋で、キット版には行がもう少しある）。

| 触った層 | 必須の検証 |
|---|---|
| DBの構造 | 統合テスト（実際のDBで） |
| サーバー側の処理 | 実物のDBを使って通すテスト（偽物のDBで済ませない） |
| 外部AI・外部APIの呼び出し | 受理されるかの検査 ＋ **実物で1周**（実際のAPIで成果物まで見る） |
| 画面 | 実データを描画するブラウザテスト |
| メール送信・課金など外向きの副作用 | 開発環境から本物が飛ばないことの確認 |
| 定時処理 | 実際に1回動かして**結果の中身**まで見る |

なぜ表にするのか。**「テストが全部緑なのに、本番では動かない」が実際に起きるから**だ。私のプロジェクトでは、単体テスト1,000件以上とブラウザテストがすべて緑のまま、Web検索付きの文章生成・画像生成・ニュース取得・画像プレビューの**4系統が同時に壊れていた**ことがある。原因は、テストが外部AIサービスを「モック」（本物のふりをする偽物）にしていたことで、**本物のAPIの仕様変更はモックのテストでは原理的に検出できない**。

この失敗から学んだのが、検証手段を**その場の判断で選ばず、表で機械的に決める**というルールだ。Claudeは表に従って「今回はDBを触ったので統合テストを回します」と自分で判断してくれる。あなたが検証手順を覚える必要はない。**覚えるのは「表に従わせる」ことだけ**でいい。表が守られたかどうかは、報告の「何を検証したか」を読み、仕上げに画面を自分で触って確かめる（あとで出てくる落とし穴2）。

## 1日の流れ（実例）

私の平日の開発は、だいたいこの往復だ。

```
あなた:  設定画面のタブが少なくて寂しいので、分けてください。
Claude:  （/add-task で起票 → /dev-loop で実装 → テスト → /doc-sync → コミット）
         T-42を完了しました。タブを4つに分け、ブラウザでの通し確認（E2E）・仕様書更新済みです。
あなた:  （画面を見て）タブ名は「通知」より「お知らせ」がいいな。
Claude:  （直して再検証してコミット）
```

要望を日本語で言う → 結果を自分の目で見る → 直しを言う。**コードは読まない。画面と報告を読む。** 報告には「何を検証したか」「何を検証できなかったか」が入るので（スキルにそう書いてあるので）、不安な点だけ追加で確認を頼めばいい。

慣れてきたら `/loop /dev-loop` で連続実行させ、たまった「要決定」だけまとめて答える運用もできる（`/loop` はキットではなくClaude Code本体の機能）。

## 非エンジニアが実際に踏む落とし穴（と、キットでの対策）

実際に踏んだ失敗を3つに絞る。すべてキットの文言に反映済みだ。

1. **「緑＝動く」ではない。** さっきの4系統の故障がまさにこれで、テストは「モックの世界で正しい」ことしか保証しない。外部サービスに触る機能は、**実物で1周**を検証に含める（実費はかかるが小さい。私の場合1周約0.3ドルで、上限額を超えたら止まるようCLAUDE.mdに書いてある）。もう1つ、手元のテストが全部緑でも、**公開先（利用者が実際に使う本番の環境）でだけ失敗している**ことがある——公開先だけ設定値が違う、はよくある事故だ。まだ公開していない人は、公開を始めた日からこの話が効いてくる。「反映しました」の報告には「公開先で画面を開いて確認した」まで含めさせる。
2. **AIの「できました」を素通しにしない。** ただし自分でコードを読む必要はない。対策は2つで、(a) 検証の表に従わせる、(b) **画面を自分で触る**。読めないコードのレビューより、触った画面の違和感の方がずっと精度が高い。
3. **仕様の判断を任せない。** AIは「もっともらしい仕様」を作るのが得意で、それが一番怖い。料金・文言・削除の挙動など利用者に見えるものは「要決定」に集めさせ、自分で決める。逆に、変数名やライブラリ選定のような**利用者に見えないもの**は任せてしまってよい（ただしADRに理由を書かせる）。

## キットの使い方（最初の30分）

**手順0（まだプロジェクトが無い人だけ）**:

- Claude Codeが未インストールなら、先に公式の[クイックスタート](https://code.claude.com/docs/en/quickstart)を済ませておく
- 好きな場所に空のフォルダを作る
- ターミナルを開く（Macは画面右上の虫めがねで「ターミナル」を検索、Windowsはスタートメニューで「PowerShell」）
- 半角で `cd `（cdの後に空白1つ）と打ち、**作ったフォルダをターミナルの窓へドラッグ＆ドロップ**してEnter——これでそのフォルダに移動できる
- `claude` と打って起動し、日本語でこう頼む——「**○○のWebアプリを作りたい。土台の準備と、gitでの管理の開始までお願いします**」

土台ができてから手順1へ進む。すでに自分のプロジェクトがある人は、そのフォルダで `claude` を起動して手順1から。

1. [claude-code-dev-kit.zip](/blog-files/claude-code-dev-kit.zip) をダウンロードして展開する
2. **配置はClaudeに任せる**——展開したフォルダの場所を伝えて「この中の `CLAUDE.md` `.claude/` `docs/` `tasks/` を、このプロジェクトに配置してください」と頼む。場所の伝え方は手順0と同じで、メッセージを打っている途中に展開したフォルダをターミナルへドラッグ＆ドロップすれば、場所が文字として貼り付く。配置が終わったら、いったん `exit` と打って終了し、もう一度 `claude` で起動し直す——置いたばかりの手順書（スキル）をClaudeに読み込ませるためだ。`.claude/` は名前がドットで始まる「隠しフォルダ」で、Finderやエクスプローラーでは表示されないことがあるため、手でコピーするより確実だ
3. 続けてこう頼む——「**CLAUDE.mdと docs/PRD.md の `<...>` を、このプロジェクトに合わせて埋めてください。埋められない箇所は質問してください**」
4. `docs/PRD.md` の「やること」「やらないこと」を自分の言葉で直す（最初は箇条書きで十分。ここだけは人間の仕事）。ファイルの開き方が分からなければ、Claudeに「PRDのやることを、次の内容に書き換えて: ……」と頼んでもよい
5. `/add-task 最初に作りたい機能` → `/dev-loop`

注意点も3つ。

- 作業中、Claudeは実行前に「このコマンドを実行してよいか」と確認してくる（英語のことが多い）。**内容をざっと見てEnterで許可**すれば進む。分からないものが出たら、全部拒否するのではなく「これは何をするの？」と日本語で聞けば説明してくれる。
- キット内の `npm run ...` はNext.js/Node.jsプロジェクトでの例。別の構成なら、手順3のときに「コマンド名をこのプロジェクトのものに直して」と一緒に頼めばいい。自分の構成が分からなければ、そのまま進めてよい——手順3でClaudeが気付いて直してくれる。
- キットは出発点で、**育てて完成する**。Claudeが同じ間違いを2回したらCLAUDE.mdに1行足す。同じ手順を2回説明したらスキルにする。この「2回ルール」は公式の推奨でもある。

## まとめ

持ち帰りは1つ。**AIとの開発で信じていいのは、記憶ではなく仕組み**——毎回読まれる約束（CLAUDE.md）、正本の仕様書（docs）、1本の作業キュー（BACKLOG）、止まる条件まで書いた手順書（skills）の4点だ。

次にやることも1つ。[キット](/blog-files/claude-code-dev-kit.zip)を展開して、CLAUDE.mdを**自分のプロジェクトの言葉で3行だけ**書き換えてみてほしい。仕組みは使い始めた日から効き始める。

*関連: この仕組みで運用しているアプリは [Exos AI](https://exosai.net)。公式ドキュメントは [Claude Code — Memory](https://code.claude.com/docs/en/memory)・[Skills](https://code.claude.com/docs/en/skills)・[Best practices](https://code.claude.com/docs/en/best-practices)。*
