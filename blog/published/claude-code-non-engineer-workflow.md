## 結論

非エンジニアがAIでアプリを作るとき、成否を分けるのは「上手な頼み方」だと思われがちだ。実際に効いたのは、決めたことを会話の外のファイルに書いておき、AIにも自分にも毎回それを読ませることだった。理由は単純で、AI（Claude Code）は会話が終わると内容を忘れ、人間（自分）は手順を忘れるから。この記事では、私が1人でX運用アプリ「Exos AI」を作り続けるために使っている4つのファイル（約束・仕様書・作業キュー・手順書）を、誰のプロジェクトでも使える形に直して配る。

配布ファイル: [claude-code-dev-kit.zip（約81KB）](/blog-files/claude-code-dev-kit.zip)。この記事で説明する4点セットの雛形に、仕様書の検査スクリプトと設定ファイルを足したもので、中身はすべて文字だけのファイルなので、開けば読める。先に手を動かしたい人は、最後の「キットの使い方」へ飛んでもらって構わない。

## この記事で出てくる4つの道具

Claude Codeを触ったことがない人向けに、先に登場人物を並べておく。どれも「プロジェクトのフォルダに置く、文字だけのファイル」で、特別なソフトは要らない。

![あなたが日本語で頼み、Claude Codeがプロジェクトのフォルダにある4つのファイル（CLAUDE.md・skills・docs・BACKLOG）を読んで作り、報告する図。CLAUDE.mdは毎回自動で読み、skillsは呼んだときに読み、docsは変えたら直し、BACKLOGは上から1件ずつ取る](/blog-images/claude-code-non-engineer-workflow-four-tools.png)

| 道具 | 何のファイルか | 役割を一言で |
|---|---|---|
| CLAUDE.md（約束） | フォルダの一番上に置く1枚のメモ | Claudeが会話を始めるたびに自動で読む。「このプロジェクトではこうする」を書く |
| docs/（仕様書） | 「何を作るか」「どう作ったか」を書いたファイルの束 | 会話が終わっても仕様が残る。迷ったらここを見る |
| tasks/BACKLOG.md（作業キュー） | やることを上から順に並べた1枚のファイル | Claudeはここの一番上から1件ずつ進める |
| .claude/skills/（手順書） | `/コマンド名` で呼び出せる手順のファイル。Claude Codeでは「スキル」と呼ぶ | 「タスクを1件終わらせる」のような決まった作業を、毎回同じ手順でやらせる |

本文で使う言葉も3つだけ先に説明しておく。ターミナルは、文字でパソコンに指示を出す黒い画面で、Claude Codeはここで動く。git（ギット）はファイルの変更履歴を残す道具で、Claude Codeが裏で使う。コミットは「ここまでの作業をひとまとまりとして記録する」というgitの操作。gitとコミットはClaudeが実行してくれるので、意味だけ分かっていればいい。

## この記事の前提

読む前に、対象と範囲を確認しておく。

- 対象は、プログラミング経験がない、またはほぼ無い人。ターミナルに1行コマンドを打つことには挑戦してもらう。
- 必要なものは [Claude Code](https://code.claude.com/)（AnthropicのAIコーディング環境。ターミナルで動く）だけ。GitHubアカウントは必須ではなく、コードのバックアップや公開が必要になったときに作ればよい。
- 書かないのは、Claude Codeのインストール手順そのもの（公式の[クイックスタート](https://code.claude.com/docs/en/quickstart)が正確）と、特定のアプリの作り方。
- 私は非エンジニア出身で、この4つの道具でWebアプリを開発・公開し、課金・自動投稿・AI生成を含む機能を1人で運用している。ここに書くのは実際に動かしているやり方で、理想論ではない。

## なぜ「頼み方」ではなく「ファイルに書く」なのか

Claude Codeは優秀だが、2つの弱点がある。

1. 会話（セッション）が終わると忘れる。公式ドキュメントにも「各セッションはまっさらな状態から始まる」とある（[Memory](https://code.claude.com/docs/en/memory)）。昨日決めたルールを、今日のClaudeは知らない。
2. 会話が長くなると精度が落ちる。これも公式が明言している。「文脈が埋まるほど性能は落ちる」（[Best practices](https://code.claude.com/docs/en/best-practices)）。

人間の側にも弱点がある。非エンジニアは「正しい確認手順」を知らないし、知っても忘れる。たとえば「公開する前にテストを回す」がそうだ。もう1つの例がDBで、DBとはアプリのデータの置き場（データベース）のことだ。DBの構造（どんな項目を保存するか）を変えたら、利用者が実際に使っている側（本番）のDBにも同じ変更を適用しなければならない。忘れると画面が壊れる。エンジニアなら体で覚えていることを、私たちは覚えていられない。

だから「毎回うまく頼む」ではなく、忘れる前提で、決めたことをファイルに書いて会話の外に置く。4つの道具のうち、CLAUDE.mdとスキルはClaude Codeが公式に用意している置き場で、仕様書と作業キューは私が足したものだ。

## 4つの道具を1つずつ説明する

フォルダに置くとこうなる。

```
あなたのプロジェクト/
├── CLAUDE.md              ← 約束。Claudeが毎回読む
├── .claude/skills/        ← 手順書。/add-task /dev-loop などのコマンド
├── docs/                  ← 仕様書。「何を作るか」「どう作ったか」のいちばん正しい版
└── tasks/BACKLOG.md       ← 作業キュー。やること一覧と「要決定」
```

それぞれを、無いと何が起きるか（失敗の形）から説明する。

### 1. CLAUDE.md（約束）: 毎回言い直していたことを書く場所

CLAUDE.mdは、Claudeが会話を始めるたびに必ず読む指示書だ。公式の推奨は「同じ修正を2回言ったら書く」「短く・具体的に」（[Memory](https://code.claude.com/docs/en/memory)）。

キットのCLAUDE.mdで一番大事なのは、冒頭の5つの原則だ。「このアプリは非エンジニアが1人で運用する」ことをClaudeに伝えるための原則で、私のプロジェクトで実際に事故を減らしてきた。

1. **黙って壊れない**。失敗は必ず記録し、通知や状態確認のコマンドに載せる。「エラーは出ないが何も起きない」が一番怖い。
2. **原因が開発知識なしで辿れる**。「ログ（動作の記録）を読んでください」で終わらせず、画面かコマンド1つで分かる形にする。
3. **手順を人間の記憶に頼らない**。忘れると壊れる手順は、1コマンドにまとめるか、忘れたら止まる形にする。
4. **費用が見える**。AIや外部サービスの従量課金は、使った額と上限を運営者が把握できるようにする。
5. **判断はまとめて求める**。細かい質問を小出しにさせず、「要決定」という欄に整理して出させる。

もう1つの柱が「変更影響 → 必須の検証」という対応表で、これは後で説明する。

書くときの注意は1つだけで、書きすぎないこと。公式も「Bloated CLAUDE.md files cause Claude to ignore your actual instructions（肥大したCLAUDE.mdは、肝心の指示を無視される原因になる）」と警告している（[Best practices](https://code.claude.com/docs/en/best-practices)）。行ごとに「これを消したらClaudeは間違えるか」と自問し、消しても困らない行は消す。

### 2. docs/（仕様書）: 「言った言わない」をなくす

非エンジニアの開発で最初に崩れるのはここだ。仕様が会話の中にしかないと、次の会話のClaudeはコードから仕様を推測する。推測は少しずつずれ、3週間後には「そんな機能だったっけ？」になる。

キットでは仕様書を3つに分ける。

| 文書 | 答える質問 | 例 |
|---|---|---|
| `docs/PRD.md` | 何を作るか | 「メールで登録できる」「投稿を予約できる」 |
| `docs/requirements/` | どう作るか | 画面の項目、DBの列、エラー時の文言 |
| `docs/decisions/`（ADR＝決定の記録） | なぜそう決めたか | 「なぜこのDBサービスにしたか。捨てた案は何か」 |

一番大事な決まりを1行で言うと「コードを変えたら、同じ作業の中で仕様書も直す」。これをClaudeに守らせるのが `/doc-sync` という手順書（スキル）で、コミットの前に毎回実行させる。動きとしては、Claudeが直したコードと仕様書を見比べ、ずれている箇所を仕様書へ書き戻す。

経験から1つ付け加えると、「一覧」や「数値」を手で書き写した箇所は必ず古くなる。私のプロジェクトでは、仕様書に書いたファイルの場所が実在するか、仕様書の表とDBの列が一致するかを、機械で突き合わせる小さな検査をClaudeに作らせている。キットの docs/README.md にその考え方を書いた。

### 3. tasks/BACKLOG.md（作業キュー）: 今やることを1か所に

やりたいことを思いついた順にチャットへ投げると、Claudeは目の前の依頼に全力を出し、前回の依頼の後始末を忘れる。だから、やることの並びを1本にする。

使うコマンドは2つだけだ。思いついたら `/add-task ○○したい` と打つ。Claudeが仕様書と照らし合わせ、実装はせずに、タスクとして一覧の末尾に書き足す。作らせるときは `/dev-loop` と打つ。Claudeが一覧の一番上から1件だけを取り、実装、検証、仕様書の更新、コミットまでを終えて報告する。作業中のタスクは常に1件以下、1タスク＝1コミットと決めてある。

もう1つ、BACKLOGには「要決定」という欄がある。料金・外部サービスの契約・利用者に見える文言など、AIが勝手に決めてはいけないことをここに溜めさせ、自分がまとめて決める。原則5をファイルの形にしたものだ。

### 4. .claude/skills/（手順書）: 毎回同じ手順をコマンドにする

Claude Codeでは、決まった手順を書いたファイルをスキルと呼ぶ。`.claude/skills/<名前>/SKILL.md` に置いた文章の手順書で、会話の中で `/名前` と打つと呼び出せる（[Skills](https://code.claude.com/docs/en/skills)）。キットには、私のプロジェクトで実際に使っているスキルを11本そのまま入れた（ブログ記事を書いて公開する2本だけは私のサイト専用なので外した。そのままなので、私のアプリ専用のコマンド名が残っている。「キットの使い方」の手順4で直す）。中心になるのは次の9本だ。

| コマンド | 役割 |
|---|---|
| `/add-task` | 要望をタスクに変える（実装しない） |
| `/dev-loop` | タスクを1件、完了まで進める |
| `/doc-sync` | コードと仕様書のずれを直す |
| `/verify-integration` | DBなど、複数の部品をまたぐ変更を実物で検証する |
| `/verify-e2e` | 実際のブラウザで、利用者と同じ操作を通しで確認する |
| `/ui-polish` | 画面を作り、画面幅・状態・アクセシビリティを確認する |
| `/refactor` | 動きを変えずに中身を整理する |
| `/security-audit` | セキュリティの穴を探す（推測で報告させない） |
| `/maintenance` | 週1回の定期点検 |

残りの2本（ブラウザ操作の道具箱、画面表示の高速化）は私の運用に合わせたもので、使わなければ消してよい。

スキルには「やること」だけでなく「やってはいけないこと」も書く。たとえば `/dev-loop` には「テストが通らない状態でコミットしない」、`/security-audit` には「攻撃者の手順を1本書き、コードで到達を確かめてから報告する（推測を報告しない）」とある。AIは頼まれたことに全力を出すぶん、止まる条件を手順書に埋めておかないと走りすぎる。

## 一番大事な表「変更影響 → 必須の検証」

ここで「テスト」という言葉を説明しておく。コードが期待どおりに動くかを機械で確かめる小さなプログラムのことで、全部通ると「緑」、1つでも失敗すると「赤」と表示される。

キットのCLAUDE.mdの中心は、次の対応表だ（下の表は抜粋で、キット版には行がもう少しある）。左の列が「Claudeが今回どこを触ったか」、右の列が「その場合に必ずやる確認」を表す。

| 触った層 | 必須の検証 |
|---|---|
| DBの構造や、DBに読み書きする処理 | 偽物のDBに差し替えず、実際のDBに書き込んで確かめるテスト |
| 外部AI・外部サービスの呼び出し | 受理されるかの検査 ＋ 実物で1周（実際のサービスを呼び、成果物まで見る） |
| 画面 | 実データを描画するブラウザテスト |
| メール送信・課金など外向きの副作用 | 開発環境から本物が飛ばないことの確認 |
| 定時処理 | 実際に1回動かして、結果の中身まで見る |

なぜ表にするのか。「テストが全部緑なのに、本番では動かない」が実際に起きるからだ。私のプロジェクトでは、単体テスト1,000件以上とブラウザテストがすべて緑のまま、Web検索付きの文章生成・画像生成・ニュース取得・画像プレビューの4系統が同時に壊れていたことがある。原因は、テストが外部のAIサービスやブラウザを「モック」（本物のふりをする偽物）で置き換えていたことだ。本物の側で仕様が変わっても、モックは決まった返事を返し続けるので、テストでは原理的に検出できない。

![モックを使ったいつものテストと「実物で1周」の比較図。モックは決まった返事を返すので本物のAIの仕様が変わっても緑のまま気付けない。実物で1周は本物のAIサービスを約0.3ドルで呼び、文章や画像の中身まで見るので壊れていれば分かる](/blog-images/claude-code-non-engineer-workflow-mock-vs-real.png)

この失敗から学んだのが、検証のやり方をその場の判断で選ばず、表で機械的に決めるという決まりだ。Claudeは表に従って「今回はDBを触ったので実際のDBでテストを回します」と自分で判断する。あなたが検証手順を覚える必要はなく、覚えるのは「表に従わせる」ことだけでいい。表が守られたかどうかは、報告の「何を検証したか」を読み、仕上げに画面を自分で触って確かめる（後で出てくる落とし穴3）。

## 1日の流れ（実例）

私の平日の開発は、だいたいこの往復だ。

![1日の開発の往復を示した図。あなたが要望を日本語で言い、あなたが /add-task と打つとClaudeがタスクとして一覧に書き足し、あなたが /dev-loop と打つとClaudeが実装・検証・仕様書の更新・コミットまで進め、あなたが報告を読んで画面を触って確かめ、直したい点を言って次の要望へ戻る](/blog-images/claude-code-non-engineer-workflow-daily-loop.png)

```
あなた:  /add-task 設定画面のタブが少なくて寂しいので、分けたい
Claude:  （仕様書と照らして、実装はせずに一覧へ）
         T-42として一覧に書き足しました。
あなた:  /dev-loop
Claude:  （実装 → 表どおりに検証 → /doc-sync → コミット）
         T-42を完了しました。タブを4つに分け、ブラウザでの通し確認・仕様書更新済みです。
あなた:  （画面を見て）タブ名は「通知」より「お知らせ」にしてください。
Claude:  （直して再検証してコミット）
```

要望を日本語で言う。結果を自分の目で見る。直しを言う。コードは読まず、画面と報告を読む。報告には、実行した検証と、できなかった検証とその理由が入る（スキルに「実行しなかった行は理由を報告する」とある）ので、不安な点だけ追加で確認を頼めばいい。

キットのCLAUDE.mdには「要望を受け取ったら `/add-task` で起票してから進める」と書いてあるので、慣れれば日本語で言うだけでもClaudeが同じ手順を踏む。それでも最初は、自分でコマンドを打つことを勧める。「いま何をしているか」が見えて安心だからだ。

慣れてきたら `/loop /dev-loop` と打って連続で回し、たまった「要決定」だけまとめて答える使い方もできる（`/loop` はキットではなくClaude Code本体の機能）。

## 非エンジニアが実際に踏む落とし穴（と、キットでの対策）

実際に踏んだ失敗を4つに絞る。すべてキットの文言に反映済みだ。

1. 「緑＝動く」ではない。さっきの4系統の故障がまさにこれで、テストは「モックの世界で正しい」ことしか保証しない。だから外部サービスに触る機能は、実物で1周を検証に含める（実費は私の場合1周約0.3ドルで、上限を超えたら止まるようCLAUDE.mdに書いてある）。
2. 手元では動くのに、公開先で壊れる。公開先（利用者が実際に使う本番の環境）だけ設定値が違っていた、というのはよくある事故で、手元のテストが全部緑でも防げない。「反映しました」の報告には「公開先で画面を開いて確認した」まで含めさせる。
3. AIの「できました」を素通しにしない。ただし自分でコードを読む必要はなく、対策は (a) 検証の表に従わせる、(b) 画面を自分で触る、の2つだ。読めないコードを眺めるより、触った画面の違和感の方がずっと当たる。
4. 仕様の判断を任せない（AIは「もっともらしい仕様」を作るのが得意で、それが一番怖い）。料金・文言・削除の挙動など利用者に見えるものは「要決定」に集めさせ、自分で決める。逆に、コードの中の名前の付け方やライブラリ（部品として使う既製のプログラム）の選定のような、利用者に見えないものは任せてよい（理由はADRに書かせる）。

## キットの使い方（最初の30分）

### 手順0（まだプロジェクトが無い人だけ）

1. ターミナルを開く（Macは画面右上の虫めがねで「ターミナル」を検索、Windowsはスタートメニューで「PowerShell」）。文字でパソコンに指示を出す画面が出る。ここから先の操作は、すべてこの画面で行う。
2. Claude Codeが未インストールなら、公式の[クイックスタート](https://code.claude.com/docs/en/quickstart)を済ませる。ターミナルで `claude` と打てば起動する状態になればよい。
3. 好きな場所に空のフォルダを作る。ここがアプリ一式（プロジェクト）の置き場になる。
4. ターミナルに半角で `cd `（cdの後に空白1つ）と打ち、作ったフォルダをターミナルの窓へドラッグ＆ドロップしてEnter。ターミナルの「今いる場所」がそのフォルダになる。
5. `claude` と打って起動し、日本語で「○○のWebアプリを作りたい。土台の準備と、gitでの管理の開始までお願いします」と頼む。Claudeがアプリの骨組みになるファイル一式を作り、変更履歴の記録を始める。

土台ができたら手順1へ進む。すでに自分のプロジェクトがある人は、そのフォルダで `claude` を起動して手順1から。

### 手順1〜6（全員）

1. [claude-code-dev-kit.zip](/blog-files/claude-code-dev-kit.zip) をダウンロードして展開する。`CLAUDE.md` `.claude/`（手順書と許可設定。隠しフォルダなので、見えなくても入っている）`docs/` `tasks/` の4つに加えて、仕様書の検査スクリプト（`scripts/`）、設定ファイル2つ（`.mcp.json` `package.scripts.json`）、短い説明書 `README.md` が入ったフォルダができる。検査スクリプトは「仕様書の更新日が古いまま」「仕様書が指すファイルが無い」を機械で見つけるもので、`README.md` に役割を書いた。
2. 配置はClaudeに任せる。展開したフォルダの場所を伝えて「この中の、一番上にある `README.md` 以外を、このプロジェクトに配置してください（`docs/` の中の README.md は仕様書の一部なので置いてください）。既にあるファイルは上書きしないでください。`package.scripts.json` の3行は package.json の scripts に足してください」と頼む。場所の伝え方は手順0と同じで、メッセージを打っている途中に展開したフォルダをターミナルへドラッグ＆ドロップすれば、場所が文字として貼り付く。`.claude/` は名前がドットで始まる「隠しフォルダ」で、Finderやエクスプローラーでは表示されないことがあるため、手でコピーするよりClaudeに任せる方が確実だ。
3. いったん `exit` と打って終了し、もう一度 `claude` で起動し直す。置いたばかりの手順書（スキル）をClaudeが読み込み、`/add-task` などのコマンドが使えるようになる。
4. 「CLAUDE.mdと docs/PRD.md の `<...>` を、このプロジェクトに合わせて埋めてください。あわせて、`.claude/skills/` の中にある、元のアプリ固有のコマンド（`npm run ...`）やファイル名を、このプロジェクトに合わせて直すか消してください。埋められない箇所は質問してください」と頼む。Claudeが穴埋めの箇所をプロジェクト名や、使っている道具（フレームワーク）の名前で埋める。スキルの中に残っている私のプロジェクト専用のコマンドも、あなたのプロジェクトで実際に使えるものへ置き換えるか消す。分からない箇所はまとめて質問してくる。
5. `docs/PRD.md` の「やること」「やらないこと」を自分の言葉で直す（最初は箇条書きで十分。ここだけは人間の仕事）。ファイルの開き方が分からなければ、Claudeに「PRDのやることを、次の内容に書き換えて: ……」と頼んでもよい。これで「何を作るか」の土台ができる。
6. `/add-task 最初に作りたい機能` と打ち、続けて `/dev-loop` と打つ。最初のタスクが一覧に載り、Claudeがそれを実装して検証し、仕様書を直してコミットするところまで進む。

注意点も3つ。

- 作業中、Claudeは実行前に「このコマンドを実行してよいか」と確認してくる（英語のことが多い）。内容をざっと見てEnterで許可すれば進む。分からないものが出たら、全部拒否するのではなく「これは何をするの？」と日本語で聞けば説明してくれる。なお、キットの `.claude/settings.json`（許可設定）では、ファイルの編集とgitのコミットは確認なしで進む設定にしてある。編集のたびに確認したければ、その中の `defaultMode` の行を消す。
- キット内のスキルの `npm run ...` は、私の構成（Next.js／Node.js）のコマンド名だ。手順4の依頼文で直る。
- キットは出発点で、育てて完成する。Claudeが同じ間違いを2回したらCLAUDE.mdに1行足す。同じ手順を2回説明したらスキルにする。この「2回ルール」は公式の推奨でもある。

## まとめ

覚えて帰ってほしいことは1つだけだ。AIとの開発で信じていいのは、記憶ではなくファイルだということ。具体的には、毎回読まれる約束（CLAUDE.md）、いちばん正しい版としての仕様書（docs）、1本の作業キュー（BACKLOG）、止まる条件まで書いた手順書（skills）の4点になる。

まず試してほしいのは、[キット](/blog-files/claude-code-dev-kit.zip)を展開して、CLAUDE.mdを自分のプロジェクトの言葉で3行だけ書き換えることだ。書いたその日の次の会話から、Claudeはそれを読んで動く。
