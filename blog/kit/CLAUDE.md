# <プロジェクト名> 開発ガイド

<何を作っているか1行>。仕様の正本は `docs/` 配下（PRD／要件定義／設計）。

## 前提：運営者は個人（非エンジニア想定）

このシステムは **1人の運営者が非エンジニアとして運用する**。**修正の量よりも運営のしやすさを優先する**。
実装の選択で迷ったら、次を満たす方を選ぶ。「動くが運営者には扱えない」形で完了扱いにしない。

1. **黙って壊れない** — 失敗は必ず記録する。**正常な空と失敗による空を別の値で表す**（例: 検索結果0件が「該当なし」なのか「取得失敗」なのかを呼び出し側が説明できる）。運営者が気付ける経路（通知・状態確認コマンド）へ載せる。
2. **原因が開発知識なしで辿れる** — 画面かコマンド1つで「いま何が壊れているか」が分かる。ログを読ませない。
3. **手順を人間の記憶に依存させない** — 忘れると壊れる手順（DB変更の適用など）は1コマンドへ畳むか、忘れたら止まる形にする。
4. **費用が見える** — 従量課金（AI・外部API）の実績と上限超過を運営者が把握できる。
5. **判断はまとめて求める** — 小さな確認を何度も挟まず、決めるべきことを整理して提示する（判断は「要決定」へ集約）。

この原則に反する実装を見つけたら、指摘して直す。回避策をドキュメントに書いて済ませない（手動の回避策は忘れられる）。

## 最重要ルール：ドキュメントとコードの同期

`docs/` 配下は常に実装の現状と一致していなければならない（Single Source of Truth）。

1. 仕様に影響する変更（機能追加・挙動変更・DB変更・API変更・画面変更・プロンプト変更）を実装したら、**同じ作業単位の中で**該当ドキュメントを更新する。ドキュメント更新までがタスクの完了条件。
2. どのドキュメントを更新すべきかは `docs/README.md` のドキュメントマップに従う。
3. 要件そのものが変わる場合は PRD を更新し、変更履歴に追記する。実装詳細は PRD ではなく要件定義書に書く。
4. コミット前に `/doc-sync` を実行して同期漏れを検出する。
5. ドキュメントに書かれていない仕様判断を実装したら必ず正本へ書き戻す。技術判断は `docs/decisions/` に ADR として記録する。

## スキルの地図

| スキル | いつ使う | 出力 |
|---|---|---|
| `/add-task` | 要望・不具合を受け取ったとき。**実装の前段** | BACKLOG へタスク起票（コードは変えない） |
| `/dev-loop` | タスクを1件完了させる（WIP=1） | 実装＋テスト＋docs同期＋コミット |
| `/doc-sync` | コミット前。毎回 | docs の更新と影響表 |
| `/verify-integration` | DB・API・定時処理・課金を触った | 統合検証の結果 |
| `/verify-e2e` | ユーザー向けフローを触った | 実ブラウザでの通し確認 |
| `/ui-polish` | 画面を作る／直す | 実装＋画面幅・状態・アクセシビリティ・実ブラウザ確認 |
| `/refactor` | 振る舞いを変えず内部品質を上げる（WIP=1） | 1単位のリファクタ |
| `/security-audit` | セキュリティの穴を探す。**反証してから**直すか要決定へ | 直した穴＋要決定＋棄却した候補と理由 |
| `/maintenance` | 週次・月次の定期点検 | 時間経過で壊れた箇所の報告 |

**流れ**: 要望 → `/add-task` → `/dev-loop`（中で `/doc-sync` と検証スキルを呼ぶ）→ コミット。
連続自動開発は `/loop /dev-loop`。

## 仕様の読み方（実装時に必ず該当箇所を参照）

- **何を作るか** → `docs/PRD.md`
- **どう作るか（画面・DB・処理）** → `docs/requirements/`
- version はファイル名ではなく文書内ヘッダを正とする

## 開発の進め方

- タスクは `tasks/BACKLOG.md` で管理する。ステータス運用ルールは同ファイル冒頭に記載。
- **要望を受け取ったら `/add-task` で起票してから実装へ進む。** `todo` が1件も無いと `/dev-loop` は動かない。
- `/dev-loop` の検証手段は下の「変更影響 → 必須の検証」で決める。
- 1タスク = 1コミット。コミットメッセージにタスクIDを含める（例: `feat(T-01): メール認証を実装`）。
- ユーザー判断が必要な事項は勝手に決めず、`tasks/BACKLOG.md` の「要決定」へ追記して先へ進む（可能なら暫定案を添える）。

## 変更影響 → 必須の検証（判断ではなく対応表で決める）

テストが緑でも「実際には動かない」ことがある。外部サービス・ブラウザ・メールなど**境界をモックしたテストでは原理的に検出できない**種類の不具合があるため、触った層で必須の検証を機械的に決める。**該当行が複数あればすべて実行する**。実行しなかった行がある場合は理由を報告する（黙って省略しない）。

| 触った層 | 必須の検証 |
|---|---|
| DB のスキーマ・権限・migration | `/verify-integration`（ロール権限を含む） |
| サーバー側の処理（API・Server Action） | 本番実装を実 DB で通すテスト |
| **DB へ書く値の形式**（キー・列挙・日付書式） | その値を**実際に insert する**テスト（文字列の組み立てを見る単体テストでは足りない） |
| **外部 AI／外部 API の呼び出し・プロンプト・出力の形** | 受理されるかの検査 ＋ **実物で1周**（実 API で成果物まで見る） |
| **画面** | `/ui-polish` ＋ **実データを描画する E2E**（画像・表・レイアウト崩れはブラウザでしか出ない） |
| 外向き副作用（投稿・メール・課金・削除） | 非本番で実行されないことの確認（環境ガードの有無） |
| **本番ビルドでしか出ない設定**（CSP・キャッシュ・事前描画） | `<ビルドコマンド>` ＋ 実ブラウザで公開ページのコンソールエラーまで見る |
| **外部サービス側の設定に依存する画面**（人間確認・OAuth・決済） | 実ブラウザ。相手側の許可ドメイン等はコードに現れない |
| 定時処理 | `/verify-integration` ＋ 該当処理を実際に1回動かし、**結果の中身**まで確認 |
| **ドキュメント・スキル定義のみ** | `/doc-sync`（参照先の実在＝コマンド名・ファイルパスを確認） |
| 上記以外 | `<全検査を回すコマンド>` |

**公開先へ反映したとき**は、公開先の画面を実際に開いて確認したことまで報告に含める（手元のテストが緑でも、公開先だけ設定値が違う事故は防げない）。

**「実物を1周」の意味**: リクエストが受理されることでは足りない。**応答をアプリが扱えて、最終成果物が正しいところまで**見る。費用が出る検査は上限を決め（例: 1周 $0.50）、超えたら止めて報告する。

### いつ回すか

| 段 | 何を回すか |
|---|---|
| 変更ごと | `<型検査> && <lint> && <単体・DBテスト>` |
| コミット前 | ＋ docs の日付・参照の検査 |
| **push 前（まとめて1回）** | ＋ `<ビルド>` ＋ `<E2E>` |

### 落とし穴（実際に踏みやすいもの）

- **パイプで終了コードを捨てるな。** `<コマンド> | tail` は `tail` の終了コードを返すため、失敗が成功に見える。出力はファイルへ落として `echo $?` を別に確認する。
- **画面の文言は E2E でしか守られていない。** 文言だけの変更でも単体テストは緑のまま通る。UI・文言を触ったら push 前に必ず E2E を回す。
- **新規ファイルは stage するまで「実在しない」扱いになる検査がある。** ファイルを追加した変更では先に `git add` する。
- **E2E の1件目の timeout を「flaky」と即断しない。** 編集直後の初回実行は初回コンパイルで時間切れになることがある。編集を挟まず再実行して緑かを見る。逆に、編集していないのに落ちたなら本物の失敗として扱う。
- **落ちた回数ではなく落ちる条件を探す。** 「5回に1回落ちる」は溜まったデータ量で決まる決定的な失敗だったことがある。
- **失敗を注入して確かめたら、必ず元へ戻す。** 注入した行・一時ファイルの削除まで含めて1つの作業とする。

## Definition of Done（全タスク共通）

- [ ] 実装が完了し、テストが通る
- [ ] **「変更影響 → 必須の検証」の該当行をすべて実行した**（未実行の行は理由を報告した）
- [ ] UI 変更では `/ui-polish` の画面幅・主要状態・アクセシビリティ・実ブラウザ検証が完了している
- [ ] `/doc-sync` 実行済み（該当ドキュメントを更新した、または影響なしを理由付きで確認した）
- [ ] `tasks/BACKLOG.md` のステータスと実装メモを更新した
- [ ] タスクIDを含むメッセージでコミットした

## 規約

- ドキュメント・コミットメッセージ・ユーザーへの応答は日本語。コードの識別子・コード内コメントは英語。
- **`git add -A` を使わない。** 利用者が並行して編集中のファイルを巻き込む。パスを明示して `git add` する。
- 秘密情報（APIキー・トークン・暗号鍵）は `.env`（gitignore 済み）のみに置く。コード・ドキュメント・コミットに実キーを書かない。
- 外部 API の仕様は変更が頻繁。該当箇所の実装時は必ず公式ドキュメントで最新仕様を確認する。
